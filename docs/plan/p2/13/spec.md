# P2-13：P2 退出评审与 P3 交接 — Spec

## 问题与目标

P2-01 至 P2-12 的 spec 与 goal 都已批准，路由均为 `done`。[P2-12](../12/goal.md#子任务跟踪) 已在同一候选上取得联合闭环、失败矩阵、网络审计、产物审阅与原版本地对照的证据，并明确把阶段退出判定留给本任务。目前还没有 P2 阶段评审，缺少以下几项：

- 把最终候选、[总计划 §12](../../master-plan.md#12-开发阶段与验收条件) 的四项 P2 退出条件、[阶段责任覆盖](../tasks.md#6-阶段验收覆盖)的全部主要交付和各任务证据串起来的权威结论；
- P2-12 中用户批准的范围例外与次级基准（高概率）判定在阶段层面如何计入；
- 仍以 P2 为负责阶段的未知项的处置；
- 向 P3 交接可消费内容与剩余规则未知项。

本任务做**阶段退出评审、必要的聚焦缺陷修复与文档交接**，形式沿用 [P1-14](../../p1/14/spec.md)。它核对已有交付，在最终候选上运行本地检查链，形成可追溯的 draft 评审，并交接 P3、P4、P5 与 P0 收尾的责任。不重新实现已有功能，不重做 P2-12 已有效取得的原版对照，也不把资源还原证据说成玩法保真。

任务导航见[阶段索引](../tasks.md#p2-13-p2-退出评审与-p3-交接)。进度分工遵循 [ADR-0014](../../../decisions/ADR-0014-status-summary-only.md)，P2/P3 重叠遵循 [ADR-0007](../../../decisions/ADR-0007-narrow-p2-overlap-p3.md)。

## 行为与边界

| 场景或状态转换 | 预期结果 | 拒绝或失败时的反馈 |
|---|---|---|
| 前置 goal 完成且证据可追溯 | 建立最终候选身份及条件、责任与证据的映射 | tracker、批准或链接不一致时列出受影响项；修复前不能写“全部完成” |
| 最终候选与 P2-12 候选只有文档、测试或技能文件差异 | 原版对照与产物审阅按无生产影响差异复用，记录差异清单 | 不能只写“生产未变”；须列出比较范围与依据 |
| 最终候选有改变转换输出、导入界面、呈现或播放路径的差异（S-04 修复，或经批准的责任任务修订） | 受影响的原版对照、产物审阅与实机核对在新候选上按原契约重做：agent 能运行的全部重跑；用户只重做受影响的试听与 P2-11 AC-21 中受影响的部分 | 未重做前，相应退出项为未验证，不能沿用旧候选的判定 |
| 本地检查链运行 | 分别记录命令、环境、退出码、实际断言与报告身份 | 首次失败保留原始报告。只有查明的环境原因（例如端口被占用）才可在不改代码、配置与断言的前提下重跑整条命令，并同时记录失败与重跑；原因不明的失败不能以重跑抵消 |
| 复现并定位了既定 P2 验收缺陷，且修复不改变契约 | 新增独立修复子任务，注明原责任与受影响的 AC；修复后按原判据与针对性回归重验 | 原因不明时不猜测修复；需要改变契约时停在用户批准关卡，不删断言、不放宽阈值 |
| 原版对照汇总 | 按[判定规则](#判定规则)计入：高概率与范围例外逐项披露 | 出现“差异，待修复”或必需项“无法判定”时，该退出条件不通过 |
| P2 负责的未知项，P2 部分已关闭或切片不需要 | 只改负责阶段一列，链接判定依据 | 证据不足时负责阶段不改；切片需要而未关闭时，相应退出条件不通过 |
| 有必需项未通过或未验证 | 结论为“不通过”，列出原责任、受影响条件与恢复路径 | 不能以“有条件通过”、移交 P3 或放宽判据掩盖 P2 缺口 |
| 全部必需项通过，尚有后续阶段事项 | 结论为“通过”；后续阶段事项列为遗留与交接，不使结论变为有条件通过 | 遗留事项不豁免其负责阶段的验收 |
| 评审完成，负责人尚未明确确认 | 评审保持 draft、结论待确认。STATUS 可以更新任务完成摘要与“下一步”：下一步指向待确认的评审，其中的未知项负责阶段与登记表一致。阶段状态仍为进行中，不写通过，评审记录列不变 | 批准本 spec/goal、执行 goal 或采纳推荐方案，都不等于确认评审结论 |
| 负责人明确确认评审结论 | 记录实际日期与范围，评审改为 accepted 并冻结；STATUS 的阶段总览状态与评审记录列与结论一致 | 当前阶段不自动切换为 P3；之后的变化写入新的评审记录或 ADR |

本任务以“证据完整、结论与逐项结果一致的 draft 评审及相关文档对齐”为完成标准，不等待负责人确认。确认是 goal 之外的阶段审批关卡。取得真实失败结果并写明问题与恢复条件，可以形成完整的“不通过”评审；缺少本契约要求的证据时，相应 goal 行须为 blocked，不能当作已完成。

### 判定规则

按用户 2026-10-08 的决定，原版对照沿用 P2-12 已批准的判定分类：

- **一致：** 计入通过，包括 P2-12 判为高概率的一致，例如依据等价链、视频基准（“一致（高概率，视频基准）”）或用户回忆（“一致（高概率，用户回忆）”）的判定。评审须按类别列出数量、置信度与依据类型，不能把高概率写成直接截图对照。
- **用户批准的范围例外：** 不计为一致，也不阻止“通过”。评审逐项列出，交 P3 在实现运行时显示后复核外观。
- **差异，已修正 / 差异，已归因：** 按其依据计入。已归因项须链接独立证据。
- **差异，待修复，或必需项无法判定：** 该退出条件不通过。

### 持久化与兼容

本任务不访问或改变玩家的 IndexedDB、localStorage 或个人浏览器 profile。E2E 沿用隔离的合成 context 与被忽略的输出目录。真实数据候选核对在 Node 中运行，输出只在 `local/`。

S-04 的修复不得改变缓存记录格式或 `ConverterVersion` 的语义。若修复改变了转换输出，转换器版本须按责任任务的既有规则递增，旧缓存按既有行为拒绝恢复；这属于契约变化，须先经用户批准。没有存档迁移；冻结前的评审可以修正，冻结后的变化写入新记录。

## 技术决定

1. **判据不新增、不豁免：** 总计划定义退出条件，阶段索引提供责任覆盖，goal/subtask 提供状态与证据，新评审独占最终判定。原版对照按[判定规则](#判定规则)计入（用户 2026-10-08 决定）。结论只有“通过”或“不通过”；“有条件通过”不用来掩盖 P2 缺口，后续阶段的遗留也不使结论变为有条件通过。
2. **最终候选上的完整本地链：** 实际运行以下检查，各命令按现有语义使用，不新增编排脚本：
   - `pnpm check`；
   - `python3 -B -m unittest discover -s tools/ghidra -p 'test_*.py'`；
   - `pnpm test:e2e`，覆盖全部三个项目，运行一次；
   - `pnpm --silent check:compliance`。

   E2E 的用例数按当时配置的 `--list` 核对，181 不是固定目标；必需用例不能被跳过。发生修复后按受影响面重验，最终证据须对应修复后的候选。
3. **真实数据核对由 agent 完成：** 在最终候选上重跑 P2-12 的候选核对脚本，确认四组完整、`loadMission` 成功，身份与 P2-12 候选一致，或差异已按技术决定 4 处理。脚本不被跟踪，证据须记录其文件哈希，以便复现。原版数据或脚本不可用时，相应 goal 行为 blocked，不以合成数据代替。
4. **按候选身份复用历史证据：**
   - **只改文档、测试或技能文件：** 复用 P2-12 的原版对照、会话与产物审阅，并记录差异清单。
   - **生产受影响：** 按 [P2-12 候选变化规则](../12/spec.md#候选身份)重做受影响的类别，执行者沿用原契约。agent 重做视觉（经 Computer Use）、布局、二维资源与任务对照，用户只重做受影响的试听。
   - **其他浏览器证据：** P2-04、P2-10 的证据与 P2-11 的自动用例由本轮 E2E 与差异分析判断是否仍然有效。P2-11 AC-21 的用户实机核对只在导入、缓存、查看或试听路径受影响时由用户重做受影响的部分。
5. **失败与重跑：** 沿用 P1-14 技术决定 5。首次失败保留原始报告；只有查明的环境原因可在不改代码、配置与断言的前提下重跑整条命令；不删除用例、不加重试、不放宽阈值。
6. **聚焦修复（用户 2026-10-08 决定）：**
   - **前提：** 只对已复现、已定位、不改变契约的缺陷新增修复子任务，不预建空修复项。
   - **内容：** 写明原责任任务与 AC、复现与根因、写入范围、验证方法。
   - **位置：** 新 ID 插在最终对齐之前；最终对齐依赖全部修复项，且只做验证。
   - **避免死锁：** 修复项不依赖发现它的 blocked 行；取得复现与定位证据后即可执行，发现项在修复重验后再完成。
   - **完成要求：** 每项补针对性回归，运行 `pnpm check` 及受影响的 E2E、合规或 Python 检查，单独提交；旧的正确证据保留不改。
   - **契约变化：** 需要改变契约的缺陷回到责任任务修订其 spec/goal，经用户批准后执行，本任务的相应行保持 blocked。
7. **P2 负责的未知项（用户 2026-10-08 决定）：**
   - **P2 部分的范围：** 以 P2-01 的切片定义与 P2-12 的必判范围为准。
   - **已关闭或切片不需要：** 只把负责阶段一列改为后续阶段，链接判定依据，并更新登记表的 `updated:`。
   - **证据不足：** 不改负责阶段，在评审中写明缺少的证据。
   - **切片需要而仍未关闭：** 相应退出条件不通过。

   已确认的 U-032 负责阶段写为 P2-12，属于历史记录，不需要改。
8. **评审路径与确认关卡：**
   - **路径：** 评审写在 `docs/reviews/P2-exit.md`。执行前检查该路径；若已有冻结记录，按命名约定另建新记录，不覆盖。
   - **状态：** 评审默认为 draft，只有负责人明确确认具体结论才改为 accepted 并冻结。
   - **STATUS：** 确认前只更新任务完成摘要与“下一步”，阶段状态不写通过；确认后再同步阶段状态与评审记录列。
   - **阶段切换：** 不自动切换当前阶段。
9. **交接不提前设计：** 评审只列出可复用设施、P3 必须另行设计的部分（例如飞行渲染、HUD 动态绘制、光照、运动与碰撞）、外观复核项与研究项。不为 P3 预先泛型化 Runtime、Session 或查看器，不把查看器的呈现约定当作飞行渲染契约。
10. **最终范围扫描：** 评审与证据文档定稿后，运行 `pnpm --silent check:original`，核对实际工作树、索引、未忽略的未跟踪文件与完整 `dist`。该命令要求 `dist` 存在且来自当前候选的构建。只改文档且构建输入身份未变时，工程、E2E 与许可证据可以复用。

## 验证策略

- **单元/契约测试：** 常规核验复用既有 Vitest 与 Python 测试；实际缺陷修复补针对性回归，不改宽松断言。
- **Replay/一致性：** 不新增 replay 要求。任务载入的一致性沿用 P2-12 M-4（两次载入深度一致），本轮由真实数据候选核对确认 `loadMission` 成功与身份不变；不推进 tick、不随机生成世界。
- **浏览器验证：** 运行完整的 `pnpm test:e2e`，覆盖三个项目，使用隔离的合成 context 与已安装的 Chrome，按 [browser-testing](../../../../.agents/skills/browser-testing/SKILL.md) 核验真实观测与清理。不使用个人 profile，不复用未知服务器。其他浏览器归 P5。
- **实机/原版对照：** 本任务不新增原版对照。最终候选与 P2-12 候选只有无生产影响差异时，复用 P2-12 的判定与 P2-11 AC-21 的实机核对。生产受影响时按原契约重做受影响的部分：
  - agent 按[原版证据获取](../../../guides/original-evidence.md)与 P2-12 技术决定 8 的修订，重做视觉、布局、二维资源与任务对照；
  - 用户只重做受影响的试听，以及 P2-11 AC-21 中受影响的真实界面核对（agent 浏览器验证只用合成数据）。

  截图与帧只在 `local/`。
- **工程检查：** `pnpm check`、Python 合成测试、`pnpm test:e2e`、`pnpm --silent check:compliance`，文档定稿后运行 `pnpm --silent check:original`。正常检查不安装或升级依赖，缺依赖时才按 frozen lock 恢复。生成本 spec 只做文档链接、元数据与结构检查。
- **证据位置：** 本任务的 subtask 记录本轮命令、适用性、修复与清理证据，goal 维护唯一执行状态，评审引用证据并作出判定。原责任任务只作来源引用，不改写旧证据。

## 风险与恢复

风险等级：**中**。常规评审不改实现，但错误的证据复用、遗漏的高概率或范围例外披露、过早的负责阶段变更或批准记录，都可能造成阶段误判；必要修复涉及已有实现，可能引入回归。

- **旧成功套到新候选：** 以候选身份与差异清单约束复用；生产受影响时重做受影响的对照，不沿用旧判定。
