# P1-03：快照、状态哈希与输入 replay — Spec

## 问题与目标

P1-02 已交付合成纯 Core：`step()` 返回事件，状态检查副本给出完整权威状态。但现在还没有版本化的快照编码、状态哈希、输入记录和重放校验，因此既无法证明总计划 P1 退出条件中的"同一输入记录 replay 后事件流与状态哈希一致"，也无法发现输入或状态偏差。P1-02 技术决定 7 中的 tick/实体 ID 上限守卫因缺少状态恢复入口，至今只有审阅证据。

本任务在 Core 内建立以下能力：

- 合成场景的版本化快照、唯一确定的规范文本和 64 位状态哈希；
- 严格校验的快照恢复；
- 输入录制、在新实例上 replay，以及事件流与周期检查点哈希的比对。

完成后，Node 测试可以用固定种子和逐 tick 输入在全新实例上重放，得到与原运行完全一致的事件流和检查点哈希。比对报告最早的**可观察差异**：事件不同的第一个 tick，或状态哈希不同的第一个检查点。检查点间隔为 1 时，状态采样覆盖每个 tick，报告首次事件或哈希差异；间隔更大时，持续到检查点且产生不同哈希的状态偏差在该点显现，而在两个检查点之间出现又消失的偏差可能检测不到（技术决定 9）。任何间隔均不排除哈希碰撞。一致性只承诺同一代码版本、同一 JS 运行时，不承诺跨浏览器或跨版本逐位一致（[总计划 §5](../../master-plan.md#5-状态管理与通信约定)、[§11](../../master-plan.md#11-测试与质量门槛)）。

阶段范围依据[总计划](../../master-plan.md#12-开发阶段与验收条件)，任务导航见[阶段索引](../tasks.md#p1-03-快照状态哈希与输入-replay)。前提为 [P1-02 最终证据](../02/subtasks/05-final-alignment.md#完成证据)。

## 范围

### 包含

- **S-01 版本化快照：** 从场景取得纯数据快照，包含全部权威状态（含 RNG 状态与 ID 分配器），带格式标识与版本。读取快照没有副作用。
- **S-02 规范文本与状态哈希：** 每个快照有唯一确定的规范文本；状态哈希为该文本的 FNV-1a 64 位值，只用于一致性校验。
- **S-03 严格恢复：** 从快照纯数据（包括 JSON 往返后的数据）恢复出等价且独立的场景，非法快照显式拒绝；借助恢复补齐 P1-02 tick/ID 上限守卫的边界测试。
- **S-04 输入录制：** 录制会话从创建配置开始，独占一个场景，按顺序记录每个成功执行的 tick 的输入，并产出原运行的事件流和周期检查点哈希。
- **S-05 Replay 与比对：** 在全新实例上重放输入记录，得到同形结果；比对两份结果，报告最早差异的 tick 与类别；非法记录或结果显式拒绝。
- **S-06 本地验证：** Node 单元测试覆盖已知答案、往返、逐字段敏感、负向偏差和数值边界；既有工程检查保持通过。

### 不包含

- 不实现 IndexedDB/localStorage/文件读写、存档系统、存档槽、导出/导入界面，也不实现玩家 replay 管理或回放 UI。快照不是已批准的玩家存档格式；正式存档按[总计划 §8](../../master-plan.md#8-浏览器运行存档与隐私)另行设计。
- replay 不从中途快照开始，P1 只支持从创建配置开始。不做旧版本快照或记录的迁移，也不做压缩、流式写入或记录大小上限策略。
- 是否默认录制、如何把录制接入调度属于 P1-04/05；浏览器中的重放和对比方法属于 P1-10。Core 只提供录制与重放能力。
- 不消费或重放 Event Bus，不用事件重建状态；事件流只作一致性校验。
- 不承诺跨浏览器、跨 JS 引擎或跨代码版本的逐位一致，也不加入行为版本号。
- 哈希不是安全或防篡改机制。不引入密码学哈希、Web Crypto 或新依赖。
- 不改变 P1-02 已批准的场景规则、输入契约、事件和投影形状，不实现任何原版规则。
- 不运行 CI、部署或云操作；遵循 [ADR-0012](../../../decisions/ADR-0012-local-p1-defer-ci-deployment.md)。

## 当前实现与依据

- [createSyntheticScene](../../../../src/core/synthetic-scene.ts) 只接受 `{seed, tickRateHz?}`，返回 `SyntheticScene`（`step`/`inspect`/`uiProjection`/`renderState`），没有从任意状态创建场景的入口。`SyntheticSceneState` 字段为 `scenario`、`tick`、`tickRateHz`、`seed`、`rngState`、`nextEntityId`、`mover`、`marker`，即 P1-02 定义的完整权威状态。
- [rng.ts](../../../../src/core/rng.ts) 的 Mulberry32 状态是单个 uint32（`RngState = number`），不存在其他隐藏的随机状态。
- `step()` 先完成全部校验与守卫（输入、命令计划、tick 安全整数、ID 安全整数、位置有限性），再修改状态。tick/ID 上限守卫已实现但无法测试（[P1-02 技术决定 7](../02/spec.md#技术决定)）。
- 既有测试覆盖了相同条件下两个独立实例的一致性和输出的 JSON 往返形状（[step 测试](../../../../src/core/synthetic-scene-step.test.ts)、[场景测试](../../../../src/core/synthetic-scene.test.ts)），没有序列化、哈希或 replay。
- Core 类型环境只有 ES2023 lib，不含 DOM/Node 声明，因此不能使用 `TextEncoder`、`crypto` 或 `Buffer`；lint 禁止 async/await 及宿主时间/随机。Web Crypto 摘要是异步的，不能在 Core 中使用。依据：[工程约定](../../../engineering/README.md)。
- 架构依据为[总计划 §5](../../master-plan.md#5-状态管理与通信约定)：replay 输入是"初始状态 + 种子 + 每 tick 输入与命令"，事件流与周期性状态哈希只用于一致性校验，快照通过显式序列化取得。另见 [§11 核心自动测试](../../master-plan.md#11-测试与质量门槛)和 [ADR-0006](../../../decisions/ADR-0006-core-returns-events.md)。
- 本任务没有原版研究依据，不新增 U/B 事实。

## 行为与边界

### 快照

- 快照由 Core 从场景当前状态生成，包含格式标识、版本和 `SyntheticSceneState` 的全部字段，见下方数据模型。
- 每次读取都返回一份新的、深冻结的纯数据，与场景内部及其他读取结果隔离；读取不改变 tick、状态、RNG 或 ID 分配器。
- 快照可以用 JSON 表示，所有数值都是有限数；JSON 往返后的数据能被恢复接受。

### 规范文本与状态哈希

- **规范文本**是无空白的紧凑 JSON。字段顺序按下方数据模型表固定，与调用者对象的键顺序无关；数值按 ECMAScript 数字转字符串规则（`JSON.stringify`）书写，`-0` 写作 `0`；全文只含 ASCII。
- **状态哈希**是对规范文本字节（即各字符的 ASCII 码）计算的 FNV-1a 64 位值（offset basis `0xcbf29ce484222325`，prime `0x100000001b3`），输出为 16 位小写十六进制字符串，保留前导零。
- 场景的状态哈希就是其当前快照规范文本的哈希。两个场景的权威状态（`-0` 视同 `0`）相等，当且仅当它们的规范文本相等。哈希碰撞不被宣称为不可能；比对时事件逐字段比较，哈希只代表状态。

### 恢复

恢复接受快照纯数据（类型未知，可来自 JSON 往返），全部校验通过后返回一个新场景。新场景的检查副本、两种投影、快照和哈希都与来源相同；之后用相同输入继续 step，产生相同的事件与状态。新场景不保留对输入对象的引用。

| 字段 | 校验规则 |
|---|---|
| 顶层 | 对象，只含 `format`、`version`、`state`；`format` 为 `'osr-synthetic-snapshot'`，`version` 为 `1` |
| `state` | 只含 `scenario` 与下列 7 个字段；`scenario` 为 `'synthetic'` |
| `tick` | 安全整数，≥ 0 |
| `tickRateHz` | 与创建配置规则相同：有限正数，且倒数有限 |
| `seed`、`rngState` | `0` 至 `4294967295` 的整数 |
| `nextEntityId` | 安全整数，≥ 2 |
| `mover` | 只含 `id`、`position`；`id` 为 `1`；`position` 只含 `x/y/z`，`x` 有限，`y`、`z` 为 0 |
| `marker` | `null`，或只含 `id`、`position`；`id` 为安全整数且 2 ≤ `id` < `nextEntityId`；三个坐标都在 `[-5,5)` |

- 任何数值字段的 `-0` 视同 `0`，恢复时规范化为 `+0`。不接受数字字符串、BigInt、`NaN` 或 `±Infinity`；缺失字段和额外字段都会被拒绝。
- 拒绝时抛 `CoreInputError`，`path` 以 `snapshot` 开头（例如 `snapshot.state.marker.id`），不返回半构造的场景。
- 恢复只校验上述结构与不变量，不检查状态能否由某段历史到达，例如 `rngState` 与 `seed`、`nextEntityId` 的关系，或标记坐标与 RNG 的关系。这类状态仍按 P1-02 规则确定地运行。

### 数值上限边界（补 P1-02 技术决定 7）

- 用恢复构造 `tick = Number.MAX_SAFE_INTEGER - 1`：一次有效 step 成功并到达上限，下一次 step 抛 `CoreInputError`，失败前后的快照与哈希相同。
- 用恢复构造 `nextEntityId = Number.MAX_SAFE_INTEGER - 1`、`marker = null`：一次添加成功，标记 ID 为 `MAX_SAFE_INTEGER - 1`，分配器到达 `MAX_SAFE_INTEGER`；移除后再添加抛 `CoreInputError`，失败前后的快照与哈希相同。同一分配器状态下不需要分配 ID 的合法 tick 仍正常推进。
- 这些测试只验证 P1-02 已有守卫，不改变其语义。

### 录制

- 创建录制会话时，提供与 `createSyntheticScene` 规则相同的配置和一个检查点间隔（正安全整数）。会话在内部创建并独占一个新场景，不接受外部已有的或恢复得到的场景，以保证记录从创建配置开始。
- 会话的 step 与读取行为和普通 `SyntheticScene` 相同。step 正常返回时，把该 tick 输入的规范副本（只含契约字段，`moveX` 的 `-0` 记为 `0`）按顺序追加到记录，并把返回事件追加到事件流。含 `command-rejected` 的合法 tick 同样记录；“成功执行”不等于所有命令都被接受。抛 `CoreInputError` 的调用不记录，录制可以继续，结果等同于这次调用没有发生。
- 配置和已记录输入均与调用者对象隔离；调用者后来修改配置、输入轴、命令对象或数组，不改变场景及已录制的数据。录制不修改或冻结调用者的对象。
- 检查点位于 tick 0、检查点间隔的每个正整数倍，以及导出时的当前 tick（最终 tick）；同一 tick 只出现一次。
- 导出返回当时的记录和结果，都是深冻结的纯数据。导出不改变场景，导出后可以继续录制；较早导出的数据不随后续录制改变。
- 记录写入生效的 `tickRateHz`：配置省略时写入默认值 60。

### Replay

- replay 先校验记录的格式、版本、配置、检查点间隔和 `ticks` 数组结构，再在全新实例上逐 tick 调用 step，得到与录制同形的结果。
- 记录中任何会被 Core 拒绝的内容（结构、范围、额外字段、数值守卫）都抛 `CoreInputError`，`path` 以 `record` 开头；顶层或配置错误指向对应字段，某 tick 内的错误包含数组索引，例如 `record.ticks[12].commands[0].type`。`ticks[0]` 对应模拟 tick 1；此时不返回部分结果。稀疏 `ticks` 数组的缺失项不是空 tick，须按该索引拒绝。
- 空记录是合法的，其结果只有 tick 0 检查点，没有事件。
- replay 不读取、不修改原录制会话；同一记录 replay 两次，结果相等。

### 结果比对

- 比对接受两份结果（期望与实际），可以是 JSON 往返后的数据。比较前对两份结果分别做下列结构校验（技术决定 10），任一项不满足即抛 `CoreInputError`，`path` 以 `expected` 或 `actual` 开头并指向字段：
  - 顶层只含 `events`、`checkpoints`，两者都是无缺失项的数组。
  - `checkpoints` 非空；每项只含 `tick`、`hash`；第一个 tick 为 0，tick 为非负安全整数且严格递增；`hash` 为 16 位小写十六进制字符串。**最后一个检查点的 tick 即该结果的最终 tick。**
  - 每个事件符合 P1-02 的 `DomainEvent` 判别联合，没有缺失或额外字段：
    - `tick` 为安全整数，在 1 至最终 tick 之间；`commandIndex` 为非负安全整数。
    - `marker-added`/`marker-removed` 的 `entityId` 为不小于 2 的安全整数；`position` 只含 `x/y/z`，三个坐标都在 `[-5,5)`。
    - `command-rejected` 的 `commandType` 与 `reason` 只能是 `add-marker` 配 `marker-already-exists`，或 `remove-marker` 配 `marker-not-found`。
  - 事件按 tick 非递减排列；同一 tick 内 `commandIndex` 从 0 起连续递增。
  - 比对器只校验结构与上述不变量，不重演事件历史，也不推断或检查检查点间隔。检查点是否齐全，由重新 replay 输入记录来保证。
- 对每个 tick，比较该 tick 的事件序列（数量、顺序和全部字段值，与对象身份或键顺序无关）和该 tick 的检查点（是否存在及哈希值）。
- 返回最早出现差异的 tick：若该 tick 的事件不同，类别为 `events`，否则为 `checkpoint`。两份结果完全相同时返回一致。
- 差异是正常的数据结果，不抛异常。
- **检测边界（技术决定 9）：** 比对的是运行结果，不是输入记录本身。
  - 只改变状态、不改变事件的偏差，若持续到检查点且该点哈希不同，则在其后第一个哈希不同的检查点（或最终 tick）报告；若在下一个检查点前已消失，则可能不报告。例如 seed 0、60 Hz、无命令时，输入 `[0,0]` 与 `[1,-1]` 在 tick 1 状态不同，但 tick 2 的完整状态和全部事件相同，因此间隔 2 下比对一致。这是周期哈希的采样粒度，不是哈希碰撞。
  - 需要精确定位首次偏差时，使用间隔 1。
  - 没有改变任何事件或状态的输入差异不报告，例如 `moveX` 为 `-0` 与 `0`，或被浮点舍入完全吸收的极小差异。
  - 需要确认两份记录的输入是否相同时，由调用者直接比较记录数据，不属于结果比对。

## 数据模型与契约

权威定义位于计划新增的 `src/core/` 文件，复用 [synthetic-scene.ts](../../../../src/core/synthetic-scene.ts) 中已有的 `SyntheticSceneState`、`TickInput`、`DomainEvent`、`SyntheticSceneConfig` 与 `SyntheticScene`。这里只约定形状、规则和所有权，类型名与文件布局由 goal 确定。

| 数据 | 形状、约束与规范字段顺序 | 权威所有者 | 输入/输出边界 |
|---|---|---|---|
| 合成快照 | `{format:'osr-synthetic-snapshot', version:1, state}`；`state` 依次为 `scenario, tick, tickRateHz, seed, rngState, nextEntityId, mover{id, position{x,y,z}}, marker`，`marker` 为 `null` 或 `{id, position{x,y,z}}` | Core | 输出深冻结纯数据；作为恢复输入时按上方规则严格校验 |
| 规范文本 | 按上一行字段顺序生成的紧凑 JSON，ASCII，`-0` 写作 `0` | Core | 可交给调用者保存；`JSON.parse` 的结果可被恢复接受 |
| 状态哈希 | 16 位小写十六进制字符串，即规范文本的 FNV-1a 64 位值 | Core | 只用于同版本、同运行时的一致性比对，不用于身份认证或防篡改 |
| 输入记录 | `{format:'osr-synthetic-replay', version:1, config:{seed, tickRateHz}, checkpointInterval, ticks}`；`tickRateHz` 必填（生效值），`checkpointInterval` 为正安全整数，`ticks` 为 P1-02 `TickInput` 数组，按 step 顺序排列，只含成功执行的 tick | Core 录制会话产出 | replay 前严格校验；JSON 往返后 replay 结果不变 |
| Replay 结果 | `{events, checkpoints}`：`events` 为全部 `DomainEvent`，按 tick 和 `commandIndex` 排序；`checkpoints` 为 `{tick, hash}` 数组，tick 严格递增，包含 0、间隔的倍数与最终 tick；最后一个检查点的 tick 即最终 tick，结果不另存最终 tick 或间隔 | Core 录制或 replay 产出 | 比对前按“结果比对”的规则校验结构；纯数据，可 JSON 往返 |
| 比对结果 | `{match:true}`，或 `{match:false, tick, kind:'events' 或 'checkpoint'}` | Core | 纯数据；差异不是异常 |
| 录制会话 | 行为与 `SyntheticScene` 相同，另可导出当前记录与结果 | Core | 独占内部场景，外部只能通过会话推进；不暴露可变记录 |

### 持久化与兼容

本任务不使用 IndexedDB、localStorage 或文件读写；保存规范文本或记录是调用者的事，不在本任务范围内。

- 快照与输入记录各自从版本 1 开始。版本或格式标识不匹配时抛 `CoreInputError`，不迁移、不猜测。
- 以后改变快照字段、记录字段或规范文本规则时，必须提升对应版本号，并同步更新已知答案与特征锁定测试。
- Replay 结果没有独立版本，跟随记录版本和同一代码版本的 `DomainEvent` 类型。
- 记录不承诺跨代码版本重放。行为改变后旧记录可能报告差异；这是如实的差异报告，不是数据损坏。

## 技术决定

1. **快照覆盖整个状态检查副本。** 快照包含 `SyntheticSceneState` 的全部字段（含不影响后续逻辑的 `seed`），外加格式与版本，使"完整权威状态"只有一个定义；哈希覆盖整个快照，tick 0 检查点同时检验种子与频率。
2. **规范 JSON 文本 + FNV-1a 64。** Core 类型环境没有 `TextEncoder` 和 `crypto`，Web Crypto 是异步的；合成状态很小，校验目的只是一致性，不是安全。64 位比 32 位更不易碰撞，文本便于调试，算法有公开测试向量，可以用纯 TS 实现且不新增依赖。ECMAScript 允许不同引擎在少数情况下对同一 double 输出不同的末位数字，这也是不承诺跨运行时一致的原因之一（[ECMA-262 2023 Number::toString](https://tc39.es/ecma262/2023/multipage/ecmascript-data-types-and-values.html#sec-numeric-types-number-tostring)）。原为代理提出，用户于 2026-10-02 确认。
3. **包含严格恢复，replay 只从创建配置开始。** 恢复让往返测试能证明快照完整，能逐字段构造仅差一项的状态以检验哈希敏感性，并补上 P1-02 技术决定 7 延后的边界测试。中途快照 replay 在 P1 中没有消费者，不纳入。恢复只校验结构与不变量，不检查历史可达性。原为代理推荐方案，用户于 2026-10-02 确认。
4. **只记录成功的 step。** 这沿用 P1-02 技术决定 3："非法调用抛错、不改变状态，等价于没有调用"，因此记录与原运行实际执行的 tick 一一对应。会话独占场景，防止绕过会话推进导致记录不完整。
5. **检查点间隔由记录指定。** 按总计划"周期性状态哈希"的要求，间隔是记录参数而不是固定常量，并始终包含 tick 0 与最终 tick；测试同时使用间隔 1 和更大间隔。本任务不规定默认间隔，由录制方（P1-04/P1-10）选择。
6. **差异作为数据返回，非法数据抛错。** 沿用 P1-02 的分层：合法但不一致的结果是校验结论；结构或版本错误是契约错误，用 `CoreInputError` 指出位置。
7. **已知答案与特征锁定。**
   - 哈希实现须符合公开 FNV-1a 64 测试向量。
   - 规范文本须与测试中手写的字面量一致，至少覆盖无标记和有标记两个状态。
   - 一段固定合成记录的检查点哈希在测试中固定为字面量，作为回归锁。它只能发现行为或编码的意外改变，不能证明正确性；有意的改变须在同一改动中更新这些值并说明原因。

   原为代理提出，用户于 2026-10-02 确认。
8. **格式版本化，不迁移。** 见上方"持久化与兼容"；P1 没有需要兼容的旧数据。
9. **只报告可观察差异，不比较输入记录。** 保留总计划规定的“事件流 + 周期状态哈希”，报告最早的可观察差异，并写明周期采样的检测边界；结果比对中不加入逐 tick 输入比较或输入差异类别。理由：判断输入是否相同只需比较记录数据，不需要 Core；输入差异如果没有改变任何事件或状态，replay 结果本来就一致。需要精确到 tick 时使用间隔 1。审阅中由代理提出（原 R-01），用户于 2026-10-02 确认。
10. **结果保持 `{events, checkpoints}` 形状并严格校验。** 不新增最终 tick 或间隔字段，最后一个检查点的 tick 即最终 tick。比对器只校验结构与不变量，不推断检查点周期，也不重演事件历史；检查点是否齐全由重新 replay 输入记录来保证，避免同一事实在结果中冗余存放、互相矛盾。审阅中由代理提出（原 R-02），用户于 2026-10-02 确认。

## 验证策略

- **单元/契约：** 计划新增 `src/core/` 同目录 `*.test.ts`，使用现有 Node Vitest。直接断言快照、文本、哈希、恢复、记录、replay 和比对结果，不 mock Event Bus，不读取原版数据。
- **Replay/一致性：** 用固定 seed（含 0 与 uint32 上界）、显式 `tickRateHz` 和合成逐 tick 输入录制，再在新实例上 replay，比较事件全文和检查点哈希。用逐字段恢复、篡改记录或结果作负向对照，不只拿同一对象自比；要求精确定位首次偏差的负向用例使用间隔 1，并保留一个间隔大于 1 的采样边界反例。特征锁定值只作回归锁，不是正确性证明。
- **数值：** 事件、哈希、tick、ID 和 RNG 状态精确比较。恢复后的继续运行与来源逐位一致，因为它们是同一运行时上相同 double 的相同运算，不使用浮点容差。
- **失败路径：** 恢复、记录和结果的每类非法输入都断言 `CoreInputError` 与 `path`；录制中的非法调用不进入记录；上限守卫通过恢复做自动边界测试。
- **浏览器验证：** 不适用。本任务没有浏览器接线；浏览器中复用记录由 P1-10 负责，本任务不预先承诺浏览器与 Node 的结果一致。
- **实机/原版对照：** 不适用；全部为自建合成行为和数据。
- **工程检查：** 先跑目标 Core 测试，再跑 `pnpm check`；保留既有工程边界回归、解析器测试和 P1-02 测试。

## 风险与恢复

风险等级：**中**。P1-04 的录制、P1-10 的记录复用和以后的调试都会依赖这些契约，但本任务不涉及玩家数据迁移或原版玩法。

- **假一致：** replay 必须使用新实例，并有篡改记录/结果的负向测试；比对事件全文，不只比较哈希。周期采样的检测边界写入契约，并有反例测试；需要精确定位时使用间隔 1，不把间隔大于 1 时的“一致”解读为每个 tick 都一致。
- **快照漏字段：** 用往返继续运行和逐字段哈希敏感性证明完整性。以后 Core 新增权威状态时，必须同步扩展快照、恢复和这些测试，并提升版本。
- **恢复引入不可达状态：** 校验保证 ID 不复用、数值有限和既定范围；历史可达性明确不检查，不把恢复当作防篡改机制。
- **编码锁死或漂移：** 规范字段顺序由 spec 固定，并有版本号；特征锁定值的更新必须在同一改动中说明原因。不承诺跨引擎一致，避免把 Node 结果当作浏览器结果。
- **未来性能：** 大世界逐 tick 哈希可能昂贵，因此间隔由录制方选择；本任务不设性能阈值。
- **恢复：** 本任务不接入应用或用户存储，新增代码和测试可以独立撤销；P1-02 内部若因恢复入口而调整，须保持既有测试全部通过。
