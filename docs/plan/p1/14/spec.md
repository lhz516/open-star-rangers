# P1-14：P1 退出评审与交接 — Spec

## 问题与目标

P1-01 至 P1-10、P1-12 已交付合成运行闭环、本地浏览器回归和合规检查，各自 Goal 已完成；但任务完成不等于阶段退出。目前尚无 P1 阶段评审，缺少把最终候选版本、全部退出条件、历史证据适用性及后续责任串起来的权威结论。

本任务是**本地验收评审、必要缺陷修复与文档交接**：核对现有交付，在本 Goal 内闭环修复已定位的 P1 验收缺陷，在最终候选版本上验证整条本地检查链，形成可追溯的退出判定，并明确 P0 收尾、P2 资源、P3 玩法和 P5 发布的边界。不重新实现已有功能，不把合成骨架或本地通过解释为原版保真、公开许可确认或云部署完成。

阶段范围依据[总计划 §12](../../master-plan.md#12-开发阶段与验收条件)，责任覆盖见[阶段索引](../tasks.md#6-阶段验收覆盖)。本地阶段分配和进度分工分别遵循 [ADR-0012](../../../decisions/ADR-0012-local-p1-defer-ci-deployment.md)、[ADR-0014](../../../decisions/ADR-0014-status-summary-only.md)。

## 范围

### 包含

- S-01：核验全部前置任务的批准、Goal 完成状态及真实证据，记录候选版本和工作树/索引差异；将总计划的 P1 退出条件及阶段索引的交付责任完整映射到证据。
- S-02：复用已有命令和测试，在最终候选源码上实际运行工程（含 P1-01 基线中独立的 Python 合成测试）、完整浏览器回归和聚合合规检查；已定位、导致既定 P1 验收失败的代码/测试接线/资源清理缺陷，可在本 Goal 中新增独立聚焦修复项并补针对性回归、重验闭环，不新增 runner 或降低原判据。
- S-03：逐类判断历史证据能否复用，记录来源版本、相关实现/配置差异与适用理由；只对失效的必需证据补验，不重复旧手工压力、DPR、故障或 HMR 全矩阵。
- S-04：核对当前构建、原版隔离、依赖与实际分发声明证据，保留完整文件哈希和许可检查的能力边界；人工来源/文件/产物审阅不能由自动通过替代。
- S-05：新建 P1 阶段评审记录，逐项作出退出判定，记录问题、恢复条件、残余事项和负责人确认状态；历史已冻结评审不改写。
- S-06：在评审中交接可复用设施、必须替换的合成规则/表现、后续资源与玩法落点、原版未知项及发布责任，不为 P2/P3/P5 分配新任务或生成契约。
- S-07：对齐直接相关的工程/使用说明和阶段摘要，完成文档、最终扫描范围及自有测试资源核验；执行状态仍只由本任务 Goal 维护。

### 不包含

- 新玩法、资源导入/转换、Worker、IndexedDB、正式存档、音视频、完整键位、Gamepad、Enhanced 或通用引擎抽象。
- 重新实施 P1-01 至 P1-10、P1-12，重新盘点原版文件或制作另一份原版事实/许可包清单；不为评审新增生产观测或世界写入接口。
- 与 P1 验收无关的顺带修复或功能扩展，以及改变已批准行为、数据格式/兼容边界或冻结架构的补丁。此类变化须另行修订契约，必要时走 ADR；本 Goal 只修复既定契约内的缺陷，不能用修复或评审降低要求。
- P0 研究收尾、原版行为对照、发布级设备/浏览器/性能/系统快捷键矩阵、法律认证或严格 clean-room 证明。
- CI、检查保护、push、Azure/SWA、部署、公开仓库或发布；未建设 CI/部署不是 P1 本地退出阻塞，也不视为已经完成。
- 自动批准阶段评审、切换当前阶段或调用下一规划 skill；本 Spec 的批准不等于未来评审结论的确认。

## 行为与边界

| 场景或状态转换 | 预期结果 | 拒绝或失败时的反馈 |
|---|---|---|
| 前置 Goal 完成且证据可追溯 | 建立最终候选版本及条件/责任/证据映射 | tracker、批准或链接不一致时明确受影响项；修复前不套用“全部完成” |
| 最终本地工程、浏览器、合规链运行 | 分别记录命令、环境、退出码、实际断言与报告身份 | 失败或缺能力均保留具体原因，不能用历史成功、列表发现或 skip 替代 |
| 历史证据相关实现未变或变化不影响其断言 | 标为复用并说明版本和适用性 | 不能只写“生产未变”；P1-12 的 App 文字、构建插件/依赖变化需按影响核对 |
| HMR、窗口焦点、DPR 等必需历史证据失效 | 按原契约有界补验，并记录实际 browser/环境与清理 | 无法取得必需证据标为未验证，不能伪造事件/getter、用 Node 模拟或近似代理通过 |
| 已复现并定位既定 P1 验收缺陷 | 记录原责任与影响，在本 Goal 新增独立修复项，修复后以原判据和针对性回归重验 | 原因不明不得猜测修复；需要改变行为/格式/架构或扩到后续功能时停在契约关卡，不以删断言/改阈值通过 |
| 本地必需项未通过或未验证 | 退出结论为不通过，列原责任、受影响条件及恢复路径 | 不以有条件通过、移交 P2/P5 或降低阈值掩盖 P1 缺口 |
| 全部 P1 必需项通过，尚有后续阶段事项 | 提出“通过”结论；后续阶段事项列为遗留/交接，不使结论变为有条件通过 | P1 必需项不能用有条件通过替代；残余事项不豁免其负责阶段验收，也不代表法律/首次公开确认 |
| 已完成评审但负责人未明确确认 | 新评审保持 draft、结论待确认；STATUS 只把“下一步”指向待确认评审，阶段总览状态与评审记录列不变，当前阶段仍为 P1 | 用户让 agent 采用推荐方案、批准本 Spec/Goal 或执行 Goal，均不自动成为未来结论确认 |
| 负责人明确确认评审结论 | 记录实际日期/范围，评审 accepted 后冻结；STATUS 阶段总览状态、评审记录列与实际结论一致 | 只有全部必需项通过且结论获确认才可标记 P1 通过；切换当前阶段仍需另行授权 |
| 后续候选版本或判据发生变化 | 重新核对受影响证据；冻结后的变化写新评审记录 | 不回写旧版本通过、不重用过期产物；冻结决定冲突须另走 ADR |

评审任务交付与阶段通过是两件事：取得真实失败结果并完成问题/交接记录，可以形成“不通过”的完整评审；但尚未取得本契约要求的评审证据时，相关 Goal 行仍须 blocked，不能把漏验当作已完成。本任务的完成以证据完整、结论与逐项结果一致的 draft 评审及相关文档对齐为准，不等待负责人确认；确认是 Goal 之外的阶段审批关卡，由负责人之后明确答复时再记录并冻结，不伪装成未决的实现选择，也不使 Goal 行 blocked。

## 数据模型与契约

**无游戏、输入、内容或存储模型契约变化，无新增 TypeScript 评审 schema。** 聚焦修复可纠正既有契约的实现，但不得改变字段、单位、格式版本或存储兼容要求；评审使用已有数据，只将必要身份、结论和证据引用写入 Markdown。

| 数据 | 类型、单位与约束 | 权威所有者 | 输入/输出边界 |
|---|---|---|---|
| `TickInput`、`DomainEvent`、projection、Render State | 现有纯数据；tick 为模拟步，频率显式；合成单位不解释为原版物理量 | [合成 Core](../../../../src/core/synthetic/synthetic-scene.ts) | 沿用 Node/浏览器现有测试，不向运行世界写参考数据 |
| `SyntheticReplayRecord`、`SyntheticReplayResult` | 既有 `osr-synthetic-replay`/1；配置、成功 tick 输入、events、checkpoints | [replay 模块](../../../../src/core/synthetic/synthetic-replay.ts) | 使用既有生产校验/比较器，不修改格式或启用 UI 录制 |
| `SessionStatus`、`SessionFrame`、UI 指令结果 | 既有 run/command 身份、控制状态和结果分类 | [Session](../../../../src/app/session/synthetic-session.ts)、[UI store](../../../../src/ui/game/synthetic-game-store.ts) | 只读观察控制/反馈，不以乐观状态代替 Core 结果 |
| 合规报告与 inventory | 既有 `osr-local-compliance`/1 与 `osr-distribution-inventory`/1；counts、findings、输入/产物指纹及 platform/arch 覆盖 | [报告](../../../../tools/compliance/report.ts)、[分发工具](../../../../tools/compliance/distribution.ts) | 聚合成功必须七个必需范围 completed、零 findings、exit 0；inventory 自身不是通过报告或签名 |
| 评审身份与逐项结果（文档新增） | 评审日期、候选 Git revision/差异、配置/环境；每项含判据来源、责任、证据链接、通过/未通过/未验证及理由 | 新 P1 评审 | 必须区分当前重跑、有效历史复用和缺失证据；不维护另一份 subtask tracker |
| 问题/残余/交接（文档新增） | 事项、是否阻塞 P1、影响、权威记录/置信度引用、负责阶段/任务、解除或后续验收条件 | 新 P1 评审引用现有权威记录 | 不复制原版事实、不发明后续任务编号或负责人的确认 |
| 总结论与确认（文档新增） | 通过/有条件通过/不通过；待确认或实际负责人确认日期/范围 | 新 P1 评审 | 与逐项结果一致；批准后冻结，与阶段切换授权分离 |

### 持久化与兼容

不访问或改变玩家 IndexedDB、localStorage、存档、导入缓存及个人浏览器 profile。检查报告、合成 trace/截图沿用 ignored 输出目录，不新增跟踪机读报告；评审与本任务完成证据只保留安全元数据及引用。

既有生成声明/inventory 由构建工具维护，输入变化或失败后按[本地合规用法](../../../guides/tools.md#本地合规)恢复，不能手改或沿用过期文件。没有存档迁移；未冻结的候选评审可修正，已确认评审只能由新记录承接变化。

## 技术决定

1. **判据不新增、不豁免：** 总计划定义退出条件，阶段索引提供责任覆盖，Goal/subtask 提供任务状态和证据，新的阶段评审独占最终判定；遵循 ADR-0014，不在 STATUS/tasks 建退出勾选表。
2. **最终候选上的完整本地链：** 实际运行 `pnpm check`、`python3 -B -m unittest discover -s tools/ghidra -p 'test_*.py'`、`pnpm test:e2e`、`pnpm --silent check:compliance`。Python 测试沿 [P1-01 AC-06](../01/spec.md#验收标准) 只用临时合成 XML，不调用 Ghidra 或读取原版数据，仍独立于 `pnpm check`。现有命令各自包含构建，按现有语义使用，不增加编排代码或为避重复构建改变脚本。完整回归含开发/生产/headed 及 P1-12 声明用例，不用旧 18 项加相关 3 项的历史结果代替。发生修复后按受影响面重验，最终证据必须对应修复后的候选；无变化的检查不机械重复。
3. **最新仓库范围独立核对：** 最终评审/证据文档形成后，使用 `pnpm check:original` 核验实际工作树、索引、未忽略未跟踪和完整 dist，记录被扫描的版本/差异。若只改文档且构建输入身份未变，工程/E2E 与许可证据可复用；输入/依赖/产物变化则重建并重跑受影响检查，不机械重跑所有历史实验。
4. **旧证据按影响复用：** 以 [P1-10 适用性映射](../10/subtasks/07-evidence-docs-alignment.md#新增自动覆盖历史证据适用性)为入口，核对 P1-12 至最终候选的相关变化。HMR/原生窗口焦点优先采用 [P1-09 实测](../09/subtasks/05-browser-input-evidence.md#完成证据)，DPR/上下文/压力及稀有故障沿原证据层次；不把 Node 故障测试改标为浏览器实测。
5. **保持原断言与能力边界：** 浏览器数量按当前配置发现，结果按真实执行判定，不新增任意阈值、不删除/skip/重试掩盖失败。任何失败先保留原始报告；只有查明的环境原因（如端口被其他进程占用、自有残留进程）在不改代码、配置和断言的前提下可整条命令重跑，评审同时记录失败与重跑。原因不明或偶发的失败不得以重跑通过抵消，须定位原责任和根因；查明缺陷后的修复重验按技术决定9另行记录，不属于未改版本的盲重跑。原生 hidden、可信输入、真实合成像素、资源身份及 GPU 判据沿 [P1-10 Spec](../10/spec.md#验收标准)。扩展缺失按原契约明确上下文丢失未验证，不冒称成功，也不擅自增加原契约未要求的设备门槛。
6. **原版/许可仍保守：** 遵循 [P1-12 Spec](../12/spec.md)、[ADR-0008](../../../decisions/ADR-0008-mit-and-dependency-licenses.md)及[总计划 §9.2](../../master-plan.md#92-版本与配置)。使用实际依赖/分发及完整许可正文，不以 dev 标签判断不分发；根 pnpm 锁是合法多文档流，不能恢复已否定的“锁不完整”前提或借评审升级工具链。
7. **明确交接而不提前设计：** 报告分别列可复用设施、合成替代项与后续待设计契约。Runtime/Session 及 synthetic 类型不预先泛型化；真实内容归 P2、正式规则归 P3，Core 纯度和单一调度/只读消费不可绕过。
8. **不预授结论批准：** 首份记录计划使用 `docs/reviews/P1-exit.md`；执行前检查路径，若已有冻结记录不覆盖，按评审命名约定追加新记录。评审默认 draft，确认前可修正；[评审索引](../../../reviews/README.md)的“写完即冻结”按 P0 先例指负责人确认之时。只有负责人明确确认具体结论才 accepted/冻结。确认通过后可以更新 P1 摘要，不自动将当前阶段切换成 P2/P3。
9. **归原责任定位，在本 Goal 修复：** 只对已复现、已定位且不改变既定 P1 契约的缺陷新增聚焦修复 subtask，列明原责任任务/受影响 AC、复现与根因、实际代码/测试文件、真实依赖和验证方法。不预建空修复项；新 ID 插入最终对齐之前，最终项依赖全部修复项且仍不写代码。修复项不得依赖发现它的 blocked 行而形成死锁：取得复现与定位证据后即可成为待执行修复项，发现项在修复重验后再完成。代码修复须有针对性回归、`pnpm check`及受影响的浏览器/合规或 Python 检查，更新相关文档/证据，单独本地提交；旧正确证据保留，以新证据记录后续变化。仅验证/文档项仍可不单独提交。改变行为/格式/架构的需求不由本条自动批准。

## 验证策略

- **单元/契约测试：** 常规核验复用既有测试；实际缺陷修复补针对性回归。`pnpm check` 复用 [Core](../../../../src/core/synthetic/)、[Runtime](../../../../src/app/runtime/)、[Session](../../../../src/app/session/)、[UI bridge/反馈](../../../../src/ui/game/)、[输入](../../../../src/platform/input/)及[合规](../../../../tools/compliance/)的邻接测试；正/负场景沿各已批准契约，不单独再造故障矩阵。修复在本 Goal 独立项内进行，不能改成宽松断言。
- **Replay/一致性：** Node 沿 P1-03 测试配置，浏览器沿 P1-10 既有 seed 0、50 Hz、四 tick、checkpointInterval 1 记录及真实比较器；默认演示的 60 Hz/不录制配置不变。记录代码/记录身份与运行时，只证明已测版本/样本，不把 replay 事件当状态重建。
- **浏览器验证：** 使用已有安装 Chrome/兼容 Chromium、隔离的合成 context 和当前三个项目，按 [browser-testing](../../../../.agents/skills/browser-testing/SKILL.md)核验真实观测及清理。完整 runner 实际执行；修复后的相关结果重验，旧 HMR、窗口焦点和 DPR 证据按 AC-07 更新适用性，必需失效项才有界补测。不能关闭/解锁个人 profile、复用未知服务器、静默安装浏览器或用 synthetic visibility 替代 native hidden。
- **实机/原版对照：** 本任务不增加原版或发布设备验收。P1 已要求的真实后台/窗口与 HMR 证据仍须有效；P0 cycles/设备/键位、P3 保真、P5 多引擎与真实平台/性能/系统快捷键/发布验证保持后续责任，合成通过不豁免。
- **工程检查：** 执行时采用已有 `pnpm check`、独立 Python 合成测试、`pnpm test:e2e`、`pnpm --silent check:compliance`；最终文档集合再核对 `pnpm check:original` 和输入身份。正常检查不安装/升级依赖；缺依赖才按项目版本与 frozen lock 恢复。本次生成 Spec 只做文档链接/元数据/结构与差异检查，不提前运行阶段验收或构建。
- **证据位置：** 本任务 subtask 记录本轮命令、修复/回归、适用性和清理证据，Goal 管唯一执行状态，阶段评审引用证据并作退出判定；原责任任务只作来源引用，旧正确执行证据不改写，新原版事实若另行研究只归 original，本任务不创建另一份原版清单或独立测试报告阶段。代码修复项按 [execute-goal](../../../../.agents/skills/execute-goal/SKILL.md)审查及 [simplify](../../../../.agents/skills/simplify/SKILL.md)做限定范围清理。

## 风险与恢复

风险等级：**中**。常规评审无需改实现或数据迁移；必要修复涉及已有实现，错误的修复、证据复用或批准记录会造成回归与阶段误判。

- 历史成功套到新候选：记录相关源码/配置/依赖身份，区分当前重跑与有效复用；涉及构建变化时验证当前产物，而不是沿用旧 hash。
- 缺能力或失败被有条件通过掩盖：必须区分失败与未验证，并定位原责任/恢复条件，契约内缺陷在本 Goal 闭环；全部 P1 必需条件通过之前不标阶段通过。
- 合规结果被过度解释：保留 manifest 覆盖/完整文件 hash、实际分发/许可文本与人工审阅边界；本地通过不是法律、名称、秘密或首次公开确认。
- 自动改阶段/扩范围：保持 draft 评审和明确负责人关卡；CI/部署及新资源/玩法只交接，不擅自执行。
- 聚焦修复扩为重设计：先复现/定位原契约缺陷，独立修复项与针对性回归限制范围；行为、格式/存储兼容或冻结架构变化先停止并重新审批，不通过原验收目标倒推未经批准的新方案。
- 补验影响共享环境：只操作自有进程、profile、临时目录和 synthetic 数据，结束时还原 HMR 临时编辑并清理；不回滚用户改动。
- 恢复：修正未冻结的评审/证据，相关实现变动后重新验证；已冻结结论以新记录承接。代码修复独立提交，回退需明确授权并重验，不回滚用户改动；构建失败沿 P1-12 清除旧有效指标并重建，不手改声明；没有玩家存储回滚或清理。

## 未决事项

无。按用户确认的方案：复用已有交付与有效历史证据，最终候选执行完整本地链（含 P1-01 的独立 Python 合成测试）；已定位的 P1 契约内缺陷在本 Goal 按独立修复项闭环，未闭合缺口保守判定。任务以完整 draft 评审完成，评审结论确认与阶段切换分别保留明确授权；确认前 STATUS 只更新下一步；原因不明的失败不以重跑抵消。尚未执行的验收及未来负责人确认不是本 Spec 的未决选择，也不在此预写通过。
