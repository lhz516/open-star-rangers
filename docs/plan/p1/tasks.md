# P1：工程与运行骨架 — 阶段计划与任务

本文件把 P1 拆成可分别执行 spec → review → goal → execute 的任务，不预先生成任务契约或实现代码。阶段范围与退出条件以[总计划 §12](../master-plan.md#12-开发阶段与验收条件)为准；本文件只做责任覆盖，最终退出判定由 P1 阶段评审记录。

## 1. 阶段目标与边界

P1 要证明的是**工程架构可以在本地端到端运行和验证**，不是证明原版玩法已经复刻，也不是证明远端发布已经完成：

- 同一份自建合成场景可以在 Node 中运行 Core，也可以在浏览器中通过 Runtime、Three.js 和 React 运行。
- 游戏意图只能经输入/命令进入 Core；状态经投影读取，一次性反馈经 Runtime 分发；暂停、继续与退出不依赖 Core 继续 step。
- 固定输入与种子能够重放；反复开始、暂停、重启、退出和热更新不会增加游戏循环或遗留会话资源。
- 本地工程检查、浏览器测试、仓库/构建产物原版哈希扫描及依赖许可检查可重复运行，不需要 GitHub/Azure 凭据或云环境。

按用户确认的 [ADR-0012](../../decisions/ADR-0012-local-p1-defer-ci-deployment.md)，CI 与 SWA 部署统一归 P5，不再是 P1 的退出条件或阻塞项；本阶段可以凭完整的本地证据通过评审。

各任务共同遵循[总计划 §4–5](../master-plan.md#4-总体架构)、[工程约定](../../engineering/README.md)和[任务工作流](../../engineering/agent-workflow.md)。合成行为必须明确标记；不得把演示用移动、命令或数值解释为原版规则。

P1-06 前按 [ADR-0015](../../decisions/ADR-0015-source-module-structure.md) 独立整理源码目录，不改变已批准的行为、契约或任务依赖。后续 spec/goal 使用[源码结构指南](../../engineering/source-structure.md)中的当前路径与消费者落点；旧计划路径和历史验收命令的对应关系及本次验证见[迁移记录](../../engineering/source-structure.md#p1-06-前迁移记录)，不作为新玩法或消费者已完成的证据。

### 本阶段不做

- CCD/IMG、ISO9660、Worker 导入、真实模型/贴图/HUD/音效转换、IndexedDB 资源缓存：属于 P2；已有研究解析器只作为工程与测试基线，不在 P1 扩展资源管线。
- 原版飞行与武器数值、AI、目标系统、战略地图、Warp、基地交互和任务胜负闭环：属于 P3。
- 完整战役、通讯/视频/音乐、原版界面和正式存档：属于 P4；音乐/视频 spike 不作为 P1 门槛。
- 全套导入格式、缓存管理、PWA/离线/升级、发布级性能与真实设备兼容矩阵：属于 P5。
- GitHub Actions、CI 合规门禁、仓库检查保护和 SWA 预览/正式部署：由 [P5](../p5/tasks.md)承接。P1 不生成、运行或验证这些交付；其外部前提也不阻塞本地任务。
- 完整 F1–F9 视角、重映射设置、全屏/Keyboard Lock 配套及跨系统快捷键验收不在本阶段提前铺开；已实现的少量演示绑定仍须遵守默认键位政策，不以新绑定替换原版默认值。
- 不新增 Gamepad、鼠标飞行、ECS、通用引擎、模拟 Worker、账户或服务端。鼠标用于 React 界面；原版输入事实见[键位记录](../../original/input/key-map.md)。

P0 的剩余研究与实机工作继续在[未知项登记表](../../original/unknowns.md)和相关研究文档中跟踪，不作为合成 Core/Runtime 开发的笼统前置条件。遇到具体未知规则时停止把它纳入合成演示，而不是猜测或扩大 P1。

- Vite/React/TypeScript strict、Node/pnpm 锁定、模块边界与确定性 lint、Vitest 和合成格式样本已纳入仓库；证据入口见 [P1-01 最终对齐](./01/subtasks/06-final-alignment.md#完成证据)与[工程约定](../../engineering/README.md)。
- [App](../../../src/app/App.tsx) 由 P1-06 接入合成开发面板（React 指令与 Core 反馈），由 P1-07 接入 Three.js 合成画面与渲染诊断，[应用入口](../../../src/main.tsx) 已启用 StrictMode。目前仍没有正式菜单或可玩的原版内容。
- [package.json](../../../package.json) 已由 P1-06 加入 Zustand、由 P1-07 加入 Three.js，尚未包含 Playwright。Core、Runtime 与会话已由 P1-02 至 P1-05 交付，UI projection 桥接与 React 指令闭环已由 P1-06 交付，合成渲染器已由 P1-07 交付；尚无 CI、SWA 配置和 E2E 测试入口。

P1-01 以既有实现为输入进行复核和证据归档，不重新初始化项目，也不为了凑任务补写虚假的历史执行记录。本文件不复制任务完成状态；每个 goal 的状态须以其实际验收为准。

## 4. 任务范围与责任

### P1-01 工程骨架基线复核

- 复核现有 Vite/React/TS 配置、Node/pnpm 版本来源、锁文件、纯模块类型环境、模块边界与确定性 lint。
- 验证测试发现范围、合成样本与研究工具隔离，以及现有 `pnpm check` 和独立 Python 检查入口；负向边界检查不依赖原版数据。
- 归档真实基线证据。若发现影响 P1 的必要缺口，在本任务 spec 中明确；不顺手升级工具链或重构解析器。
- 后续引入 Zustand、Three.js、Playwright 的依赖和配置由 P1-06、P1-07、P1-10 各自负责，不提前安装一套未使用的框架。

### P1-02 最小纯 Core 与合成场景契约

- 定义演示真正需要的权威状态、实体 ID、可配置 tick 频率、带种子的随机源，以及连续输入、离散命令和 `DomainEvent` 契约。
- 用最小合成行为证明 step 会改变状态、接受或拒绝命令并返回带 tick 的纯数据事件；可在 Node 中直接运行和断言。
- 同时交付纯 UI projection 和 Render State 提取契约，供两条消费链复用；不得暴露可修改的世界引用或在 Core 内引入 Event Bus。
- 统一合成初始状态与场景入口，后续 UI/渲染/测试不能各自维护另一套演示世界。
- 只定义当前切片需要的数据形状，不提前建完整舰船、武器、任务或存档模型。具体演示动作和数值在 spec 中确认，不冒充原版规则。

### P1-03 快照、状态哈希与输入 replay

- 显式序列化影响后续逻辑的权威状态及 RNG 状态，形成可重复的状态校验；具体编码和哈希方案由 spec 确定。
- 记录初始条件、种子、每 tick 连续输入与离散命令，以相同版本/运行时重放并比对事件流及周期性状态哈希。
- 包含能发现真实输入或状态偏差的负向验证，不只拿同一个对象与自己比较。
- 不消费 Event Bus 来重建世界，不承诺跨浏览器逐位一致，不实现 IndexedDB 存档或玩家 replay 管理界面。

### P1-04 Runtime 调度、命令与事件分发

- Runtime 统一持有固定步长调度、补跑上限、命令队列及会话级类型化 Event Bus；Core 和渲染器不另开循环。
- 明确连续输入采样、离散命令的消费边界、零/单/多 tick 帧及长帧时间处理；限流策略和具体上限在 spec 中确定。
- 本帧所有模拟结束后按 tick 顺序分发事件；订阅者产生的新命令进入后续 tick，不能在更新中途修改权威世界。
- 每 tick 提取并保存上一份/当前份独立 Render State，提供插值所需的时间信息；不能把可变世界引用当作旧快照。
- 用可控时钟和合成消费者验证调度与契约，不依赖 React 或真实 GPU；已批准 spec 的可选录制接线复用 P1-03，因此任务整体也依赖 P1-03。

### P1-05 会话与浏览器生命周期

- 建立 Runtime 控制通道与会话状态转换，覆盖开始、暂停、继续、重启、退出和幂等销毁；暂停后仍能处理继续/退出。
- 处理页面隐藏、恢复及时间基准重置，明确暂停期间的输入/队列行为，不追补整个后台或暂停时长。
- 规定会话资源的注册/清理责任，防止旧会话回调继续更新新会话；失败必须可观察，不能静默启动另一条循环。
- 用合成订阅与消费者验证循环和会话清理。真实 UI 订阅、键盘监听和 GPU 资源的释放仍分别由 P1-06、P1-09、P1-07 实现，P1-10 联合核验。
- 不为了未来音视频或 Worker 加入空实现；相关资源实际接入时必须遵循同一会话生命周期。

### P1-06 UI projection 与 React 指令闭环

- 引入 Zustand vanilla store 与桥接层：读取 Core 的纯投影，按既定分层频率发布，重要状态变化及时反馈；React 按 selector 订阅。
- React 只提交游戏命令或 Runtime 控制；至少证明一个接受路径和一个拒绝路径，拒绝时不显示成功状态。
- 持续事实从 projection 得到，一次性反馈消费事件；不能靠事件累积重建 UI，也不能把整个世界塞入 store。
- 交付可验证的开发演示控件与状态反馈，并释放桥接/订阅；不在这里实现完整菜单、设置或用 React 承载逐帧飞行 HUD。

### P1-07 Three.js 合成渲染

- 引入 Three.js，以合成几何/自有素材和实体 ID 建立模型映射，只读取 P1-04 的 Render State 并插值，不持有另一套游戏事实。
- 实际显示由 Core 驱动的场景变化，处理实体新增/移除、暂停与重启时的渲染状态；不能只证明 Canvas 存在。
- 按既定 Classic 默认比例实现尺寸与设备像素比处理、黑边和资源释放；WebGL 不可用或初始化失败时明确反馈。
- 固定默认视野，不提前实现全部相机、驾驶舱/HUD 资源、原版像素模式、宽屏开关或 Enhanced 效果；不另起 rAF 循环或引入 React Three Fiber。

### P1-08 菜单与导入占位

- 装配菜单、合成演示入口、暂停/继续/重启/返回菜单，并呈现 Runtime/渲染失败与恢复入口。
- 明确区分“启动合成演示”“导入尚未实现”“存在已验证资源”等不同事实；P1 不能产生假的导入成功或可玩原版标记。
- 导入入口只承担原型说明和必要交互；不接入真实 File 解析、Worker、上传或本地资源缓存。
- 验证常规 React 键盘/鼠标与焦点流转。合成演示无需先导入数据，真实游戏也不能被这条演示入口绕过资源要求。

### P1-09 最小键盘适配与输入隔离

- 将少量演示绑定经平台适配层转换为游戏动作；连续操纵用模拟轴，离散意图入命令队列，P 等暂停控制直接走 Runtime。
- 使用 `KeyboardEvent.code`，明确按住、抬起、重复事件、活动界面与焦点规则；菜单/表单不拦截游戏键，失焦/隐藏/会话结束清空瞬时输入。
- 演示若涉及开火意图，遵守既定 Alt/Option 默认政策；未确认的方向/横滚键不写成原版事实，也不增加鼠标飞行。
- 若演示使用 Pointer Lock，则验证退出后的清键；不为了“以后可能需要”强制引入锁定流程。
- 只交付最小适配与页面层处理，不宣称系统快捷键已被拦截。完整键位和实机冲突验证仍回到[键位表](../../original/input/key-map.md)与 P0/P5。

### P1-10 浏览器集成与回归冒烟

- 建立本地 Playwright 配置、类型/lint/脚本入口与可重复运行的方法；本任务 spec 明确必须运行的浏览器引擎和环境，不把最终发布设备矩阵提前作为 P1 门槛。
- 联合验证菜单 → 合成场景、React/键盘指令 → Core → UI/渲染、命令拒绝、暂停/继续/重启/退出、失焦/后台恢复和尺寸变化。
- 验证 StrictMode 挂载/清理与重复会话；HMR 在开发环境另做明确验证，不能用生产构建测试代替。
- 对循环、监听、订阅与 GPU 资源采用可观察证据；重复次数、判据和容许波动由 spec 确定，不把“页面没崩”当作无泄漏。
- 复用 P1-03 的输入记录与初始条件；按 [browser-testing](../../../.agents/skills/browser-testing/SKILL.md) 做真实浏览器观察和清理。自动化只用合成内容，不覆盖原版保真结论。
- 这是跨模块测试与必要的测试接入，不是把所有单元测试推迟到这里，也不以测试名义悄悄补新玩法；发现缺口归回责任任务。

### P1-12 本地原版隔离与许可检查

- 提供可重复运行的本地检查入口；从[原版 manifest](../../original/manifest.md)读取哈希黑名单，扫描受版本控制的仓库文件与本地构建产物，不能扫描或依赖开发者的 `local/`。
- 用自建样本证明黑名单命中会失败，包括改名的相同文件；黑名单缺失、格式损坏或意外为空时明确失败。全文件哈希不能证明片段、转换资源或截图没有泄露，保留文件/产物审查。
- 按[许可政策](../master-plan.md#92-版本与配置)识别直接/传递依赖与实际分发内容；开发依赖标签不能代替分发范围判定，未知或不合规许可不能静默通过。
- 在本地构建中生成第三方许可声明及必要的项目/原版权利边界说明，不要求发布网站；首次公开所需的负责人确认仍按总计划执行，不擅自视为已完成。
- 两类检查覆盖可证明失败的合成路径；后续新增依赖和资产持续重跑，不只检查一次初始壳。P5 可复用这些命令接入 CI，不在本任务建立远端门禁。

### P1-14 P1 退出评审与交接

- 汇总下方覆盖表、各任务 goal/subtask 证据、本地工程/浏览器/合规结果，逐项评审调整后的 P1 退出条件，不仅统计已完成任务数量。
- 在 `docs/reviews/` 写新的 P1 评审，记录通过/未通过、版本、证据和遗留事项；评审结论确认后更新 STATUS 的阶段摘要，不自动批准阶段切换。
- 明确哪些是合成骨架、哪些可以被 P2 真实资源替换、哪些规则仍需 P0/P3 研究；不以 P1 通过宣称 P0 收尾或原版玩法通过。
- 本任务是评审与文档交接，不实现新功能。必需的本地缺口归回原责任任务/其 goal 的修复 subtask，并重跑受影响验收；CI/部署未建设不阻止本地 P1 通过，但必须明确交接到 P5。

## 5. 实施顺序

主线不是编号从小到大串行：

1. **确认起点：** P1-01；随后从 P1-02 明确所有消费者共同使用的最小契约。
2. **尽早建立本地合规检查：** P1-01 → P1-12，可与 Core/Runtime 主线分别推进。
3. **形成两条基础证据链：** P1-02 → P1-03 证明 replay；P1-02、P1-03 → P1-04 → P1-05 证明调度与会话，P1-04 的录制接线复用 P1-03。
4. **分别接入消费者：** P1-05 之后的 P1-06、P1-07、P1-09 相互没有整项前置依赖；每项自带其测试与释放责任。再由 P1-08 形成可从菜单使用的演示。
5. **联合验证与交付：** P1-03、P1-08、P1-09 → P1-10；全部本地交付 → P1-14。

“可以分别推进”不要求并发 agent 修改同一工作树。每个 goal 仍按自己的真实依赖执行；跨任务依赖须写入其前提并链接已验证证据，不靠会话记忆。不为本阶段的执行索取远端凭据、提前建设 CI 或部署。

这是覆盖映射，不是另一份完成清单。进行中的状态和证据分别见各任务 goal/subtask；最终是否通过由 P1 阶段评审逐项判定。

## 7. 后续规划入口

每个任务先澄清自己的 spec，再生成 goal 与 subtasks，路径为 `docs/plan/p1/<任务号>/`。不要一次性为这 12 项猜测具体字段、数值、重复测试次数或浏览器矩阵。

建议下一项为 `/generate-spec p1/01 工程骨架基线复核`；复核后进入 `/generate-spec p1/02 最小纯 Core 与合成场景契约`。已有交付可验证归档，但没有已批准的契约和真实证据，不自动把新 goal 标记为 completed。
