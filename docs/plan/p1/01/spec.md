# P1-01：工程骨架基线复核 — Spec

## 问题与目标

项目已提交 Vite/React/TypeScript 工程、纯模块边界、确定性 lint 与合成解析器测试，但边界规则的负向验证目前只在[工程约定](../../../engineering/README.md)中记录为临时实验，尚无持久回归用例。配置存在不等于每条规则真实生效，历史测试记录也不能代替本次版本的检查结果。

本任务以已有工程为起点，交付可重复的本地基线检查和边界回归证据，让后续 Core/Runtime 开发能够复用现有配置，而不是重新搭建项目。成功结果是：正常代码仍能检查、测试、构建和启动；违规样本被目标规则拒绝；检查失效时明确失败；验证不依赖原版数据、远端 CI 或云凭据。

阶段范围依据[总计划](../../master-plan.md#12-开发阶段与验收条件)，任务导航见[阶段索引](../tasks.md#p1-01-工程骨架基线复核)。阶段级历史进度仍以 [STATUS](../../../STATUS.md#工程骨架) 为准，不在本任务伪造历史执行记录。

## 范围

### 包含

- **S-01 工具链与配置基线：** 核对版本声明、锁文件、实际运行工具、TypeScript 项目划分、lint/Vitest 发现范围，以及现有检查命令的有效覆盖。
- **S-02 持久边界回归：** 增加使用现有依赖的本地正向/负向自动检查，验证纯模块类型环境、依赖方向和 Core 确定性限制，并接入现有 `pnpm test`、`pnpm check` 链路。
- **S-03 必要配置修正：** 若回归证明既定边界未被拦截或合法代码被误拦，只修正直接相关的配置、规则或检查接入；不得通过放宽限制、忽略用例或屏蔽诊断制造通过。
- **S-04 现有测试与构建复核：** 运行完整本地工程检查和现有独立 Python 合成测试；以当前版本的实际结果归档，不以测试总数或旧日志单独判定通过。
- **S-05 最小启动冒烟：** 验证 Vite 开发入口可启动，并对本地生产构建做一次实际浏览器应用壳检查，包含页面刷新与启动错误观察。
- **S-06 证据与清理：** 在后续 subtask 文档记录命令、退出结果、目标诊断及浏览器观察；验证结束释放自己启动的服务，清理临时样本，维护直接相关的工程说明。STATUS 中工程骨架项的证据改为指向本次可重复检查，不保留过期的测试数量或一次性实验描述；若复核证明已勾选项不成立，在修复并验证前取消勾选。

### 不包含

- 不重新初始化 Vite、拆包、升级工具链或新增依赖；依赖缺失时按锁文件恢复，不借机更新版本。
- 不实现 Core、Runtime、replay、Zustand、Three.js、输入适配、菜单或导入；分别由其他 P1 任务负责。
- 不提前创建未使用的模块目录、占位模型、公共测试 API 或通用静态分析框架。
- 不扩展或重构解析器，不修复与本任务无关的既有缺陷。
- 不建立 Playwright/E2E runner，不验证游戏循环、Canvas/WebGL、StrictMode/HMR 会话清理或完整浏览器/设备矩阵；这些由 P1-10 等任务负责。
- 不读取 `local/`、原版封包、截图或真实 Ghidra 项目，不安装/修改真实 DOSBox/Ghidra 环境。
- 不实现原版哈希扫描、依赖许可证工具或第三方声明；本地合规由 P1-12 负责。
- 不建设或验证 CI、仓库保护、SWA、PWA、部署；按 [ADR-0012](../../../decisions/ADR-0012-local-p1-defer-ci-deployment.md) 归 P5。

## 当前实现与依据

以下是对源文件和配置的核对，不表示已在本次 spec 生成中重新运行或通过验收：

- [package.json](../../../../package.json) 是单个 private ESM 项目，声明 Node 最低版本与 pnpm 版本；[.nvmrc](../../../../.nvmrc) 提供 Node 主版本，[锁文件](../../../../pnpm-lock.yaml) 已提交。当前锁文件包含包管理器依赖和应用依赖两个 YAML 文档，复核不得误当作重复键或只读取其中一段。
- [tsconfig.base.json](../../../../tsconfig.base.json) 开启 strict/noEmit 等共同选项；[core 配置](../../../../tsconfig.core.json) 不包含 DOM/Node ambient 类型，评审时其程序只含 ES lib 与现有 `src/original-data` 文件；`node:fs` 等 Node 模块导入没有 lint 规则，只能依靠这一类型环境拒绝；[app 配置](../../../../tsconfig.app.json) 含 DOM/JSX；[node 配置](../../../../tsconfig.node.json) 覆盖现有 TypeScript 工具与测试，include 中的 `eslint.config.js` 因未开启 allowJs 不进入类型检查。根 [tsconfig.json](../../../../tsconfig.json) 是编辑器引用入口，不能用其空 `files` 替代三个项目的实际检查。
- [eslint.config.js](../../../../eslint.config.js) 定义纯模块导入限制、Core 随机数/时间/调度/await 限制及测试例外。规则是否拦截样本须由回归验证，不能只断言配置里有某个字符串。评审时用 ESLint 虚拟输入探测（未写入仓库）发现以下已知缺口，由 S-02 回归证明、S-03 修正：
  - 纯模块与 Core 规则只匹配 `.ts`。`src/core` 下的 `.tsx` 导入 React 或调用 `Math.random()` 均无诊断，但 core 类型项目会纳入这些文件。
  - `react/jsx-runtime`、`idb-keyval` 子路径和 `../app` 目录入口导入未被拦截；type-only `three` 导入与 `../app/App.tsx` 已被拦截。
  - 不含 `await` 的 `async` 函数没有诊断。
- [vite.config.ts](../../../../vite.config.ts) 使用 React 插件和 Node 环境 Vitest，目前发现 `src/**/*.test.ts` 与 `tools/**/*.test.ts`；`.test.tsx`、DOM 单元测试和 E2E runner 不是现有能力。
- [IMFAT 测试](../../../../src/original-data/imfat.test.ts)、[payload 测试](../../../../src/original-data/payloads.test.ts) 使用 [synthetic.ts](../../../../src/original-data/synthetic.ts) 构造数据。[Python 测试](../../../../tools/ghidra/test_patch_watcom_cspec.py) 使用临时合成 XML，不需要安装 Ghidra。
- [应用入口](../../../../src/main.tsx) 启用 StrictMode，[App](../../../../src/app/App.tsx) 只显示项目标题和未包含原版内容的占位说明；没有游戏场景或会话。
- [nob-list](../../../../tools/nob-list.ts)、[nob-check](../../../../tools/nob-check.ts) 复用共享解析器。它们可被静态检查，但原版文件实验命令不能进入本任务的自动检查链。
- [.gitignore](../../../../.gitignore) 排除本地研究、依赖、构建产物和环境文件；这不等于已经具备内容哈希扫描。

架构边界依据[总计划 §4–5](../../master-plan.md#4-总体架构)、[ADR-0002](../../../decisions/ADR-0002-single-vite-project.md)、[ADR-0006](../../../decisions/ADR-0006-core-returns-events.md)。本任务不研究原版规则，无新的 U/B 结论。

## 行为与边界

### 自动检查契约

- 检查必须使用仓库实际的 TS/ESLint 配置、文件作用域和例外，不能复制一套更严格的测试专用规则来证明生产规则有效。
- 负向样本必须进入被检查作用域，并以所属类别的目标机制被拒绝：
  - 库依赖、应用层依赖与 Core 确定性限制：目标是对应的 ESLint 规则；即使 TypeScript 同时报错，也须断言该规则。
  - DOM、浏览器存储与 Node 环境限制：目标是纯模块类型项目缺少相应声明（找不到名称或模块）。须有同一源码在 app 或 Node 项目中可通过的对照，证明失败来自类型环境，而不是拼写错误或真实缺包。
  - 无输入文件、规则未应用、无关语法错误或 unused 报错都不能替代目标诊断。
- 纯模块类型程序不得经间接引用加载 DOM 库或 Node 类型声明，否则环境限制会静默失效。
- 边界不得因文件扩展名被绕过：纯模块类型项目纳入的每类非测试源文件（至少 `.ts`、`.tsx`）都必须受同一组纯模块与 Core 规则约束，或被明确拒绝。具体机制由 goal 决定。
- 不要求安装当前尚未使用的 Zustand、Three.js 或存储库来验证导入限制；检查不得依赖这些库缺失时的解析错误来通过。
- 每类负向限制有合法正向对照。预期被拒绝是该用例的通过结果，不应导致正常 `pnpm check` 报错；未被拒绝、误拒绝合法代码或检查器无法运行则应使整体检查非零退出。
- 回归只验证下表的明确语法/路径形式，不宣称能识别所有动态调用、别名重绑定或蓄意绕过。发现需要扩大规则语义的情况先记录，不能悄悄扩成通用静态分析项目。

### 必须覆盖的边界矩阵

| 类别 | 负向输入与预期限制 | 正向对照 |
|---|---|---|
| 纯模块 DOM 环境 | `src/core/`、`src/original-data/`、`src/content/` 中直接使用 `document`、`HTMLElement` 等 DOM 全局/类型须被拒绝 | 对应纯数据样本合法；app 中使用 DOM 合法 |
| 纯模块浏览器存储环境 | 上述纯模块直接使用 `indexedDB`、`localStorage` 须被拒绝 | app 层访问浏览器存储不应被纯模块规则误拦；不实际读写用户存储 |
| 纯模块 Node 环境 | 上述纯模块使用 `process`、`Buffer` 等 Node 全局/类型，或显式导入 `node:fs` 须被拒绝 | Node 工具/测试使用 Node 类型和接口合法，不实际读取原版文件 |
| 纯模块库依赖 | 上述纯模块的值导入、类型导入和 re-export 受相同边界保护：React/React DOM、Zustand、Three.js、`idb`、`idb-keyval` 的包根及其任意子路径（如 `react/jsx-runtime`）须被目标 lint 规则拒绝 | 相同纯模块的本地纯 TS 导入合法；适当消费层导入不得被纯模块规则误拦 |
| 纯模块应用层依赖 | 上述纯模块导入 app/render/ui/platform/workers 的相对入口或子模块须被拒绝，不能只覆盖一种深度的路径 | app/工具依赖共享纯模块合法 |
| Core 宿主随机与时间 | 直接 `Math.random()`、`Date.now()`、Date 构造及 `performance.now()` 须被拒绝 | Core 的显式 tick 参数、传入种子/纯数据和确定性计算合法 |
| Core 调度与异步 | 直接 `setTimeout`、`setInterval`、`requestAnimationFrame` 和 `await` 须被拒绝；`async` 函数声明、函数表达式、箭头函数与方法同样须被拒绝，无论是否包含 `await`。不经 `async`/`await` 的 Promise 链属于已知限制，不是本任务检测目标 | Runtime/app 的宿主调度与异步使用不应被 Core 专属规则误拦 |
| 扩展名作用域 | 纯模块中被类型项目纳入的 `.tsx` 等非测试源文件，执行上述库导入或 Core 宿主 API 时须被同样拒绝，或文件本身被拒绝 | app 层 `.tsx` 组件仍按 app 规则正常检查，不被纯模块规则误拦 |
| 测试例外与发现范围 | 不能通过把生产样本放入 `.test.ts` 或未扫描位置来宣称生产规则有效；测试仍必须被 Node 类型检查、lint 与 runner 发现 | `.test.ts` 使用 Vitest/Node 测试能力合法，既有生产/测试分工不变 |

本矩阵验证冻结的模块职责，不创建真实 Core 或未来消费者。尚未存在的目录使用合成检查样本表示；不留下占位生产文件。

### 运行、失败与清理

| 场景 | 预期结果 | 失败反馈 |
|---|---|---|
| 工具版本和依赖符合现有声明 | 使用锁定工具链运行现有检查，不修改 manifest/lock | 明确指出版本或锁定清单不一致，不自动升级 |
| 依赖/工具缺失 | 按仓库约定恢复已声明依赖；正常已有依赖不重复安装 | 无法恢复时记录未完成检查，不伪造通过 |
| 正向或负向回归不符合预期 | 总体检查失败，标明样本、作用域、检查器、预期与实际诊断 | 保留失败证据；只允许修复直接相关的既定约束 |
| 检查范围或测试发现为空 | 明确失败或报告不满足验收，不能以零用例成功作为基线 | 指出缺失的文件/用例与覆盖项 |
| 原版文件和真实 Ghidra 均不可用 | 自动检查与本地应用壳验证仍可完成 | 任何对这些输入的必需依赖视为隔离缺口 |
| 浏览器能力不可用或应用未渲染 | 浏览器验收未完成 | HTTP 200/build 成功不能代替浏览器结果 |
| 临时样本/服务清理 | 只删除本次拥有的临时样本、释放本次启动的服务 | 清理失败须报告，不删除用户文件或停止复用的用户服务 |

## 数据模型与契约

**无游戏或持久化数据模型变化。** 本任务不新增世界、实体、命令、事件、projection、内容 schema 或存档模型。已存在的解析结果类型仍在 [imfat.ts](../../../../src/original-data/imfat.ts) 与 [payloads.ts](../../../../src/original-data/payloads.ts)，不因工程复核改变其字段或语义。

回归结果须能关联“用例/受保护路径 → 检查器 → 预期限制 → 实际诊断/通过结果”，用于验收证据；这是测试报告要求，不是需要提前实现的公共 API 或独立 schema 文件。

### 持久化与兼容

不适用：不读写 IndexedDB、localStorage、用户资源缓存或存档。验证样本只在检查进程或独立临时位置存在；不修改用户 Ghidra 安装。已有解析器 API、应用壳可见行为和测试环境保持兼容。

## 技术决定

1. **保留现有工具链。** 使用 manifest/nvmrc/lock 声明的版本，不按“最新版”重选。TypeScript 兼容约束以[工程约定](../../../engineering/README.md#typescript-配置)为依据。
2. **持久自动回归而非一次性实验。** 用户于 2026-10-01 明确选择补自动正/负边界测试，使用现有依赖并接入现有检查链；本次 spec 不预定具体 harness 实现或文件拆分。
3. **允许最小必要修正，不扩大产品 scope。** 只修复使既定边界、发现范围或命令入口真实生效的缺口；不放宽纯度，不新增游戏行为，不处理无关问题。
4. **浏览器检查只到应用壳。** 用户于 2026-10-01 选择一次最小本地冒烟，不安装 Playwright。用现有 browser-testing 能力观察本地生产构建，游戏/HMR 生命周期仍留给 P1-10。
5. **两条测试链明确区分。** `pnpm check` 覆盖当前 TS/app 与新增边界回归；Python 工具测试单独运行，不宣称已经包含在 `pnpm check` 内，不引入新的统一编排工具。
6. **Core 同步边界包含 `async` 函数。** 用户于 2026-10-01 评审时确认：依据[总计划 §5](../../master-plan.md#5-状态管理与通信约定)“Core 不得调用任何异步 API”与同步 `step()`，`async` 函数（含箭头函数与方法）与 `await` 一起属于既定边界，按 S-03 补充语法级限制。Promise 链不扩展为通用异步检测，作为已知限制记录。

## 验收标准

## 验证策略

- **单元/契约：** 保留现有 Node 环境 Vitest 和合成解析器测试；计划新增边界回归用例，使用既有 TS/ESLint 能力检查真实规则。具体新文件由 goal 确定，不在 spec 阶段创建。
- **负向验证：** 对照边界矩阵确认每条禁止能力被目标限制拒绝，并覆盖回归检查自身错误、作用域未应用和无用例的失败反馈；无需永久修改真实规则或写入真实生产模块。
- **完整工程检查：** 执行现有 `pnpm check`；Python 另用 `python3 -B -m unittest discover -s tools/ghidra -p 'test_*.py'`。两者都只使用合成数据。
- **开发启动：** 使用现有 `pnpm dev` 启动本地入口，记录实际绑定地址和响应；不测试游戏/HMR 生命周期。
- **浏览器：** 按 [browser-testing](../../../../.agents/skills/browser-testing/SKILL.md) 观察由现有 `pnpm preview` 提供的本地生产构建，只要求当前应用壳的实际渲染、刷新和启动错误检查。选择本次可用桌面浏览器，不将其结果扩为完整兼容矩阵。
- **Replay/一致性：** 不适用；没有 Core 或 per-tick 输入，P1-03 负责。
- **实机/原版对照：** 不适用；不验证系统快捷键、GPU 性能或原版保真。
- **证据归档：** 执行时记录已验证提交/工作树基线、实际工具版本、命令结果和相关 AC，避免记录私人绝对路径或原版输出。不在生成 spec 时填入尚未执行的通过结果。

## 风险与恢复

风险等级：**低**。主要增加验证与必要配置修正，不改变游戏、解析结果或持久化数据。

- **假阳性/假通过：** 负向样本可能因缺模块、错误语法、unused 或未进入项目而得到错误结论。要求目标诊断、作用域证明与合法对照。
- **作用域缺口：** 规则可能只覆盖部分扩展名、包子路径或路径形式，使边界看似生效而实际可被绕过。评审已确认 `.tsx`、子路径与目录入口缺口存在，回归须覆盖这些形式。
- **错误规则副本：** 使用测试专用配置可能掩盖真实工程规则失效。要求实际仓库配置，不另写一套更严格的政策。
- **扩大修复范围：** 新回归可能暴露无关问题。只修复本矩阵及检查链的必要缺口；其他失败保留证据，不偷偷修复或放宽验收。
- **临时状态污染：** 违规样本或服务可能影响下一任务。验证使用隔离且明确拥有的临时位置，结束时清理，不撤销用户改动。
- **恢复策略：** 新增回归和必要配置修正应可独立撤销；不进行数据迁移或环境重置。恢复不得牺牲已确认的边界政策，重新执行受影响的本地检查。
