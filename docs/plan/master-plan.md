# Star Rangers 重制版：架构与开发总计划

> 核心路线：用 TypeScript 重实现游戏规则，Three.js 呈现世界，React 构建界面；复用用户本地原版内容，先完成忠实复刻，再推出可切换的美化资源包。首发为浏览器游戏，部署至 Azure Static Web Apps。

本计划冻结产品方向、技术边界、架构分工与阶段验收，不是完整的格式分析报告（§1.4 只记录初步文件盘点），也不是法律意见。工作名不代表商标可用性已经核实。具体依赖版本在项目初始化时选择经验证的稳定版本并锁定。

## 1. 项目定位与范围

### 1.1 项目是什么

这是一个**原版内容兼容的独立引擎重实现项目**，而不是给 DOS EXE 加网页外壳，也不是把反编译结果自动转换成 TypeScript。原版程序用于行为对照与必要的格式研究；正式产品不依赖 DOSBox，也不在浏览器中执行原版 EXE。

开发顺序固定为：**Classic 忠实复刻 → Classic 1.0 发布 → Enhanced 视觉升级**。先验证“这是原来的游戏”，再讨论“它是否更漂亮”。

### 1.2 首版交付范围

目标是支持选定基准版本的主要菜单、训练/练习模式（以实际版本为准）、完整战役、飞行与视角、武器和目标系统、战略地图、Warp、基地交互、通讯画面、过场视频、音频及保存流程。保留原版快捷键与信息布局，补充浏览器必需的资源导入、设置、错误提示和备份能力。

首发验收以 Windows、macOS、Linux 桌面浏览器为主。**首版只支持键盘与鼠标**：键盘负责飞行和全部快捷键，鼠标负责菜单、战略地图选择，以及原版支持的鼠标操控（以 P0 确认为准）。原版支持摇杆（含按住 2 号键将左右推杆变为横滚），并附带 ThrustMaster、Gravis、Suncom 配置文件；首版不开发手柄/摇杆功能，横滚等操作必须能用原版的键盘或鼠标操作完成。为后续扩展只预留必要接口：输入层按“输入源适配器 → 游戏动作”的方式组织，连续操纵以 −1…1 的模拟轴值进入 Input Snapshot，而不是写死为数字按键，从而将来新增 Gamepad 适配器时无需修改 Game Core。首版不调用 Gamepad API，不做设备映射、校准或设置界面，也不做手柄测试。手柄/摇杆、手机触控、Steam Deck 专项优化、原生商店发行、多人联网、原创战役和关卡编辑器不阻塞 Classic 1.0。

**默认键位即原版键位，包括 Alt/Option 开火与 F1–F9 视角。** 策略是“尽可能拦截，只对系统层面无法拦截的组合做兜底”，而不是预先换掉原版按键：

- **页面层拦截**：飞行中对所有已绑定按键的 `keydown` 与 `keyup` 调用 `preventDefault`，包括单独的 Alt（避免 Windows 上 Firefox 弹出菜单栏、Chromium/Edge 把焦点移到浏览器菜单）、F 键（如 F1 帮助、F3 查找、F5 刷新、F6/F7 焦点与光标浏览），以及 Alt+方向键（后退/前进）、Alt+D、Alt+F、Alt+Home 等浏览器快捷键。菜单、设置等非飞行界面不做拦截。
- **全屏 + Keyboard Lock**：在支持的浏览器（目前为 Chromium 系）中，飞行时进入全屏并锁定游戏用到的按键，可额外截获部分通常归浏览器或系统处理的组合。可截获范围因平台而异，以实机测试为准。[^keyboard]
- **系统层无法拦截的情况**：Ctrl+Alt+Del、未被 Keyboard Lock 覆盖时的 Alt+F4（Windows 与多数 Linux 桌面会关闭窗口）、Alt+Tab、Alt+Space，以及 Linux 窗口管理器自定义的 Alt 组合键。其中按住 Alt 开火时按 F4 切换视角，会直接触发 Alt+F4，是原版键位在浏览器中最主要的风险。兜底措施：任务进行中注册 `beforeunload`，关闭或刷新页面时由浏览器弹出确认；Windows/Linux 非全屏飞行时首次提示该风险；设置中可单独重映射开火键或视角键，但默认值不变。
- **macOS**：Option 键不被浏览器占用；Option 组合产生的特殊字符和死键不影响识别，因为所有键位按 `KeyboardEvent.code` 识别，不依赖 `event.key`。这也使 `?`、`<`、`>` 等依赖布局的按键在非美式键盘上仍可用。
- **AltGr**：欧洲键盘的右 Alt 会报告为 `AltGraph`，Windows 上还会附带一个合成的 `ControlLeft`。`AltRight`/`AltGraph` 同样视为开火，并过滤这个合成的 Ctrl，避免误触发其他绑定。
- **按键卡住**：Alt+Tab 等操作会让页面收不到 Alt 的 `keyup`。窗口失焦、页面隐藏或退出 Pointer Lock 时清空所有按住状态，恢复时以实际按键状态为准。

Pointer Lock 状态下按 Esc 必然退出锁定，无法拦截；Esc 的游戏功能需与这一行为兼容。[^pointer] P0 必须产出原版键位冲突表，逐项标记“页面可拦截 / 仅全屏 Keyboard Lock 可拦截 / 系统层不可拦截”，并在 Windows、macOS、Linux 实机上验证。自动化测试中的合成按键不经过浏览器自身的快捷键处理，因此不能作为拦截有效的证据。

### 1.3 什么叫“忠实”

忠实度优先级为：**玩法与胜负规则 → 任务和资源内容 → 操控与数值 → 画面和音频特征 → 不影响玩法的历史瑕疵**。不承诺逐像素或逐指令一致，也不以保留崩溃、损坏存档等问题为目标。任何改变视野、碰撞、AI、Warp 难度或信息可见性的修改，都不能冒充单纯美化。

“忠实”必须可量化验收。DOSBox 的时序不是逐帧确定的，原版对照只能按容差判定：每类行为（最高速度、加速、转向率、武器射速与射程、导弹追踪、护盾与能量恢复、Warp 能量消耗、停靠距离等）在行为规范中写明测量方法、样本数和允许误差（例如 ±5%，或 N 次试验中通过的比例）。没有容差定义的行为不能标记为“已对照”。

### 1.4 已盘点的原版事实

以下是影响本计划决策的关键事实，来自开发者本地光盘镜像与安装目录的文件盘点（2026-09-30），状态为“已确认”。权威的详细记录在 [original/](../original/)：文件与哈希见 [manifest](../original/manifest.md)，格式见 [formats/](../original/formats/)。

| 事实 | 对计划的影响 |
|---|---|
| 介质为 CD-ROM（卷标 `STAR_RANGERS`），只有 1 条 MODE1 数据轨，**没有 CD 音轨** | 音乐不来自光盘音轨；BIN/CUE 中的音轨不是必要支持项 |
| `SRANGERS.EXE` 为 MZ + LE 格式，含 Watcom 与 DOS/4G 标识，即 DOS/4GW 32 位保护模式程序；安装目录中的副本与光盘逐字节一致 | 基准为光盘原版、未打补丁（仍需查证是否存在官方补丁）；静态分析需要 LE 加载能力 |
| 数据主要位于 `MAIN/*.NOB`：`SR`、`OPTIONS`、`CRAFT`、`SCENARIO`、`AISTUFF`、`COMM`、`DEBRIS` | `.NOB` 封包是首要攻克格式 |
| 安装目录是光盘内容的子集；`COMMFACE.NOB`、`COMMFAC2.NOB`（约 64 MB）与 `FLICS/` 下 37 段 Smacker（`SMK2`）视频（约 45 MB）**只在光盘上** | 只导入安装目录无法得到完整内容；光盘镜像本身即可提供全部所需数据 |
| 音频通过 Miles 驱动（`.MDI` 音乐 / `.DIG` 数字音效），可选 AdLib、OPL3、MT-32、General MIDI、AWE32 等 | P0 必须选定一个参考音乐设备；不同设备音色差异很大 |
| 光盘另含其他游戏演示与宣传程序（`APCHDEMO`、`CAPDEMO`、`MKTSCRN`） | 不属于本项目内容，导入时跳过 |

尚未确认的事项统一登记在[待确认登记表](../original/unknowns.md)（`U-###`），涵盖数据与格式、画面、玩法与数值、输入、存档和环境六类，不在本计划中重复列出。P0 必须让每一项都已确认，或有明确的研究计划与负责阶段。

首个阶段必须固定版本、语言和补丁组合，避免同时兼容所有发行版。

## 2. 冻结的技术选型

| 领域 | 本项目决定 | 边界 |
|---|---|---|
| 语言 | TypeScript，开启 strict | 游戏核心不依赖浏览器或 UI 框架 |
| 工程 | 单个 Vite + React + TS 项目，pnpm 管理依赖 | 一个仓库、一个 `package.json`（`private: true`）；不用 monorepo/workspace，不发布 npm 包；不引入 SSR、Next.js 或游戏服务端 |
| 3D | Three.js，首版使用 WebGLRenderer / WebGL 2 | WebGPU 为后续专项，不双轨开发 |
| UI | React + DOM/CSS；必要时 SVG/Canvas | React 不承载逐帧模拟；Classic 飞行中的驾驶舱、HUD 与 MFD 不用 DOM 绘制 |
| 状态 | Game Core + Zustand vanilla stores；类型化 Event Bus 归 GameRuntime | 唯一游戏事实源在 Core；Core 定义事件类型但不知道 Event Bus 存在 |
| 通信 | Commands/Input 向内，State/Events 向外 | UI、渲染器不能直接修改世界 |
| 游戏组织 | 实体 + 按职责分开的系统 | 首版不引入 ECS、通用引擎或大型刚体库 |
| 输入与声音 | 浏览器输入适配层（首版仅键盘、鼠标）+ Web Audio 适配层 | 对外只暴露游戏动作与音频接口；输入源可插拔，预留模拟轴 |
| 数据导入 | 纯 TS 解析器（含光盘镜像扇区与 ISO9660），浏览器与 Node.js 工具共享 | 导入/转换放 Worker；主模拟首版留主线程 |
| 视频与音乐播放 | 冻结 `VideoPlayback` / `MusicPlayback` 抽象接口，不冻结解码或合成实现 | 只在本地解码，不上传、不用服务器转码；不分发原版内容或其转码结果；不要求跨源隔离；按需加载，不进主包；许可证符合依赖许可证政策（§9.2）。具体方案由 spike 决定 |
| 持久化 | IndexedDB；小型偏好设置可用 localStorage | 不将完整游戏世界交给 Zustand persist |
| 测试 | Vitest + Playwright + 实机对照 | 自动测试不能替代真实 GPU 与键鼠实机测试 |
| 交付 | 静态 Web 构建 + PWA | 首版不制作 Windows/macOS/Linux 原生安装器 |
| 部署 | GitHub Actions → Azure Static Web Apps | 原版资源不进入构建、服务器或公开 CI |

Three.js 官方仍将 WebGLRenderer 列为纯 WebGL 2 项目的推荐路径。向 WebGPURenderer 迁移时，自定义材质与后处理可能需要改写，不能视为替换构造函数即可完成。因此首版固定 WebGL 2，先把玩法与保真验收做完。[^three]

不使用 React Three Fiber 作为首版场景管理层。这不是否定其能力，而是选择由独立 GameRuntime 管理生命周期、场景和帧循环，使 React 专注界面。

## 3. 逆向 DOS 游戏与复用原版内容

### 3.1 总体方法

采取**先观察行为、再研究数据、最后针对性分析代码**的路线，不以理解整个 EXE 为前提。

| 步骤 | 主要工作 | 输出 |
|---|---|---|
| 建立基准 | 在隔离的 DOSBox 环境安装与运行；固定模拟器配置、游戏版本和音频设备设置 | 可复现基准环境、操作录像、版本指纹 |
| 文件盘点 | 比较安装前后与光盘内容；记录文件大小、哈希、头部与用途线索 | 文件 manifest、资源目录、未知项登记 |
| 行为实验 | 对飞行、导弹、护盾、Warp、地图、基地和任务触发逐项测试 | 行为规范、测量结果、对照场景 |
| 格式研究 | 优先解析图片、调色板、音频、模型，再研究任务与存档 | 格式说明、解析器、资源查看器 |
| 针对性代码分析 | 围绕文件加载、按键处理、数值计算和任务判定定位必要逻辑 | 有证据支持的规则与兼容性说明 |
| 回归验证 | 在同类场景下比较原版与新版 | 差异清单及其处理结论 |

DOSBox-X 的调试构建提供寄存器、内存、反汇编、断点和入口调试能力；Ghidra 用于静态分析、交叉引用和反编译辅助。主程序是 DOS/4GW 下的 LE 格式（§1.4），使用前需核实所用 Ghidra 版本能否直接载入 LE；不能时采用 LE/LX 加载扩展或先转换格式，并把所用工具与版本记录在研究笔记中。是否还需要额外的解包或运行时内存映射，由实际二进制决定。不能把反编译输出当成原始源码。[^dosbox][^ghidra]

每条研究结论标记为“已确认 / 高概率 / 未确认”，并关联版本、实验或偏移位置。受原版资源版权约束的光盘镜像、截图、音频、EXE、内存转储和提取结果只放在仓库内被 `.gitignore` 排除的 `local/` 目录（或仓库之外），绝不提交。由于源码公开，`docs/` 中的格式说明只描述结构，不粘贴原版的大段字节、图片、文本或解码结果。

### 3.2 复用边界

| 原版内容 | 处理方式 |
|---|---|
| 模型、贴图、调色板、驾驶舱图片 | 从用户合法取得的副本本地解析，转换为内部资源 |
| 音效与音乐 | 原版没有 CD 音轨；音乐与音效经 Miles 驱动输出。先识别实际编码；音效解码后经 Web Audio 播放，音乐按 P0 选定的参考设备经 `MusicPlayback` 还原，OPL 模拟、MIDI 合成或预渲染等具体路径由 spike 决定（§3.4）；不默认都是 WAV |
| 过场视频与通讯画面 | `FLICS/*.SMK`（Smacker）与 `COMMFACE*.NOB` 从光盘数据本地读取；视频经 `VideoPlayback` 播放，运行时解码还是导入时转码缓存由 spike 决定（§3.4） |
| 任务、文本、舰船和武器参数 | 尽量本地导入；嵌入 EXE 的数据按必要范围研究 |
| 游戏规则与算法 | 根据行为规范和必要分析独立重实现，不直接拼接反编译源码 |
| DOS 绘图、驱动、内存管理和平台接口 | 不复用，由新运行环境替代 |
| 原版二进制存档 | 列为可选兼容工作；不阻塞新版自有存档 |

**解析不了不等于随意编造。** 不影响主线的未知内容登记后延后；影响核心玩法的未知项需要继续实验。临时替代资源或近似行为必须明确标记，不能计入忠实复刻完成率。

### 3.3 统一资源流程

```text
用户自己的原版光盘镜像或光盘文件
        ↓
版本识别、校验、解包与解析
        ↓
版本化内容清单 + 内部标准数据
        ↓
浏览器本地资源缓存
        ↓
Game Core / Three.js / Audio / React
```

标准数据方向为：模型与材质可导出 glTF/GLB，图片可导出 PNG，采样声音转换为受支持的音频或 PCM，任务和数值转换为有 schema 的结构化数据。标准化过程必须保留坐标、单位、材质、透明、调色板动画和逻辑语义，而不是仅做到“能打开”。

资源通过稳定 Asset ID 引用。缓存键包含原版指纹与转换器版本。`tools/` 中的 Node 脚本与浏览器共享 `src/original-data` 的解析逻辑，用于研究、批量转换和排错；游戏运行时使用规范化后的数据。

首版主要导入入口为**原版光盘镜像**：CloneCD（`.ccd`/`.img`/`.sub`）、BIN/CUE 和 ISO。解析器支持 2352 字节原始扇区与 2048 字节用户数据扇区，在 TS 中读取 ISO9660 目录，只提取本项目需要的文件（`MAIN/`、`FLICS/` 等，约 125 MB），跳过其他游戏的演示和宣传内容。镜像通过 `File.slice` 按需分块读取，不整体载入内存。备用入口为光盘文件的 ZIP 或文件集；目录选择作为增强功能，不依赖某一浏览器独有接口。showDirectoryPicker 目前仍不是所有主要浏览器都支持的功能。[^file] 导入格式分阶段实现：P2 只支持开发者现有的 CCD/IMG，BIN/CUE、ISO 和 ZIP/文件集在 P5 补齐。

安装目录只是光盘的子集，缺少通讯画面与过场视频，不能单独作为完整导入源；它只用于补充比对。浏览器不运行 DOS 安装程序，也不需要运行——光盘上的 `MAIN/` 已包含安装后的全部游戏文件。版本识别按原版文件白名单与哈希进行，忽略 `SRANGER.CFG`、`SRHISCOR.RAW`、`*.SWP`、`.DS_Store` 等用户状态或系统文件。

### 3.4 视频与音乐：先冻结接口，再用 spike 选实现

Smacker 视频解码要处理 Huffman 树、调色板增量、分块视频、压缩音频和音画同步；Miles 驱动的音乐需要 OPL 模拟或 MIDI 合成。两者都是独立的工程，因此只冻结接口和约束，具体实现由 spike 决定：

- **`VideoPlayback`**：打开资源、播放/暂停/跳过、把帧输出到 Canvas 或纹理、通过 Web Audio 时钟同步音频、播放结束与出错事件。
- **`MusicPlayback`**：载入曲目、播放/停止/循环/淡出、音量，以及按游戏状态切换曲目。
- **视频候选方案**：纯 TS 解码器；只编译 FFmpeg 中 Smacker 部分的精简 WASM（不是完整的 ffmpeg.wasm）；导入时转码并缓存（如用 WebCodecs 编码，需核实各浏览器编码支持与存储成本）。
- **音乐候选方案**：TS 或 WASM 的 OPL 模拟；General MIDI 合成（需音色库，注意其许可证）；导入时预渲染为音频并缓存。
- **判定标准**：与本地参考结果逐帧或逐段对照的正确性、音画同步、体积、加载与解码性能、维护成本，许可证符合依赖许可证政策（§9.2），以及是否满足 §2 中的约束（尤其是不要求跨源隔离，这默认排除多线程 WASM 方案）。

spike 不阻塞主线，可在 P4 之前任何时候进行（例如与 P3 并行），结论写入 ADR。上层代码只依赖接口，因此更换实现不影响其他模块。

## 4. 总体架构

### 4.1 目录与模块划分

项目是一个普通的 Vite 应用，模块只是 `src/` 下的目录，不拆成独立包：

```text
index.html               Vite 入口页面
vite.config.ts           构建、Worker 与 PWA 配置
public/                  原样复制到构建产物：staticwebapp.config.json、图标、manifest
src/
  main.tsx               应用启动
  app/                   应用装配、GameRuntime、页面流转、导入流程
  core/                  世界、实体、系统、规则、命令、事件、UI projection（纯数据）、存档模型
  original-data/         光盘镜像与原版格式解析、版本识别、转换与校验
  content/               内容契约、Asset ID、资源包版本
  render/                Three.js 场景、相机、模型映射、特效、Classic 驾驶舱/HUD/MFD
  ui/                    React 组件、Zustand stores、projection → store 桥接
  platform/              输入、音频、视频播放、存储、浏览器生命周期
  workers/               导入/转换 Worker 入口
e2e/                     Playwright 测试；单元测试与源码同目录放置（*.test.ts）
tools/                   本地盘点、解包、查看和对照的 Node 脚本，直接引用 src/original-data
docs/                    文档，结构见 docs/README.md：进度、总计划、ADR、原版知识、指南、评审记录
local/                   原版镜像与研究产物，git 忽略，永不提交
```

目录就是职责边界。边界由 lint 规则检查，而不是靠拆包：`src/core`、`src/original-data` 和 `src/content` 不得导入 React、Zustand、Three.js、DOM 或 IndexedDB；`src/core` 不得导入 `render`、`ui`、`platform`、`app`，也不得使用 `Math.random`、`Date.now`、`performance.now` 等非确定性 API（见 §5）。`src/original-data` 通过抽象的字节读取接口访问数据，浏览器端用 `File.slice` 实现，Node 端用 `fs` 实现，因此同一份解析代码可同时供 Worker 和 `tools/` 使用。首版不建设插件市场、通用编辑器或通用游戏引擎。

UI projection 是 Core 内把权威状态映射为纯数据视图的函数，不依赖 Zustand；`src/ui` 中的桥接层按采样频率调用它并写入 Zustand store。Classic 模式下，飞行中的驾驶舱、HUD、MFD（通讯、能量、损伤）全部由 `src/render` 在同一画面管线中绘制，以保证缩放与对齐一致；React 负责菜单、导入、设置以及飞行之外的界面。

### 4.2 数据流

```text
键盘 / 鼠标 / React 控件（将来可接入其他输入源适配器）
            ↓
连续 Input Snapshot / 离散 Command Queue（归 GameRuntime）
            ↓
GameRuntime 按固定步长调用 GameCore.step(tickInput)
            ↓
Game Core 更新权威状态，返回 DomainEvent[]
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
          Render State  UI Projection  DomainEvent[]
              ↓          ↓          ↓
           Three.js    Zustand    GameRuntime 在本帧模拟结束后 flush 到 Event Bus
                         ↓          ↓
                       React      音频 / 特效 / 提示 / 开发事件日志
```

Game Core 不导入 React、Zustand、Three.js、DOM 或 IndexedDB，也不持有任何对外引用：输入和命令通过 `step()` 的参数进入，事件通过返回值交出。它能够在 Node.js 测试中无画面运行。GameRuntime 负责装配各模块、调度帧循环、持有命令队列与 Event Bus，以及开始、暂停、重启和销毁会话。

渲染器以实体 ID 维护模型映射，可保存插值结果、粒子和相机表现，但不保存用于判定胜负的另一套血量、坐标或任务状态。资源载入和存储等异步工作位于核心之外。

## 5. 状态管理与通信约定

| 状态/信息 | 权威位置 | 消费方式 |
|---|---|---|
| 坐标、速度、血量、能量、AI、任务、Warp | Game Core | 系统更新；GameRuntime 每 tick 后提取 Render State 与 UI projection |
| Classic 飞行中的护盾、弹药、目标名称、速度等 HUD/MFD 数据 | Core 的 UI projection | `src/render` 每个渲染帧直接读取最新 projection 绘制，不经 Zustand |
| 菜单、简报、地图、设置等 React 页面需要的游戏数据 | Core 的 UI projection → Zustand | 桥接层按 10–20 Hz 采样写入，重要状态变化立即发布；React 通过 selector 订阅 |
| 菜单页、对话框、设置表单、地图缩放 | React 本地状态或 UI Zustand store | 仅影响界面；涉及游戏的动作转 Command |
| 用户偏好与键位 | 设置 store + 持久化适配器 | 运行时应用；不冒充游戏事实 |
| 插值坐标、相机平滑、粒子生命周期 | Renderer | 逐渲染帧处理 |
| 开火、爆炸、Warp 开始等已发生事件 | `GameCore.step()` 的返回值，由 GameRuntime 发布到会话级 Event Bus | 音频、特效、提示和开发事件日志订阅 |

采用 Zustand 的 vanilla store，使非 React 的桥接层能够发布 UI 快照；React 按 selector 订阅，而不是订阅整个世界。官方 API 支持这种独立 store 和选择性订阅模式。[^zustand]

**命令不是状态。** 点击“Warp”只能提交请求，由 Core 校验能量、目的地与当前模式，再改变状态并发出结果；UI 不能先把自己改成“已经 Warp”。连续操纵轴由 Input Snapshot 表示，开火、选目标、确认地图等离散操作由 Command 表示。

**事件是 step 的输出，不是 Core 的副作用。** Core 定义 `DomainEvent` 类型，但不知道 Event Bus 存在，也不接受 `emit` 回调。注入回调会让订阅者在 tick 中途运行，读到更新了一半的世界；改为返回事件数组后，这种情况从结构上就不可能出现。一帧可能运行多个固定步长 tick，GameRuntime 先收集这些 tick 的事件（每个都带 tick 号），等本帧模拟结束后统一发布，并限制每帧最多补跑的 tick 数，避免切回页面后一次补跑过多。订阅者不能修改世界，新的意图进入下一个 tick 的命令队列。

**Core 内部不使用发布/订阅。** 同一 tick 内，碰撞 → 伤害 → 摧毁 → 任务触发这类连锁，由按固定顺序执行的系统流水线显式传递本 tick 的事件列表完成，执行顺序在代码中一目了然，不在 Core 内另建事件总线。

**状态与事件的界线。** 需要持续显示或判定的事实，例如护盾值、当前目标、任务目标是否完成，属于状态，经 UI projection 读取；一次性的反馈，例如音效、闪光、提示音，属于事件。UI 和渲染器不能靠累积事件重建状态，否则读档、中途挂上订阅者或漏掉事件时，界面会与真实状态不一致。Event Bus 不负责保存持久事实，也不承担事件溯源架构。事件是可序列化的纯数据，附带必要的实体 ID、tick 和位置快照，不持有实体对象引用，避免收到爆炸通知时实体已经不存在。

**确定性约束。** Core 内部使用可变世界，不为每个 tick 复制不可变状态，以免在 60 Hz 下造成 GC 压力；确定性来自“相同初始状态 + 相同种子 + 相同的每 tick 输入与命令 + 固定系统顺序”，与状态是否不可变无关。Core 不得调用 `Math.random`、`Date.now`、`performance.now` 或任何异步 API：随机数来自 Core 自有的带种子随机数生成器，时间只来自 tick 计数；粒子等纯表现层的随机放在 Core 之外，不消耗 Core 的随机序列。以上由 lint 检查。replay 的输入是“初始状态 + 种子 + 每 tick 输入与命令记录”，事件流与周期性状态哈希只作为一致性校验，不用于重建状态。快照（replay 校验、调试、存档）通过显式序列化取得。

同一 JS 引擎下基本浮点运算可复现，但 `Math.sin`、`Math.cos`、`Math.exp` 等函数的结果在不同引擎间可能不同，因此不承诺跨浏览器逐位一致。若 P0 证实原版使用定点数与三角函数查表（光盘上同时期的 Apache 演示带有 `ARCSIN.TBL`、`ARCCOS.TBL`、`ARCTAN.TBL`，可作为线索，尚未确认），Core 将按原版方式实现，同时获得数值保真与跨引擎确定性。

**更新频率分层。** 以 60 Hz 固定模拟为初始方案，渲染按显示刷新率插值；原版时间规律通过测量与兼容逻辑校准，不把“原版也是 60 Hz”当作事实。tick 频率是 Core 的参数而不是隐含常量：速度、加速度、冷却和恢复等数值统一以“每秒”或明确的“每原版 tick”为单位存储，使后续调整 tick 频率不会让已校准的数值失效。Classic 飞行 HUD 由渲染器每帧读取 projection，不降频；React 页面经 Zustand 的数据按 10–20 Hz 采样，重要状态变化立即发布。

**渲染插值与可变世界。** Core 原地修改世界，旧值会被覆盖，因此渲染器不直接读取正在变化的世界。GameRuntime 在每个 tick 之后提取一份 Render State（实体 ID、位置、朝向及渲染所需的少量标志），保留上一个 tick 与当前 tick 两份，渲染器在两者之间插值。

**运行时控制与游戏命令分开。** 暂停时不调用 `step()`，游戏命令队列也不会被处理。因此暂停、继续、退出、返回菜单（包括原版的 `p` 暂停键）走 GameRuntime 自己的控制通道，不进入游戏命令队列；暂停期间仍必须能处理这些控制以及设置界面。所有订阅、输入监听、音频和 GPU 资源必须随会话销毁；React StrictMode、热更新或返回菜单不能产生第二条游戏循环。

## 6. 补齐 Three.js 之外的游戏能力

本项目只建设需要的“小型游戏运行层”：固定步长调度、实体生命周期、输入映射、碰撞与命中、音频管理、任务状态、存档和资源管理。

碰撞、导弹制导、移动与 AI 都应由原版行为决定。简单球体碰撞可以作为原型，但高速弹丸要测试穿透漏判；基地交互不能盲目用一个大包围球代替。也不自动加入横移、真实牛顿惯性或现代物理，以免改变玩法。

保留必要的开发工具：资源查看器、实体/任务状态检查、碰撞可视化、事件日志、帧耗时显示和可重复输入场景。工具可以做成开发模式页面；首版不建设可视化关卡编辑器。只有实际性能分析证明有瓶颈，才引入 WASM、ECS 或模拟 Worker。

## 7. 美术与声音路线

### 7.1 Classic：先保真

原版模型轮廓、贴图、色彩、驾驶舱布局、目标提示、Warp 隧道形态和音频反馈优先保留。原版有两种游戏分辨率：HI 为 640×480，LO 为 320×240，都是 4:3 方形像素（见待确认登记表 U-006）。Classic 以 HI 为基准。

**窗口自适应。** 画面随窗口大小连续缩放，分三层处理：

- **飞行画面（Classic 默认）**：3D 场景、驾驶舱与 HUD 组成一个 4:3 的画面，整体等比缩放以填满窗口，多出的部分留黑边。原版是方形像素，不需要纠正像素比例。缩放没有上限；窗口小于 640×480 CSS 像素时继续缩小，但提示文字可能难以辨认。3D 默认按窗口实际像素渲染（乘以设备像素比，并设上限以控制性能），因此放大后更清晰而不是像素变大；驾驶舱位图随画面等比缩放。可选“原版像素”模式：在 640×480 的离屏目标中绘制全部画面再放大，并可选整数倍最近邻放大。窗口变大只会让画面更清晰，不会让视野更宽。
- **可选宽屏（默认关闭）**：窗口宽高比在 4:3 到 16:9 之间时，保持垂直视野不变，水平视野随窗口加宽（Hor+）；超出该范围的部分留黑边。只用于全屏视角（F2）和外部视角（F3–F9）；驾驶舱视角的位图是固定画幅，仍按 4:3 显示。HUD 元素按原版位置锚定到中心或屏幕边缘，不拉伸。宽屏会让玩家看到更多内容，属于改变信息可见性，设置中需明确标注，不计入 Classic 保真验收。Core 中的目标选择、雷达和 AI 一律使用固定的原版逻辑视野，不读取渲染视野，因此开启宽屏不改变规则判定。
- **非飞行界面**：菜单、导入、设置、简报等 React 页面采用响应式布局，随窗口重新排版。战略地图是原版固定布局的 640×480 整屏画面（见 [B-001](../original/behavior/B-001-strategic-map.md)），因此与飞行画面一样整体等比缩放，不做响应式布局。

菜单、导入、设置和错误提示可以从开始就用现代网页交互，但战斗信息结构与数值含义不重设计。字幕、音量、键位重映射、减少闪烁等可访问性设置独立提供，默认不改变游戏规则。

### 7.2 Enhanced：再美化

Classic 1.0 验收后，逐项替换高清纹理、重绘 UI、更细致的模型、粒子和后处理。美化以原版轮廓、配色和识别特征为约束，不默认追求写实或 AAA 效果。

两个模式使用**同一 Game Core、任务数据、数值和存档**。外观资源通过 Asset ID 覆盖；碰撞体、锁定点和基地停靠范围仍由逻辑定义，不从美化模型重新推导。美化失败或设备性能不足时可以回到 Classic。

复用、描摹或重绘原版美术并不自动获得分发权。只有权利清晰的资源包才可公开部署；其余转换或增强结果保持在用户本地。[^fairuse]

## 8. 浏览器运行、存档与隐私

原版数据在本地选择、解包和转换，默认不上传服务器。导入器应限制文件数、解压后大小与资源尺寸，校验偏移和路径，处理损坏文件；不运行导入文件中的 JavaScript、可执行代码或任意插件。

IndexedDB 分开存储导入资源、转换缓存、设置与自有版本化存档。需要提取的原版数据约 125 MB，但转换后的缓存可能大得多：8 位调色板贴图展开为 RGBA 后是原来的 4 倍，音频解码为 PCM 也会变大，若视频 spike 选择转码还要另算。因此缓存尽量保留调色板等紧凑格式，加载时再展开；导入前按转换后的预计大小检查可用配额并提示。存档记录游戏/schema 版本及内容指纹；升级要支持迁移或给出明确不兼容提示，不能静默覆盖。原版存档导入是后续适配器，不与新版保存能力绑定。

存档时机遵循原版（P0 确认）。若原版只在任务之间保存战役进度，首版同样只保存战役进度，不承诺在任务中任意时刻序列化完整世界；任务中途挂起是另行评估的可选功能。战役存档至少包含：当前任务与剧情分支、战役开始时锁定的难度、僚机选择、勋章与晋升、战役统计；具体字段以 P0 对原版的研究为准，存档槽数量也按原版确定。高分榜作为独立记录保存在 IndexedDB，不与单个存档绑定。一次存档在单个 IndexedDB 事务中整体写入，避免写到一半时页面关闭导致存档损坏。

浏览器数据可能因用户清理、存储压力或浏览器策略被删除，因此必须提供**存档导出/导入、资源重新导入、空间不足提示**。Safari 会删除最近 7 天浏览中没有用户交互的站点由脚本创建的数据，对未安装为应用的网页尤其要提醒用户定期导出存档。可请求持久存储，但不能保证永不丢失。生产域名尽早固定；预览域名和正式域名的数据不能假定互通。[^storage]

音频在用户点击“开始/继续”后解锁，并处理被浏览器阻止的情况。切换后台时自动暂停、清空瞬时输入；恢复时重新校准时钟，避免累计时间导致游戏瞬间快进。浏览器会限制后台 requestAnimationFrame，Web Audio 也受自动播放策略约束。[^audio][^raf]

默认不接广告、账户或遥测。诊断信息由用户主动导出，排除原版资源字节、私人路径和不必要的个人数据。网络隐私验收以实际请求审计为准，而不是只写一段隐私声明。

## 9. 打包与发布方案

### 9.1 首版包形态

Vite 输出静态应用包，应用壳、3D 运行时代码、导入 Worker 和开发工具按需拆分。游戏资源不编入 JS bundle。发布物包括网站构建、版本信息、本项目许可证与第三方许可声明，以及使用指南。研究工具留在仓库的 `tools/` 中，从源码直接运行，不单独发布。[^vite]

PWA 提供可安装入口与离线应用壳。离线游戏的前提是应用所需文件已经缓存，且本地原版资源仍完整存在；PWA 安装能力因浏览器而异，不要求所有平台都有同一种安装按钮。[^pwa]

Service Worker 更新在菜单或用户确认后激活，不在战斗中替换资源。缓存按版本管理，先验证新版本再清理旧缓存。离线能力、更新能力和存档安全必须分别测试。

首版不发布原生安装器，也不把 Electron/Tauri 列为前置依赖。未来需要商店发行或操作系统深度集成时，再单独做包装层决策，不重写 Game Core。

### 9.2 版本与配置

分别版本化：应用、内容 schema、解析/转换器、自有存档。依赖使用 lockfile 固定，升级经测试后合入。构建时的公开配置不得包含 Azure token 或其他秘密。

源码公开，默认采用 MIT 许可证，在首次公开仓库前最终确认；确认后若要更换，作为 ADR 记录。许可证只覆盖本项目自有的代码、文档与合成测试资源，不覆盖也不授予任何原版内容的权利；README 与站点需写明这一点。选择 MIT 意味着允许他人基于本项目制作闭源衍生版本；若将来希望衍生版本保持开源，可在作为唯一作者期间改用 MPL-2.0 或 GPL。有外部贡献者后再更换许可证需征得其同意。

**依赖许可证政策。** 约束主要来自依赖本身的许可证，而不是本项目选择 MIT：

- **宽松许可证**（MIT、BSD、Apache-2.0、ISC、Zlib 等）直接允许。
- **LGPL** 只允许作为独立加载、可被替换的模块（如单独的 `.wasm` 文件）进入网站产物，并随发布提供该部分的源码获取方式与许可声明。
- **GPL/AGPL** 不进入网站产物。网站把 JS/WASM 发送到用户浏览器，一般视为分发，混入 GPL 代码会使整个网站须按 GPL 提供。确有需要时，作为“是否更换项目许可证”的决策写入 ADR，而不是悄悄引入。
- 只在本机使用、不随网站分发的研究工具（如 DOSBox-X、Ghidra 及其插件）不受此限。`tools/` 中若包含 copyleft 代码，须在对应目录标明其许可证。
- 音色库、字体等数据资源同样适用此政策，按各自许可证核实可否随网站分发。

CI 检查依赖许可证是否符合以上政策；构建时自动生成第三方许可声明，随网站发布。

## 10. Azure Static Web Apps 部署

### 10.1 部署拓扑

```text
GitHub 仓库
  ├─ PR → 类型检查 / 测试 / 构建 → SWA 预览环境
  └─ 受保护 main → 同一套检查 → SWA 正式环境

SWA：应用代码、自有网页素材、许可证与公开说明
用户浏览器：原版数据、转换缓存、存档
```

首版采用 SWA Free 承载个人非商业项目，独立资源组与项目仓库。不需要 Azure Functions、数据库、Container Apps、Front Door 或资源上传 API。只有经授权的美化资源显著变大或访问需求超出额度后，才增加 Blob Storage 或调整套餐。

当前微软配额表列出 Free 单环境存储 250 MB、全部环境合计 500 MB、每月包含带宽 100 GB、预览环境 3 个；上线前再次核查。原版数据只在用户本地，不消耗这些站点资源额度。[^quota]

### 10.2 构建与环境

GitHub Actions 显式安装固定的 Node/pnpm 版本、安装锁定依赖、执行 lint/typecheck/test/build，再将 `dist/` 交给 SWA。选择“CI 自行构建、SWA 跳过重复构建”路径，部署目录必须包含 `staticwebapp.config.json`，该文件放在 `public/` 中，由 Vite 原样复制进 `dist/`。微软支持预构建产物部署和相关路径配置。[^build]

部署令牌只保存在 Actions secrets。源码公开后，来自 fork 的 PR 不获得部署凭据，不能通过执行不受信任 PR 代码读取秘密。`main` 受保护，必须通过 CI 检查才能合并；单人维护阶段不要求他人审批（GitHub 不允许批准自己的 PR），有协作者后再启用审查要求。预览环境及时关闭，避免累积超过额度。

公开仓库和预览网站都是公开的。预览只包含应用壳和权利清晰的合成测试内容；确有保密需求时另行配置访问控制，不能依赖“网址难猜”。

### 10.3 站点配置与运维

`staticwebapp.config.json` 管理路由回退、MIME、缓存和安全响应头。SPA 回退不得吞掉缺失的 JS、Worker、模型或音频请求；带 hash 的静态文件长缓存，HTML、Service Worker 与版本清单采用可更新策略。CSP 按实际 Worker/blob/音频使用收紧，不使用宽泛通配策略。[^swa]

首版不需要 SharedArrayBuffer，不强制开启跨源隔离；未来采用线程化 WASM 时再评估。生产域名、自定义证书和离线缓存应联合测试。每个发布保留可重新部署的产物、版本记录与回滚步骤，并验证旧页面遇到新部署时能安全回到菜单更新。

## 12. 开发阶段与验收条件

按通过验收推进，不先承诺日历工期。各阶段的实际进度记录在 [STATUS.md](../STATUS.md)，阶段结束时的评审记录在 [reviews/](../reviews/)。逆向的不确定性优先消除；P0 可行性评审前，工程工作只限于不依赖原版格式的骨架和公开合成资源预览。

**P3 越早出现越好。** P2 与 P3 可以重叠：P1 完成后即可用明确标记的临时替代资源搭建 P3 的玩法框架，P2 每交付一项原版资源就替换一项。重叠只影响开工时间，不放宽退出条件——P3 仍须使用原版内容走通闭环。P2 只做玩法切片需要的内容，其余导入格式、视频、音乐和内容补全分别放在 P4 与 P5。视频与音乐的实现 spike（§3.4）不属于任何阶段的退出条件，在 P4 之前完成即可。

| 阶段 | 主要交付 | 退出条件 |
|---|---|---|
| P0：基准与可行性 | 基准版、隔离运行环境、文件 manifest、行为记录与容差、键位冲突表、研究未知项和目标测试设备；待确认登记表逐项结论 | 原版可重复运行；关键记忆场景可复现；来源、版本与研究范围已记录；不存在把猜测当成格式规范的条目；[待确认登记表](../original/unknowns.md)每一项都已确认，或有明确的研究计划与负责阶段；**可行性评审通过**：能列出 `.NOB` 封包条目，并至少还原一个舰船模型和一个任务的结构，同时确认任务数据是否嵌在 EXE 中。评审不通过时，先写明缩小范围或调整路线的方案，再进入 P1/P2 |

| P6：Enhanced 美化 | 独立美化资源包、可切换外观、画质设置和性能回退 | 使用同一存档与规则；同一运行时/输入下逻辑结果不因外观切换改变；不改变碰撞和难度；Classic 仍完整可用；公开资源权利清晰 |

**关键里程碑不是先做漂亮菜单，而是 P3 的完整玩法切片。** P4 不因为局部逆向困难就偷偷改成原创玩法；遇到关键阻塞时记录影响并重新安排研究范围。

## 13. 主要风险与治理

| 风险 | 应对决定 |
|---|---|
| 数据封装复杂或规则嵌入 EXE | 先攻克 `.NOB` 封包与玩法切片所需内容；P0 设可行性评审；逐项追踪，不试图一次反编译全部程序 |
| 现代实现改变原版手感 | 对照实验、带容差的版本化行为规范、数值回归；规则改动必须单独审批 |
| 浏览器占用原版键位 | 默认保留原版键位；页面层 `preventDefault` 加全屏 Keyboard Lock 尽量拦截；系统层冲突用关闭确认、风险提示和可选重映射兜底；按 `code` 识别 |
| Three.js 周边工作失控 | 只建项目需要的运行层与小工具；暂停通用编辑器、ECS 和过早多线程 |
| 浏览器兼容与数据丢失 | 普通文件导入、真实设备测试、备份/重新导入、稳定域名；对 Safari 7 天清理策略单独提示 |
| 美化侵入玩法或推迟发布 | Classic 发布前不以美化为主线；逻辑和外观资源分离 |
| 只用键鼠导致操控手感偏离原版 | 原版默认操控若依赖摇杆模拟量，P0 记录键盘/鼠标下的原版行为作为对照基准；Core 预留模拟轴，手柄/摇杆适配器作为首版后的独立专项 |
| 原版版权与名称风险 | 本地数据、独立实现、不默认公开提取资源；原版文件不进仓库（`.gitignore` + CI 哈希扫描）；首次公开仓库与网站前完成名称审核 |

项目在美国开发与发布，网站和源码均公开。非商业用途不是自动授权；美国版权法的 fair use 需要具体判断。§1201(f) 的互操作性逆向例外有明确条件，且只在需要规避技术保护措施时才相关，因此 P0 要记录原版是否有光盘检测或手册问答等拷贝保护。本项目采用“引擎/工具与原版资源分离”降低风险，但这不是合法性保证。公开仓库中的格式文档只描述结构，不包含原版字节或内容。仓库名与站点名使用“Star Rangers”前，需检查商标与名称权利，必要时改用不含原名的项目名，只在说明中注明兼容对象。一个人既研究又实现，不应对外宣称完成了严格的 clean-room 流程。[^fairuse][^law]

关键决策写入 [ADR](../decisions/)：Web-first、独立 Core、状态所有权、光盘镜像本地导入、WebGL 2、Classic 驾驶舱渲染归属、Classic/Enhanced 分离、静态部署、项目许可证与依赖许可证政策，以及视频与音乐 spike 的实现选择。只有出现可复现的性能、兼容、内容生产或发行需求时才重审，不因为新框架发布而迁移。

后续扩展顺序为：Classic 稳定维护 → Enhanced → 手柄/摇杆输入适配器 → 手机/Steam Deck 与包装层专项 → 原创内容工具。联网、账号和云存档都需要新的产品决策，不是当前架构的隐含承诺。

## 结论

**先让原版内容在新的 Web 运行时中完整、可信地复现；再改善外观，而不是在复刻过程中重新设计游戏。**

本计划的下一项交付是 P0 的基准环境、行为规范与可行性评审，当前进度见 [STATUS.md](../STATUS.md)。架构选择已经确定；原版尚未验证的事实，交给逆向证据而不是技术栈偏好决定。
