# P3-10：通讯、基地交互与补给 — Spec

## 问题与目标

P3-02 到 P3-07 已经交付正式 Core、Runtime 与会话、原版键位、飞行运动和战斗规则，但闭环中的 L-08“基地交互”（[P3-01 闭环步骤](../01/spec.md#闭环步骤)）还完全不能走通：

- `communications`、`launch`、`navigate-selection` 及基地上下文的 `select-number`、`confirm-selection` 尚未实现（[commands.ts](../../../../src/core/systems/commands.ts)）。飞行中的 `select-number` 则在 [flight-control.ts](../../../../src/core/systems/flight-control.ts) 的 `judgeCommands` 内已被处理为 `ignored`/`wrong-context`，不会到达 `judgeCommand`；只改后者不能接通通讯数字。P3-05 已经绑定相关物理键（[绑定表](../05/spec.md#绑定表)）。
- 流水线的 `communications-reply` 与 `base-interior` 阶段是空的，`mission-flow` 没有停靠子状态（[pipeline.ts](../../../../src/core/systems/pipeline.ts)）。`communications` 分区未就绪，其中 `MenuContentReference` 与 `OptionUnavailableReason` 仍是 `never` 占位（[projection.ts](../../../../src/core/projections/projection.ts)）。
- P3-03 导入的 `data/comm-menus` 与 `data/base-repair-items` 还没有进入 Core（[RuleDataInputs](../../../../src/core/world/rule-data.ts)）。
- P3-07 在伤害与被毁规则中为通讯反应留下了固定调用点 `0x3c208`、`0x3c0f4`；P3-06 在停放行进中标出了僚机到达与靠近基地的报告位置；实例化扩展点 `0x38cd4`（僚机报告）也未接入。这些调用点都还没有实现，因此与原版相比少了它们的随机抽取和状态（[Core 交接](../../../engineering/modules/core.md#交接)）。
- 入港与离港是飞行中的 Smacker 过场（G-02/3、G-02/4）。P3-04 只实现了出发前的初始保持，运行中衔接的 Core 状态、输出、继续条件与 replay 语义留给本任务定稿（[P3-04 衔接占位](../04/spec.md#衔接占位)）。
- 基地内部画面（G-05）与通讯头像、通讯动画（G-03）都没有项目呈现。

完成后可观察到：

- 在 Node 中，用合成或本地真实内容创建的世界里，玩家可以按原版规则打开通讯菜单，逐级选择类别、对象和命令。远处的基地只给出状态查询；进入停靠距离后，基地菜单给出停靠。停靠请求经回复与倒计时后入港，进入基地内部；在基地内部可以选择并完成修理与补给，再按 `l` 离港回到飞行。全程以带 tick 的领域事件与 projection 呈现。
- 伤害、被毁与实例化中的通讯反应、僚机报告和无线电队列按原版代码路径运行。它们写入的友伤累计与感谢计数交给 P3-08、P3-11 读取。
- 浏览器中，入港与离港显示可跳过的 G-02 占位；基地内部是明确标注的项目界面（G-05），显示修理与补给的结果；通讯菜单的状态与 G-03 文字由 projection 提供，绘制归 P3-13。
- 同一内容、配置、种子与输入在同一运行时 replay 一致，与占位的显示时长和是否跳过无关。
- 通讯、停靠与补给的原版事实写入 `docs/original/`。R-17 至 R-19 按本 spec 写定的方法与判据取得与原版的对照结论（[规则对照目录](../01/spec.md#规则对照目录)）。

阶段范围依据[总计划 §12](../../master-plan.md#12-开发阶段与验收条件)，任务导航见[阶段索引](../tasks.md#p3-10-通讯基地交互与补给)。生成、审阅或批准本 spec 都不会自动启动实现。本任务沿用 [P3-01 的切片配置](../01/spec.md#切片配置)：战役 group 0 / slot 1、原始难度 19、僚机可选。

- **S-04 无线电队列、来电页与通讯反应：** 回复队列与 `communications-reply` 阶段、来电页 5、队列清空的调用入口；伤害与被毁中的通讯反应（含抽取）、友伤累计、感谢计数与限频计时；实例化与停放行进中的僚机报告（[无线电队列与通讯反应](#无线电队列与通讯反应)）。
- **S-05 停靠请求与等待（R-18）：** 任务内子状态 3、4 的进入、回复、倒计时、取消与到期（[停靠请求与等待](#停靠请求与等待)）。

- **S-07 基地内部、修理与补给（R-19）：** 基地上下文的命令，服务项的状态、服务队列与每帧服务，完全修理 `0x39820`，弹药与能量的补给，基地受攻击或失效时的影响与自动离港（[基地内部、修理与补给](#基地内部修理与补给)）。
- **S-08 离港（R-18）：** `l` 离港与自动离港，视角恢复、僚机恢复、按保存的位姿放置玩家（[离港](#离港)）。
- **S-09 运行中衔接（G-02/3、G-02/4）：** Core 的衔接输出与 Runtime 在该 tick 之后的保持、清键与恢复；同步修订 P3-04 的运行中衔接（[运行中衔接](#运行中衔接)）。

### 不包含

- **僚机命令的效果（P3-08）：** 僚机收到命令码 1–7 之后的行为（攻击、忽略、掩护、交战、返航、移动、状态回复）由 AI 处理 `0x61f20` 实现，归 P3-08。本任务投递并保存命令码，提供无线电队列供其回复；P3-08 未接入时不宣称僚机命令已生效。
- **基地与应答机的 AI（P3-08）：** 基地的自动挂点开火（P3-07 已交付规则，P3-08 决定何时扣动）以及基地、应答机（Xpon）的其他行为。
- **种类 `0x4000` 的拟移交边界，尚未生效：** [P3-02 的 CR-02](../02/spec.md#cr-02-实体的战斗状态d-01)目前将运行时构造明确交给 P3-10，而[阶段索引](../tasks.md#p3-08-ai-与僚机)将 Xpon 的 AI 与行为交给 P3-08。两者不能靠本 spec 单方面排除来消除冲突。推荐由 P3-08 统一拥有 AI 调用和玩家 `b` 键共用的构造，依据为[已确认的分配入口与调用关系](../../../original/formats/executable.md#two-allocator-paths-native-inputs-and-profile-comparison)，不是“与通讯无关”的推断。D-01 须先在 P3-02 与接收任务契约中获批落实，包含输入责任与验收归属；移交前仍保留现行责任，不得把此项记为已交接或无人负责。若移交不获批，须补齐本 spec 的相应范围与验收后再分解该部分工作。
- **地图与 Warp（P3-09）：** 基地中 `m` 打开地图、地图拒绝 `w` 等地图规则，以及左显示屏页 6。本任务保证基地视角 6 作为上一视角时的写入符合原版，并把接口交给 P3-09。
- **任务流程（P3-11）：** 主流程状态 0–5、任务内子状态 1、2、6，玩家被毁、救援、信标、结果与僚机损失计时。本任务提供 `0x39820` 给救援复用、提供队列清空入口给流程调用，不实现这些流程。
- **表现（P3-12 至 P3-14）：** 通讯菜单、来电页与 G-03 文字在驾驶舱中的绘制，基地视角下的 HUD 组；通讯、光标与执行键的音效。
- **切片外与非正常玩法：** 第三个通讯类别（B-004 在其他任务中观察到的平民类别，对应关系为高概率；所选任务中没有其对象）、10 项以上对象列表的字母按键、作弊与调试命令、练习模式。按[通讯菜单](#通讯菜单)的规则在创建时拒绝切片不可达而未支持的语义。
- **其他：** 原版基地内部画面与 TABL 10165 的图像和文字（G-05，P4）；通讯媒体的实际播放（G-03，P4）；存档。默认复用已导入内容，不自行扩充导入链、内容契约或转换器版本；若通讯回调、时序、消息选择或 RNG 需要当前缺少的内容元数据，由 D-03 明确所需数据并先完成 P3-03 契约修订，不能以“不改导入”为由省略规则。

## 行为与边界

本节区分已引用的原版契约、明确的项目选择与待 Q 研究的方向。后者不是已确认算法：例如菜单是否自动跳级/刷新、状态回复的分支、服务顺序与速率，必须由对应 Q 达到门槛并经 D-01/D-03 定稿后才可实现。研究和正文方向矛盾时修订正文，不以带有“Q 核实”的猜测作为测试期望。

### 通讯菜单

- **层级与页面：** Core 表示类别、对象列表与命令菜单，页 2–4 的逐一对应、空/单对象时是否跳级由 Q-01 定稿，不强制所有打开路径都逐级经过三屏。菜单的保存页、来电保存页与 Warp 保存页不得共用一个含义不明的字段。写页时复用 `left-page-changed`，命令序号的使用与 P3-07 一致。
- **类别菜单：** 依 TABL 2007 的顺序列出对象列表非空的类别，按显示位置生成键（1 起）；最后一项为数据给出的 `x`。
- **对象列表：** 列出所选类别掩码中、按种类位升序与分配次序遍历、状态 ≥ 7 的对象（停放者在内，Q-01 核实筛选条件），按位置生成键；最后一项来自 TABL 2009。项中保存对象引用；对象失效后该项的处理按 Q-01。
- **命令菜单：** 菜单表的选择沿用 [comm §2](../../../original/formats/comm.md#2-builders-and-selection-confirmed-code) 的已确认谓词；门禁测试分别覆盖活动字段、种类、距离和任务流程，不从地图可见性或模型大小推断。Q-01 确定菜单何时建立、是否刷新、当前战斗目标与通讯对象的关系，不能预先要求“必须重开才会刷新”。
- **按键与可达性检查：** 保留数据键的字节位置与匹配次序，不能把命令码或源项序号当键。当前切片只接通 `select-number`（1–9）与 `communications close`（折叠后的 `x`）；物理键的修饰组合仍以 P3-05 为准。创建时同时检查：
  - 数据键文本足够长，所有会被读取的命令项键可由这两个命令表达，命令码在已支持语义内，退出键与零值项相符；保留原版首匹配规则，不擅自去重。
  - 可显示类别数和各类别对象数的保守上界分别不超过 9，退出项不计入生成键上界。按有效僚机配置、声明/编组展开、延迟与条件生成及运行时构造共同确定，不只数当前存活对象；上界不能证明有限时明确拒绝，不截断、分页或猜为零。沿用现有生成范围检查，不建设切片外的通用任务分析器。
  - 所选内容中未出现的键不因此成为普遍格式约束；内容读取器仍保留原始结构，Core 以不支持的规则语义拒绝。Q-01 的真实内容闭包须证明所选任务所有可达菜单都通过。
- **命令入口与次序：** 在 `flight-control.ts` 的唯一 `judgeCommands` 循环中、`flightAction` 消费数字之前接入菜单判定。不能只在 `commands.ts` 添加分支。每条命令按当前位置的权威菜单与交互状态判定，产生恰好一个 `command-result`；本条直接改变的菜单供后续条目读取，请求阶段才生效的变化不提前冒充已应用。覆盖同 tick 的 `open → 数字 → 数字 → close → 数字`、重复 open/close、`Enter` 与 `speed-preset` 交错，不能逐类重排或沿用整批开始时的菜单快照。
- **上下文：** 基地、地图与 Warp 不经通讯键过滤；是否保存、遮盖、恢复或清理已有菜单/来电状态按 Q-01、Q-04 与 D15 定稿，不概括为“菜单状态不变”。菜单键之外的动作按其既有语义处理；特别是飞行 Enter 保留手动匹配速度。
- **通讯子系统：** 玩家字段 13 为 2 时拒绝打开（原版不消费 `c`）。玩家的该字段至多为 1，伤害不可达（[D6](../../../original/formats/executable.md#d6-two-bit-subsystem-fields--confirmed-code-meanings-likely-consumers)）；规则照样实现并测试。
- **菜单内容与文字：** projection 给出菜单身份（哪一张表）、层级、各项的键、项在源表中的序号或对象 ID 与可用性；文字由消费者从导入内容与名称引用解析，Core 不含文字。

### 规则输入与读模型边界

- **创建输入：** 在 [create-world.ts](../../../../src/core/world/create-world.ts) 的顶层 `CreateWorldInput` 增加两份 `LogicAssetInput`，沿用既有严格解码、字段白名单、ID/身份核对与冻结副本；在世界内部保存为带具体 `CommMenus`/`BaseRepairItems` 类型的已验证输入。同步 `CONTENT_INPUT_FIELDS`、Core 和 app 的两处 `RuleDataInputs`、包解码、运行创建、replay 的另供内容与本地检查工具。不得旁路 `validatePackage`，也不得为旧调用者填合成默认数据。
- **服务项语义：** `BaseRepairItems` 的格式域是 0–31、33、34，而 `Entity.combat.subsystems` 目前只有 19 项。创建时验证本次必读选择值及其组展开能由已支持规则处理，超出则结构化拒绝；不能越界读写、默认为完好或无依据扩成 32 项。Q-08 还须明确容量/除数为零、负数、整数溢出等输入的合法性；使用已有 Core 错误与数值契约，不用默认速率或 NaN 掩盖问题。
- **projection：** `communications` 就绪后明确区分无玩家、关闭菜单、各菜单层级、来电显示与基地服务状态；`menu: null` 表示关闭，不表示未实现。已毁但仍存在的玩家不伪装成无玩家，控制可用性另按原版门禁表达。字段形状在 D-01 定稿，读者只获得允许显示的信息，不能为便利泄露完整实体表或隐藏对象位置。
- **身份与快照：** 菜单项用源表/源项或生成时的对象身份作稳定引用；显示位置和快捷键单独给出，不能把会变动的行号作为跨 tick 身份。来电可在说话者被移除后到达，持久消息及一次性事件必须保存解析所需的名称引用/类别快照，不能只靠对象 ID 再查当前世界。所有输出深度冻结且脱离世界，重复读取不抽取 RNG、不改变状态；后挂消费者不靠重放事件历史才能恢复当前菜单与来电。

### 命令投递与回应

- **投递：** 命令菜单所选项的值非 0 时，投递一个命令请求（原版消息 0x100），在请求处理中把命令码写入目标对象（+0x184）；值为 0 时不投递并关闭菜单。命令码 9 同时进入停靠请求（`0x333b4`）。目标在请求处理时已失效则无作用（Q-02 核实）。投递后菜单是否关闭并恢复保存的页按 Q-01。
- **接收者时序：** 请求处理中写命令码，与对象更新读取命令码是两个阶段；同 tick 多次写同一对象的覆盖、对象先失效、延迟回复与过期停靠请求的关联由 Q-02/Q-06 定稿。不能把每个 accepted 命令都扩成一条必达回复，也不能为避免覆盖而加入原版没有的每对象命令队列。`command-result` 与实际投递、回复、取消事件分别描述事实。
- **基地回应（`0x3bed0` 的通讯部分）：** 按 Q-03 核实的对象更新与停放调用位置处理状态查询（7）和停靠请求（9），保留其门禁、合并/覆盖、回复选择和清除语义；不预设每次都恰好回复一条。停靠回复的回调须与 Q-04/Q-06 的时机一致；受攻击的状态回复不等于自动禁止停靠或减慢修理。
- **僚机：** 种类 2 的命令码 1–7 由 P3-08 的 AI 处理 `0x61f20` 消费。本任务交付投递与保存，以及供其回复使用的队列接口；P3-08 未接入时，命令码保存在僚机上而没有效果，projection 与事件不宣称僚机已执行。
- **事件：** 只有实际写入对象命令码时才发出投递事实；若 D-01 决定另记排入请求的事实，必须与投递区分。每个事件带 tick、稳定身份与消费所需快照，回复取出另有消息事件。UI 不因 accepted 显示“已执行”。

### 无线电队列与通讯反应

- **队列（`0x2c740`）：** 世界拥有一个按到期时刻排序的队列，同刻先进先出，项为 `{ 消息身份, 到期, 回调 }`；回调是封闭的规则枚举（例如“停靠回复”），不是函数。队列进入快照。原版无界；Core 设项目上限，超出为故障，上限依据在 D-01 定稿。
- **取出（`communications-reply` 阶段，`0x2cd60`）：** 按 C2 在此阶段至多取一条到期且满足流程/通道条件的消息，不能在 `base-interior` 等后续阶段再次排空。D-03 定稿逻辑通道的占用与回调执行点；入队、取出、可见和完成不是同一事实，不能预设取出即播完或立即回调。基地回应、伤害反应在本 tick 哪一阶段入队，决定它最早在哪次取出中可见。
- **流程门禁：** D-01 定义任务进行中与停靠子状态的唯一权威来源，`MissionStatus: built` 不等同于原版全部主流程状态。P3-11 尚未接入时明确限定本构建可验证的状态，不能将其未实现的门禁硬编码为永远通过；双方共享字段/谓词，不另建竞争的主流程。
- **清空（`0x2cd20`）：** 本任务提供清空入口与其对左页的作用（回到页 0）；被毁、信标到期、状态切换与任务开始的调用归 P3-11。
- **通讯反应：** 在 P3-07 的固定调用点插入 `0x3c208` 与 `0x3c0f4`：
  - 僚机受玩家攻击时的友伤累计（窗口 0x780 单位），僚机受他人攻击且船体低于三成时的报告（限频 0x5A00）；
  - 玩家攻击友方（限频 0xF00，玩家状态 +0x78）；友方受敌方攻击（每个受害者限频 0x2D00，对象 +0x17C）；
  - 僚机击杀报告；友方在僚机 3500 以内被敌方击毁；清除最后敌人后对受攻击友方的感谢与感谢计数（玩家状态 +0x60）；玩家击毁友方（限频 0x3C0，玩家状态 +0x7C）；其他友方被毁。

  条件抽取按 C2/Q-05 的来源、分支和调用次序逐一核实，包括消息查找是否成功、媒体身份与声音分配的分支，不能预先固定成“总共两次”。D-03 必须说明保留哪些规则抽取及其理由；不能因为项目不播放头像/声音就减少世界 RNG 的消耗。救援清除两个玩家限频计时（P3-11 调用）。

- **规则输出：** 友伤累计供 P3-08 读取（`0x61f20` 拒绝命令、`0x61abd` 进入模式 5）；感谢计数供 P3-11 的统计；其余写入只影响消息。
- **消息身份：** 每条消息以封闭身份及说话者快照给出，不含原版文字或语音。G-03 的项目摘要必须区分本次规则判定的各类回复/拒绝/状态，不能把不同状态归成一个“收到”。缺少名称到消息映射或时序所需的内容时由 D-03 阻塞，不按种类猜出一条替代消息。

### 停靠请求与等待

- **进入：** 命令码 9 的投递把任务内子状态设为 3，期限为当前取样 + 0x780；`0x333b4` 的写入时刻、期限所用的全局与比较方式按 Q-06。
- **回复：** 基地排入的停靠回复被取出（或按 Q-04 的回调时刻）时，若子状态仍为 3，则设为 4，到期为取样 + 0x200。
- **检查（`mission-flow` 阶段，读取上一 tick 的取样）：** 子状态 3、4 中，停靠对象（玩家对象 +0x194，Q-06 核实其写入者）不再有效或状态 < 7 时回到 0；子状态 3 到达期限也回到 0；子状态 4 到期时投递停靠请求（子命令 0）并设为 5。比较的严格与否、u32 视图与上一取样按 Q-06。
- **等待中：** 不额外锁住普通飞行或暂停模拟；保留当前视角的键处理。Warp、地图等动作仍须通过其自身规则，不能把“按键仍处理”写成无条件允许 Warp。研究覆盖打开菜单换通讯对象、重复请求、回复迟到与基地失效发生在不同阶段的情形。子状态 3–5 的菜单门禁按已确认记录。
- **取消反馈：** 原版取消时有无消息按 Q-03、Q-06；Core 发出带原因的取消事件，G-03 文字只在原版有反馈时出现。

### 停靠

- **门禁：** 请求处理中执行子命令 0：`0x3959c` 返回的基地须等于停靠对象，否则回到子状态 0，不停靠。
- **执行：** 保存玩家位姿、停靠玩家及符合条件的僚机、进入基地视角、清除玩家目标、建立服务列表与光标、置重绘标志并给出事件。精确先后、保存视角的字段、僚机距离与修理的对象由 Q-07 定稿。任务子状态 5 在停靠请求执行前就会写入，不能只凭该值输出“已停靠”；projection 必须与实际活动、视角及有效基地状态一致。
- **停靠中的其他系统：** 停靠的玩家与僚机保留移动块并参与运动（停靠中的速度与位置变化按 Q-10）；不参与能量更新、碰撞与弹丸命中，不是目标候选；导弹起爆照常命中。玩家被毁走 P3-11 的入口（`0x32d74` 在子状态 3–5 中照常接受）。
- **地图：** 基地中的 `toggle-map` 由 P3-09 实现；上一视角保持为 6，关闭地图回到基地，地图拒绝 `w`。本任务保证进入与离开基地时视角字段的写入与原版一致。

### 基地内部、修理与补给

- **命令：** 基地上下文中 `navigate-selection` 移动光标（`0x186b20`），夹在 0 与 10 之间；`confirm-selection` 在光标项仍需服务（`0x39cb4`）时把它移到服务队列（`0x186a70`）首位；`launch` 离港。每次导航与执行发出事件，供 P3-14 播放光标与执行音效（SND 10167、10169）。执行键不论项是否需要服务都有音效（已确认，代码）；光标在端点时是否有音效按 Q-08。
- **服务项状态（`0x39cb4`）：** 按 Q-08 核实单槽位/组的聚合、资源或挂点的特殊状态，以及它读取存储的子系统字段还是直接查询挂点；不能把 W4 的挂点状态函数直接当作 `0x39cb4` 的完整算法。显示排序、光标选中项和执行队列为不同概念，Enter 重排队列不能无依据改动显示排序。
- **服务（`base-interior` 阶段，`0x398ec`）：** 按 Q-08 确定每项生效时刻、分步修理、队列移动/出队、资源和弹药的增量/上限，以及控制锁定与扰动的各自重置点。已有 [repairListMounts](../../../../src/core/rules/mounts.ts) 的“修一个/修全部”返回值不同且不补弹，必须复用其真实语义，不能在一次服务调用中无依据全修全补。基地内开地图后是否停止这一阶段、重排服务或离港后是否保留已完成进度，都须从 Q-08/Q-09 定稿。
- **完全修理（`0x39820`）：** 与逐项服务是不同入口，按 D7 只重置它实际写入的字段；复用挂点修理/选择和 P3-06 的控制辅助，不调用完整世界或实体初始化代替。分别核对护盾、充能、最高速度、能量更新时钟、武器选择/冷却、耗尽锁存、控制锁定/扰动、击杀与统计哪些改变、哪些保留。项目耗尽锁存须允许真实恢复后再次耗尽发出新事实，但不能伪造第二次耗尽。事件只在原版有对应反馈的调用位置产生，尤其区分请求处理与之后阶段的音效请求（[帧流水线](../../../original/formats/executable.md#frame-pipeline-p3-0201)）；不能看到循环选择就无条件播放音效。D-01 定稿 `commandIndex: null` 的 `weapon-selected` 使用边界。
- **基地状态的影响：** 基地受攻击、受损或失效时是否暂停服务、拒绝停靠或中断补给，按 Q-03、Q-08 的代码证据实现；子状态 5 中基地失效时自动离港。
- **只读视图：** projection 给出 Q-08 证明可显示的基地、服务项身份/状态、光标、服务顺序与进度、玩家资源和弹药。未知速率不伪造倒计时，未确认的内部队列不默认作为原版可见信息；开发诊断可以经快照另行检查。

### 离港

- **入口：** `launch` 命令在基地上下文中投递子命令 4；子状态 5 中停靠对象失效时，`mission-flow` 阶段自行投递。
- **执行（`0x38ff4` 子命令 4，Q-09 核实次序）：** `0x4f4e0` 中属于规则的部分（Q-09）；玩家活动恢复为活动；视角恢复为上一视角，低于 0xC 时为 0xC（P3 中为 F1）；停靠的僚机恢复活动；按保存的姿态与位置放置玩家，放置序号加 1；子状态回到 0；视角切换置重绘标志；发出离港事件与离港衔接事件（G-02/4）。
- **离港后：** 玩家的速度、油门与移动块是否重建按 Q-09；不另设项目规则。

### 运行中衔接

本节提出 [P3-04 留给本任务](../04/spec.md#衔接占位)的运行中衔接契约，D-01 时同步定稿 P3-04 spec；不是已经实现或已经获批的 API。

- **Core：** 接纳 [P3-02 技术决定 2](../02/spec.md#技术决定)（G-02 占位不计时）。停靠/离港状态变化仍在原定阶段执行，该 tick 的其余阶段照常完成；只把媒体用时按零处理，不宣称固定步长与原版整帧完全等价。使用继承 `{ type, tick }` 的领域事件携带 `gap`，不是裸 `{ gap }`。Core 不保存宿主等待状态，也不接受“占位结束”命令；跳过不能跳过回复、停靠倒计时或服务。
- **Runtime 帧边界：** Runtime 内部在一次成功 step 后识别有类型的衔接输出，此 tick 为本帧最后一个 tick，仍保留该 tick 所有命令结果及其余规则输出。实际执行 tick 数与提前截断原因由帧报告明确表示，不冒充补跑上限或录制容量停止。先固定屏障，阻止追加游戏输入，再按原有规则帧后分发事件；不能由 Event Bus 订阅者重入 `clearIntent`/`resetClock`，也不开放外部每 tick 检测器。会话在安全边界进入保持并发布静止帧，折叠两帧 Render State（previous = current，alpha = 0），避免离港放置或保持结束出现旧帧插值。
- **输入与完成凭证：** 保持期间无 step、无游戏输入、无游戏 rAF；清除按住与重复，取消 Runtime 中尚未交给 step 的命令，并经 `onCommandsCancelled` 以 `transition` 通知一次。已经执行的命令不能再报告为取消。同一运行可能多次停靠/离港，因此凭证必须绑定 **ownerId + runId + 本次 transitionId**；旧占位计时器、重复 skip 与旧完成请求不得结束同 run 的下一次占位。transitionId 是 app 的单调身份，不进入 Core 或 replay。结束后重锚时钟，不补跑。
- **多事件与竞态：** 同 tick 重复离港请求的规则效果按 Q-09 定稿，不能用“每 tick 最多一个”的未证假设丢事件；若该 tick 实际产生多条衔接，按事件次序形成有限的占位序列，全部结束之前不恢复模拟，每项有独立凭证。D-01 定稿容量与故障反馈。退出/释放/换 run 使整个序列失效；异常按既有锁存优先于正常保持，不能故障后继续播放再重启。暂停或隐藏请求与衔接交错时保留恢复保护；hidden/pagehide 后即使 visible 且占位自然结束，仍要求显式继续。结束后呈现 Core 的最终状态，不强制跳到与它矛盾的基地/飞行页。
- **replay：** 录制只含 tick；保持不进入录制，因此 replay 与占位显示多久、是否跳过无关。
- **不做：** 不在 tick 中间暂停，不以完成占位写 Core 状态。该机制仅承诺本任务两种衔接；P3-11 可复用基础设施，但其救援/终态的优先级和衔接须在自己的契约核实，不由本 spec 预先批准。

### 依赖与交付边界

- 直接依赖仍为阶段索引的 P3-03、P3-06、P3-07；复用已经交付的 P3-02、P3-04、P3-05。本 spec 不改变阶段任务依赖，也不要求等待下游 P3-11/P3-13 整项完成。
- P3-08 与本任务共享命令接收槽、友伤累计与回复接口，D-01 在双方接线前确定唯一写入点；先集成的一方不得加入长期无消费者的空回调代替效果。若 P3-08 已实现，联合验证真实的命令消费和回复；尚未实现则以独立的合成内部状态验证生产者契约，明确 R-12 的实际行为仍未验收，不伪造僚机确认。
- 地图/Warp 及被毁救援的完整状态链分别由 P3-09、P3-11 验收。本任务覆盖自己对 view/activity、子状态、队列清空和修理入口的契约；当前树没有这些系统时，使用已有内部 test-support 建立前态测试，不新增生产状态注入入口、不伪装成真实闭环。已经集成的消费者必须做实际流水线回归；尚未集成者交 P3-15 复验，不能倒置 P3-11 对 P3-10 的依赖。
- P3-10 的浏览器验收是输入/规则/G-02/G-05 的集成，不是正式通讯画面验收。P3-13 必须把菜单和 G-03 信息实际画出；其完成前不宣称 L-08 的可视闭环或整个 P3 退出条件通过。

### 数值、随机数与时序

- **时间：** 遵循 [P3-02 时间模型](../02/spec.md#时间模型)：时钟单位 1/64 秒，生产每 tick 2 单位。`mission-flow` 读上一 tick 的取样，其余阶段读本 tick 的取样（C3）。到期比较的 u32 视图与严格与否按 Q-06、Q-11 逐条确认，不统一套用。
- **随机数：** 只用世界 RNG，在固定阶段按确定次序抽取；`0x3c208`、`0x3c0f4`、`0x38d54` 的条件抽取，以及 Q-03、Q-08 若发现的其他抽取，都按原版条件发生。不要求复现原版序列，按 P3-02 的支持集模型核对。
- **表现无关：** 规则不读语音、动画或渲染帧；D-03 定稿的来电时序只依赖 Core 状态与时钟。

### 对照方法与判据

沿用 [P3-07 的两层方法](../07/spec.md#对照方法与判据)：规则或单次转移核对，加默认 2 单位/tick 的正式 World 连续运行。后者从自己的内容、配置和输入推进，不能每步把原版前态灌回后声称连续一致。两次运行的随机序列不同，不要求未经条件化的整个任务逐位相等。

连续行为的单位、窗口、容差、样本依据及媒体设置按 D-02 在正式采样前、看到新版对照结果前定稿批准。可以借鉴 [P3-07 D-02](../07/spec.md#d-02-连续行为判据) 的事件锚与步长误差分析，但不能先验认定修理、语音和来电页也能“归一化后精确一致”。只有独立证据证明同一确定递推关系时才采用精确判据，其余从采样分辨率和误差预算导出容差；不套用无依据的百分比或“一个 tick”。方法在 B-004 采集前写定，新版结论与候选身份归 subtask 证据。

| 类别 | 判为“一致”的条件 |
|---|---|
| 菜单层级、项与键、页面 | 相同场景下各级菜单的表、项数、键、可用性与页面变化一致（离散） |
| 距离门禁 | 阈值常量按代码精确核对；运行时在阈值两侧各取样，结论与距离读数一致 |
| 停靠等待与倒计时 | 子状态序列、取消条件与回复到入港的时间链在 D-02 判据内一致 |
| 停靠、离港的状态写入 | 同一完整操作数下离散转移一致；连续位置/姿态依据 Q-11 与 D-02 的精度判据，不泛化为 DOS/JS 逐位一致 |
| 修理与补给 | 各服务项的完成时间链在 D-02 判据内一致；修理后的字段、资源与弹药精确一致 |
| 通讯反应与报告 | 条件化后的触发/限频/身份一致；随机规则独立核对支持集、原像数/概率、条件关联和抽取次序，样本落在范围内不能单独证明分布一致 |

- **运行：** agent 按[证据指南](../../../guides/original-evidence.md#agent-运行原版)优先自行取证。当前[模拟器内输入](../../../guides/runtime-measurement.md#模拟器内输入)不仅支持菜单/基地按键，还支持 BIOS 修饰位与声明的设备输入，因此转向、飞行、地图选点和停靠也先尝试以有界配方完成。Computer Use 的本机限制不能推出这些操作必须由用户完成。依据本次运行的对象位置导航，并在注入基地键前确认视角 6、子状态及停靠活动；不沿用另一运行的坐标，不重用 P3-05 已耗尽的尝试授权。本任务自己的测量方案规定有限预算与恢复条件。只有当前可用的合规途径均不能满足某个具体操作时，记录已尝试途径与准确障碍，再请用户做最小操作；全程不改写玩家位置、资源、任务状态或 RNG。
- **cycles 与参考钟：** 依 [B-006](../../../original/behavior/B-006-simulation-timing.md)与[计时指南](../../../guides/runtime-measurement.md#计时游戏时钟与参考钟)记录原版游戏时钟、模拟器参考时间、步长、调试暂停及媒体设置；不能用游戏时钟证明自身速率。入港/离港媒体用时为零的等价比较与启用过场的差异分开，通讯媒体则按 D-03 的实际模型取证。U-021 冻结前的结果仅适用于所测配置，冻结后须核对适用性，必要时重测。
- **样本不足与例外：** “没有触发”不等于“不可达”。达到有限尝试预算但样本不足时记为 blocked，不能自动改用 Node 通过。只有对明确分支提供代码与内容的不可达证明、列出影响的 AC 和恢复条件，并在 D-02/契约修订中获得针对该分支的批准，才可用静态证据加 Node 独立期望作为限定结论；列为未运行对照，不泛称整条规则已运行一致。不得据此豁免正常停靠、离港、服务与补给的主链。
- **独立性：** Node 单元测试的期望由原版规则独立推导，不调用被测实现；原版对照可由本地脚本调用 Core 的内部规则函数。
- **判定：** 只有全部样本满足判据才判为“一致”；不一致回到研究或实现，不放宽判据。

### 共享契约修订（P3-02、P3-04）

下表是共享契约的**修订方向**，随本 spec 批准的是方向与边界，不是最终字段。依 [P3-02 扩展规则](../02/spec.md#扩展规则)，完整形状、时序与公开语义须按 D-01 写入 P3-02 与 P3-04 的正文并取得明确批准。本 spec 的生成与审阅不修改这两份 spec 或已有 goal/subtask。

每批定稿必须逐字段写明具体类型、单位、整数/浮点范围、初值/null、唯一所有者、所有写入阶段、保存/清空/救援/新 run 的生命周期与序列化规则；事件明确发生阶段和最低快照，命令明确 outcome/reason 的优先级。尚未填写这些细节的概念表不能授权直接写共享类型，关卡可分批但不能由代码倒推契约。

### 持久化与兼容

本任务不引入存档、IndexedDB/localStorage 写入或缓存清理；两份菜单/服务 payload 已导入，不因增加消费者而递增转换器。若 D-03 证明必需元数据缺失，先修订 P3-03 的内容/转换器契约，按其规则使不兼容旧缓存不恢复并明确提示重新导入，不能使用旧包加猜测默认值。本 spec 不预先批准该变更。

replay 仍从调用者另供的内容重放，校验 rulesVersion、实际格式版本、完整内容身份和 setupHash；旧规则录制在执行前拒绝，不迁移、不嵌入导入 payload。快照仍只读、不提供恢复。重试以新世界重建通讯/停靠状态，同时使旧 owner/run/transition 的所有回调失效；不清除玩家的资源缓存。

## 技术决定

1. **运行中衔接不计时：** 接纳 P3-02 技术决定 2，只省略 G-02 媒体用时。Core 完成整个 tick 后 Runtime 保持，停靠倒计时和服务仍推进规则时间；用每次衔接身份而非仅 runId 保证完成一次。replay 不记录宿主等待，不宣称两版全部时序天然等价。
2. **G-03 先保留玩法语义（D-03）：** 不预选“语音包没打开”来省事。推荐按基准已确认的消息选择、逻辑忙闲、回调时刻及 RNG 次序建立纯 Core 模型，媒体本身可缺。只有证实原版有受支持的无媒体路径，且停靠回调、必要信息、时序和抽取的变化已逐项核对并获准，才可采用该替代路径；文件打开失败不自动等价于关闭媒体设置。需要时长/映射等元数据时走 P3-03 契约变更，证据不足则阻塞，不用“立即完成”或任意显示秒数填空。
3. **菜单输入沿用现有命令：** 所选任务的菜单只用数字与 `x`，因此用 `select-number` 与 `communications close` 表达，不加按键级命令；创建时拒绝会生成字母键的任务。
4. **菜单优先级在 Core：** 通讯判定先于其他飞行命令，输入层不读菜单状态（P3-05 规则 5）。
5. **规则数据经 `createWorld` 进入：** 默认复用 P3-03 已导入的两种 payload，受 setupHash 绑定；D-03 若证明还缺必需元数据，必须先走上游契约修订，不能用默认值绕过。
6. **跨 tick 状态由本任务拥有：** 无线电队列、限频计时、子状态与基地内部状态都是具名的快照状态；P3-07 的调用点以静态调用接入，不用 Runtime 订阅者回写。
7. **子状态的共享方式：** 本任务建立任务内子状态的类型与 0、3、4、5 的规则，P3-11 在同一字段上扩展。理由：P3-11 依赖 P3-10，先建立的一方定义可扩展的封闭联合。
8. **僚机命令只交付投递：** 命令码写入僚机，效果归 P3-08，不建空的效果处理。
9. **完全修理是共享纯规则：** `0x39820` 由本任务实现，救援、停靠、离港与僚机到达复用同一函数。
10. **G-05 为键盘操作的 React 项目页面：** 只读 projection，只提交已绑定的基地命令；项目名称按选择值，沿用 D6 的置信度；不复刻原版画面、不硬编码原文，合法导入的名称仍由内容引用解析。
11. **两层对照：** 沿用局部核对加默认步长连续运行的方法，判据由本任务预实验推导，不直接复制 P3-07 的零残差结论；预算耗尽不自动豁免原版样本。
12. **种类 `0x4000` 的单一所有者：** 推荐 P3-08 统一构造及其两个调用者，须先同步并批准 P3-02 与接收任务契约；本草案不能取消现行 P3-10 责任。
13. **先定方向，后定细节：** 本 spec 批准方向、研究范围与验收要求；研究之后才能确定的细节，按[实施关卡](#实施关卡)在依赖它的工作开始之前定稿批准。

上述方案依据用户在生成与本轮审阅的授权（“如果有需要我回答的问题，就直接按你最推荐的答案”）写入草案。推荐方案已直接选择，不为这些选择再次提问；这不等于完整 spec、未来未知形状或其他任务契约已批准，也不能代替原版证据。未改变总计划的冻结决定；若需要突破冻结边界，先完成 ADR/总计划修订，本轮不修改它们。

### D-03 定稿（已批准）

> **状态：已批准（2026-10-14）。** 由 goal 子任务 07 起草，依据用户对关卡推荐方案的授权批准（见[审批](#审批)）。事实依据见 executable 的 [RQ1–RQ10](../../../original/formats/executable.md#base-replies-radio-queue-and-incoming-messages-p3-1002) 与 [RX1–RX10](../../../original/formats/executable.md#communications-reactions-and-wingman-reports-p3-1003)。

**1. 选定模型：基准设置下的逻辑模型。** 语音档案已打开，GAMEHIRES 为真（COMMFACE，HI）。Core 不播放媒体，但按原版的消息选择、通道忙闲、可见与结束时刻、回调和抽取次序推进。被排除的方案：

- **原版无媒体路径：** 不存在。原版没有关闭头像或语音的设置；档案打不开时没有回复，每次停靠请求在 0x780 后超时，正常请求路径无法停靠（RQ7，已确认，代码）。技术决定 2 的替代路径因此不成立。
- **取出即完成或立即回调：** 与基准运行的时间链不符（RQ5、RQ6，已确认，运行）。
- **同时支持 LO（COMMFAC2）：** 本任务不支持。基准运行只覆盖 HI；LO 的部分消息时长不同，而且停靠中、显示模式 1 时有不调用回调的纯文字分支（RQ5）。这是有据偏差，以后另行修订再支持。

**2. 状态（`communications` 分区，进入快照与 replay）：**

- **无线电队列：** 有序列表。每项为 {消息身份 {表 20011 | 20019 | 20985 | 20983，头像 0–4 或无，序号}，到期 u32 时钟，回调 `none` | `docking-reply`，表现标记（可选，供 P3-14 的音乐提示）}。所有入队的延迟都是 0，到期等于入队 tick 的取样。停靠回复插在队首；其他项插在第一个到期（i32 有符号比较）更大的项之前，到期相等时先进先出（RQ3）。
- **来电通道：** `idle` | `loading`（消息、回调、就绪 tick）| `playing`（消息、回调、开始 u32、各帧时长 i32，单位 1/8 秒）。
- **来电保存页：** 与菜单打开时保存的页、Warp 保存页各自独立（RQ8）。
- **头像：** 每个对象有头像（`unassigned` 或 0 … n − 1）；每个任务有两组占用标志（机体 3 个、基地 5 个），任务构建时清零（RQ4）。

**3. 每 tick 的时序：**

1. **取出（`communications-reply` 阶段，对应原版派发器第 2 步）：** 只看队首。取出条件：sample ≥ 到期（u32）、通道为 `idle`、流程状态 3 且子状态 ≠ 2。取出后移出队首，通道变为 `loading`，就绪 tick 为下一 tick。每 tick 至多取出一条，取出时不执行回调。
2. **通讯呈现子步（新增，排在本 tick 全部规则阶段之后，取代原版渲染末尾的 `0x4e308`/`0x4e5a0`，是纯 Core 规则）：**
   - `loading` 到达就绪 tick 时变为 `playing`，开始为本 tick 的取样。视角不是 Warp 时保存当前页并设为页 5，同时发出“来电可见”事件。**载入延迟固定为一 tick。** 原版的延迟取决于 IO，基准两次观察都是一趟渲染（RQ5，高概率只适用于基准）；固定值记为有据偏差。
   - `playing` 时按 e = ((sample − 开始) × 8 mod 2³²) >> 6 依次消耗各帧（e ≥ 帧时长，有符号比较）。全部消耗后通道回到 `idle`；页仍为 5 时恢复保存页；然后执行回调，并发出“来电结束”事件。
   - 回调 `docking-reply`：流程状态为 3 且子状态为 3 时，子状态变为 4，到期为本 tick 取样 + 0x200。不核对回复者，与原版相同：迟到或旧请求的回复推进当前等待（DK1）。回调结果在下一 tick 的 `mission-flow` 才被读取，对应原版的“下一趟”。
   - **尾随警告：** 原版在渲染路径（RX5）中执行。Core 在本子步按原版条件执行：视角模式为 1、6、8 或 0xC–0x12；计时 < sample（u32 严格）时检查。检查结果或导弹警告结果（按 executable 中 `0x4f000` 的条件）非 0 时，计时重设为 sample + 0x40，否则为 sample + 0x80。检查通过后按 `0x38c30` 的条件入队，不抽取。AI 字节的含义归 P3-08；P3-08 交付之前，用其已发布的只读状态，或按 D-01 的接口判定。
3. **清空（对应原版 `0x2cd20`）：** 清空队列，停止来电（页为 5 时恢复保存页），`loading` 中的载入取消且不执行回调，页设为 0。调用者包括 P3-10 停靠等待在子状态 3/4 中因对象失效的取消，以及流程切换、被毁、任务开始（P3-11 共用同一入口）。停靠等待超时不清空（RQ3、DK1）。
4. **不建模的分支：** 停靠中的纯文字分支只在 GAMEHIRES 为假时出现，所选模型中不可达。页 5 没有条目时（例如在页 5 上用 `c` 打开菜单后关闭），Core 直接把页设为 0，等价于原版连续三次绘制失败后的结果，只省略中间的处理调用，只影响表现（RQ8）。

**4. 消息身份与查找：** Core 用（表、头像、序号）表示消息。查找成功的条件是：头像 ≥ 0、序号小于子表长度、条目非 0；档案在模型中恒为已打开。反应所需的名称序号（COMM TABL 2001/2011 中的位置，RX1）在 `createWorld` 时由导入的名单与任务对象名逐字节比较得出，并受 setupHash 绑定。

**5. 抽取（全部保留，使用世界 RNG，次序与原版相同）：**

| 抽取 | 条件 | 次数 | 理由 |
|---|---|---|---|
| 头像分配 `0x3c91c` | 每个基地或 `0x87c` 对象第一次说话，在查找之前 | 1（该类头像用完时 2） | 与媒体无关（RX9 #4） |
| `0x3c208` 第二分支 rand % 4 | 名称在 2001/2011 中且第一次查找成功 | 1 | 依赖档案；模型固定档案已打开，按基准保留（RX9 #1） |

| 入港背景 rand % 3（`0x4f480`） | 每次入港 | 1 | 结果属于表现而丢弃，但共用生成器，必须保留抽取（DK2） |
| 基地船体步骤 | 每步 | 1 | 属于 Q-08，列在此处只为完整；实现归 17 |

导入的内容能否实际播放媒体，不改变上述任何抽取或时序：“缺少媒体”不等于原版的“档案未打开”。

**6. 内容是否足够：不足。** 需要 [P3-03](../03/spec.md) 修订 2（已随本节批准，见其 S-18、AC-22 与“修订 2”记录）。要点：

- **来源白名单：** 增加 `MAIN/COMMFACE.NOB`（来源指纹随之改变，用户须重新导入），只读取结构与时长；不读取 `COMMFAC2.NOB`。

## 验证策略

- **单元/契约测试：** Vitest，与源码相邻。用 [rule-data.test-support.ts](../../../../src/content/rule-data/rule-data.test-support.ts) 与 Core 的世界辅助构造合成菜单、服务项与任务（基地放在玩家附近，以便测试停靠）。覆盖上列规则、失败与边界、事件快照、序列化与阶段集成；期望独立推导。先跑受影响的测试文件，再运行 `pnpm exec vitest run src/core src/app src/ui tools/engineering-boundaries.test.ts`。
- **Replay/一致性：** 同一配置、规范内容、种子与有序输入在同一运行时重放一致；含停靠与离港的录制与占位行为无关。完整闭环的 replay 归 P3-15。
- **浏览器验证：** 本机 Chrome 上使用现有合成包辅助和独立 E2E runner 按 AC-14 验证，只有测试侧可读诊断，不新增生产状态修改 API。通讯菜单的 Classic MFD 像素归 P3-13；本任务自己的占位/G-05 必须检查实际 DOM、布局、焦点与规则结果。合成键不作为 OS 快捷键拦截证据，本任务未改变的 P3-05 实机绑定不重复宣称已重新验证。
- **实机/原版对照：** 静态证据与有界配方由 agent 负责；运行先尝试声明的键盘、修饰位和设备输入，而不是默认要求用户飞行。复用既有证据须核实身份、配置、采样点与本 AC 适用性；P3-05 成功进入基地不替代本任务的服务/补给速率样本。当前合规途径无法满足特定操作时才记录障碍并请求最小帮助；必需样本仍缺则 blocked。
- **工程检查：** `pnpm check`；`pnpm check:compliance`；改动 `tools/baseline/` 时运行其 unittest；文档的链接与元数据检查。仅生成或审阅本 spec 时，只检查文档与路由。

## 风险与恢复

风险等级：中高。共享契约（P3-02、P3-04）、相邻任务状态、媒体影响规则的边界和原版取样可达性是主要风险；默认没有持久化迁移。

- **来电时序依赖表现：** D-03 先固定逻辑忙闲、回调与抽取；缺媒体不是立即完成或少抽随机数的授权。数据不足须修订内容契约，不能以 G-03 包装未批准的规则差异。
- **与 P3-08、P3-11 的状态交叉：** 子状态、队列、友伤累计与完全修理被多方读写。缓解：本任务建立可扩展的封闭类型与静态调用入口，接口表写明所有者；P3-11 扩展子状态时按扩展规则修订，不改写本任务已批准的语义。
- **Runtime 保持与迟到回调：** 帧截断和同 run 多次占位可能误取消已执行命令或提前结束新占位。D-01 同步 P3-04，逐次凭证、多 tick 帧、事件消费者失败与控制竞态均回归，错误不得恢复模拟。
- **原版运行取样难：** 先用当前运行的读数规划配方；预算耗尽记阻塞，不把未观察当不可达。分支静态验收例外须有证明并另行批准，正常停靠和服务主链不能豁免。
- **范围空洞与蔓延：** 种类 `0x4000` 的责任须获批同步后才移交；僚机 AI、地图和救援的集成按依赖边界交接。数字键范围来自经过核对的切片闭包，不为后期通用菜单预建引擎。
- **恢复：** 回退自有实现时连同受影响的消费者（P3-04 会话、UI 页面）协调回退，保留契约修订的历史记录；不迁移旧 replay、不清理玩家缓存。代码提交只在后续获授权的执行阶段进行。
