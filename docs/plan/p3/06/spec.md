# P3-06：飞行运动与速度控制 — Spec

## 问题与目标

[P3-02](../02/spec.md) 交付了正式 Core（[Core 模块说明](../../../engineering/modules/core.md#正式-core)）：实体有位置与姿态，`TickInput` 接受 `pitch`/`yaw`/`roll` 三个轴与 `speed`、`select-number` 等命令。但运动相关的部分还没有实现：

- 流水线的 `movement`、`parked-update` 与 `area-check` 三个阶段为空，实体实例化后永不移动。
- 每个命令都得到 `rejected`/`not-implemented`，轴输入没有效果。
- 实体没有移动块、速度或油门，`flight` 分区未就绪。
- 活动区域只在实例化时判定一次：玩家移动后，对象既不停放也不恢复；停放对象不更新，也不会离开世界。
- 原版运动模型（U-008 的运动部分）仍未确认，以下都只有线索：
  - 机型记录 +0xAC–+0xC4 的含义；
  - 速度如何趋向目标，转向如何随操纵变化；
  - 油门表与最高速度；
  - 仅用键盘时操纵值如何产生。

本任务研究并在 Core 中实现原版的飞行运动与速度控制。它覆盖 P3-01 [规则对照目录](../01/spec.md#规则对照目录)的 R-04（飞行运动与速度操作）与 R-05（世界边界与起飞初始状态），即[闭环步骤](../01/spec.md#闭环步骤) L-03 的规则部分与 L-02 的起飞初始状态。

完成后可观察到：

- **玩家运动：** 在 Node 中逐 tick 推进世界时，玩家按轴输入转向，按速度命令改变油门与目标速度；速度按机型速率趋向目标，位置沿机头方向前进。
- **非玩家飞行器：** 按同一积分规则运动。它们的操纵由 P3-08 的 AI 提供，在此之前保持实例化时的状态。
- **活动区域：** 玩家移动后，对象按原版规则停放或恢复。停放对象按原版节奏更新，离开世界时移除并产生领域事件。
- **projection：** `flight` 分区的运动组就绪，给出玩家的位置、姿态、当前速度、指令速度、最高速度与速度辅助状态。
- **对照：** 分别核对同前态、同步长下的规则计算，以及生产固定步长下的连续运动、速度控制与转向。按事先批准的判据给出 R-04、R-05 的结论；逐步公式相同不能代替持续驾驶的保真验收。
- **原版事实：** 写入 `docs/original/`，U-008 的运动部分随结论更新。

阶段范围依据[总计划 §12](../../master-plan.md#12-开发阶段与验收条件)，任务导航见[阶段索引](../tasks.md#p3-06-飞行运动与速度控制)。生成、审阅或批准本 spec 都不会自动启动实现。

| 速度命令或飞行上下文的 `select-number` 在原版处理该键的上下文中（只有飞行上下文） | `accepted`，按 M-04 得到本条命令的油门，经操纵应用写入指令速度；`select-number` n 等同原版的 Shift+n 档位；写入后数值未变、或移动块锁定而被丢弃，也记为 `accepted` | 不适用 |
| 速度命令在原版不处理该键的上下文中（Warp、基地、地图） | 状态不变 | `ignored`，原因 `wrong-context` |
| 玩家实体不存在、已被毁、尚未活动或正在移除 | 该命令不改变控制状态，其他规则照常推进 | `ignored`，原因 `player-unavailable`；不以 DOS 轮询尚未到期为拒绝理由 |
| `match-target`（或其别名）时没有有效目标，或目标没有移动块 | 状态不变 | `ignored`，原因 `no-target` |
| 可操纵状态中的 `toggle-auto-match` | 切换唯一的速度辅助开关（与难度辅助是同一开关，M-05），发出 `speed-assist-toggled`；开启时到期时刻归零、清除“已匹配” | 门禁与普通速度命令一致 |
| 速度辅助开启，有效目标在辅助种类内、距离不超过阈值且已到期 | 匹配速度，从本次时钟重新计时（不追赶），匹配成功时发出 `speed-matched`（`origin: 'assist'`） | 不适用 |
| 速度辅助开启、曾经匹配，之后玩家目标为空或失效 | 投递最大油门的操纵请求，清除“已匹配”，发出 `speed-assist-released` | 不适用 |
| Core 内部规则函数收到已校验的步长 | 按同一规则计算；Node 可单独验证零步长，但公开 `World.step()` 仍每次推进已配置的正步长 | 超出已批准支持域时显式拒绝，不提供任意补时或可变步长的生产入口 |
| 本 tick 请求处理中实例化的实体 | 本 tick 不更新、不运动、不参与碰撞；仍可由既有读模型呈现，不泛化为“之后所有阶段均不可见” | 不适用 |
| 轴从非零变为零，或进入地图、基地 | 当前 tick 应用零偏转，停止旧的手动转向；地图、基地中有效手动轴为零（有意差异，原版保持旧转向）；时钟、既有速度与独立的规则效果继续推进 | 被屏蔽的飞行命令得到 `ignored`/`wrong-context` |
| 活动对象越过活动区域边界 | 按 Q-08 的时机切换停放；停放时释放移动块，并只在玩家目标恰为该对象时清除它；种类位 `0x1f00000` 的对象离区直接待移除，不停放、不发事件 | 不适用 |
| 停放对象恢复活动 | 按原版重建移动块（模式 0、满油门、初速恰为当前最高速度） | 不适用 |
| 停放对象在停放更新的到达分支中位于内缩 100 的世界矩形之外（僚机除外） | 写入待移除并发出一次 `object-left-world`，按 Q-08 的时机移除 | 不适用 |
| 停放对象的行进、Warp 跳跃或编队跟随写入新位置 | 位置非连续改变，放置序号加 1；不发事件、不改活动 | 不适用 |
| 活动对象（含玩家）越出世界矩形 | 状态不变：原版没有夹取、移动或移除（M-07）；只适用下一行的坐标域故障规则 | 不适用 |
| 运动结果非有限，或超出支持的数值域 | 世界进入故障状态，不发布部分结果 | `CoreFaultError`（`invariant-violated`） |
| craft-info 缺失、结构错误或不满足 Core 的语义要求 | 不创建世界 | 读取器的 `ContentContractError`，或 `CoreInputError` |
| replay 的 setupHash 与包含 craft-info 的初始数据不符 | 不执行 | `CoreInputError` |

**结果的含义：** “状态不变”指被拒绝动作不改变其控制/目标状态，不代表整个 tick 的运动、时钟或自动规则被冻结。每个合法命令恰有一个带原 `commandIndex` 的结果；`accepted` 的 reason 为 null。尚无实现的其他命令仍为 `rejected`/`not-implemented`，不能误报为原版的忽略行为。

### 运动阶段与积分

- **阶段：** `movement`（第 8 阶段）按 `0x221fc` 实现（[运动阶段](../../../original/formats/executable.md#movement-stage-and-integration-p3-0601)）：
  - 用实时种类遍历（全部种类，玩家最先）访问对象。筛选：活动不是停放（活动与停靠都参与），且状态为被毁源（4）或活动及以上（7、8）。被毁源保留移动块，按最后的角速率与速度继续运动；本 tick 新生的实体（状态为新建或表现就绪）不运动。
  - 每个通过筛选的对象必有移动块；缺少移动块为 Core 故障（原版没有空值检查）。
  - 按移动块的模式分派：`craft`（原版模式 0）→ 飞行器积分 `0x222f0`；`warp`（模式 3）→ Warp 积分 `0x22600`。P3-06 交付两者的规则函数与分派；模式 3 只由玩家的 Warp 开始写入，触发归 P3-09，P3-06 用内部状态测试。
  - 弹丸、碎片与地图标记的模式（原版 1、2、4）由 P3-07、P3-09 在同一分派中加入，加入前分派表中没有它们的变体（类型上不可构造）。原版在模式 1 内调用的命中测试是否必须留在运动循环中，由 P3-07 判定；需要改变阶段表时修订 P3-02。
  - 模式 0、3 的积分不读其他对象，遍历次序只影响 P3-07 的命中测试。
- **移动块：** 实体上可为空的纯数据记录，对应原版对象 +8；封闭形状、单位、初值与生命周期见[检查点 A 定稿的状态与契约](#检查点-a-定稿的状态与契约)。
  - 停放的实体没有移动块；活动实体在实例化或恢复活动时获得移动块（`0x2c3b0`，满油门）；停放或移除时释放。救援（P3-11）与种类 `0x4000`（P3-08）经 `0x218e8` 按旧速度比重建，由各自任务调用 P3-06 交付的重建规则函数。
- **位姿权威：** 实体的 `position` 与 `orientation` 是唯一位姿。M-01 已确认：模式 0、3 直接改对象自身的位姿，原版没有逐帧副本或写回；`0x21794` 只在（重）建移动块时应用参数记录，不是帧内步骤。
- **积分：**
  - **公式与次序：** 按 M-01 确认的原版公式与次序（冲量位移与衰减 → 用更新前速度前进 → 未到达时趋向指令速度、越过时按位取目标并置到达 → 速度比 → 转向因子 → 依次绕第 1、2、3 行旋转，含定时旋转、+0xC4 耦合与到期），以本 tick 的步长（`clockUnitsPerTick` ÷ 64 秒）调用规则函数。只在 Core 内部的有界校准入口中使用原版记录的步长与前态；不扩展生产 `World` 的写入口或快照恢复能力。
  - **不钳制最高速度：** 积分从不读实体的 `maximumSpeed`。上限降低后当前速度可以暂时高于上限，按减速率下降（M-01、M-04）。
  - **数值：** 中间运算用双精度，f32 写回用 `Math.fround`，浮点转整数向零截断；写回点按 [运动路径的数值](../../../original/formats/executable.md#numbers-on-the-movement-path-p3-0601)逐一实现。sin、cos 用 `Math.sin`/`Math.cos` 后写回 f32，不查表、不定点、不重新归一化行向量（原版也不）。不用人为调整 sin/cos 或归一化输出掩盖差异。域外、非有限结果为故障；不能把仅对放置证明的坐标域直接当作飞行空间上限。
  - **定时旋转的时间：** 原版以 f32 的绝对取样秒判定到期；Core 以任务时钟换算的 f32 秒（时钟 ÷ 64）判定。两者原点不同，到期帧不能逐位重现（已知差异，计入检查点 B 的误差预算）。
- **其他任务写入的分支：** M-01/M-02 证实冲量、定时旋转（P3-07 的导弹爆炸与两处碰撞响应写入）、操纵锁定（P3-07 的能量耗尽写入，基地修理清除）与扰动（P3-07 的受损写入，修理与救援清除）在切片中可达（高概率），由 P3-06 在积分与操纵应用中实现其消费者，写入者归各自任务；Node 测试经 Core 内部状态覆盖这些分支。
- **AI 交付前：** 在 P3-08 交付之前，非玩家飞行器按实例化时的移动块运动（沿第三行直线前进）。这是分阶段接入，不是 AI 的替代，不能写成 AI 行为已对照。
- **驾驶舱的第三行角速率（交接）：** 原版驾驶舱表现 `0x46fe0` 每帧读取 `0x21cf8` 给出的稳定或耦合的第三行角速率（不含定时分量）。运动 projection 不含这一量；是否需要由 P3-12/P3-13 决定，需要时按 P3-02 的扩展规则修订分区。

### 操纵

原版没有键盘操纵：俯仰、偏航、横滚只来自游戏端口摇杆，经设备路径进入整数操纵路径（M-03，[飞行操纵](../../../original/formats/executable.md#flight-controls-and-rotation-p3-0602)）。总计划首版输入一段的冻结决定不变（首版只支持键鼠，键盘负责飞行、横滚须能用键盘完成，Core 预留 −1…1 模拟轴），其风险行已预见原版依赖摇杆的情形。P3-06 只定 Core 轴的语义：**项目轴作为原版整数路径上的数字摇杆**；物理操纵键由 P3-05 选取，不与原版视角键冲突。

- **项目轴到原版操纵值（检查点 A 定稿）：**
  - 对应：`pitch` → 第 1 轴（绕第 1 行，俯仰），`yaw` → 第 2 轴（绕第 2 行，偏航），`roll` → 第 3 轴（绕第 3 行，横滚）；正方向即原版设备的正偏转（抬头、机头右转、驾驶员视角顺时针横滚；代码链已确认，画面含义高概率，由 17 的运行读数核对）。这对应 Flight 摇杆模式（Arcade 模式会对俯仰取反）。
  - 换算：偏转 = 向零截断（轴值 × 设备路径的满偏刻度），在双精度中计算；±1 精确对应正负满偏，0 对应 0（关闭该轴），绝对值不足一个刻度的非零轴值也得 0。向零截断与原版浮点转整数的约定一致，结果对正负对称。
  - 偏航与横滚是两个独立的轴，可同时非零；原版设备的 X 轴只能送往偏航或横滚之一（Ctrl 或 2 号键切换），二者同时非零只是项目输入，只由 Node 合成测试覆盖。
  - 灵敏度：固定为原版 Medium 档的灵敏度表（启动时由代码计算的表，代码规则），绑定到规则版本；改变档位须递增 rulesVersion。飞行中切换（F11）不提供（G-10）。
- **只在变化时应用（检查点 A 定稿）：** 玩家控制状态保存每轴的上次读数（原版 `0x1b2470` 的对应物，初值 0）。每个成功 tick，玩家可用时，计算每轴的有效偏转并与上次读数比较：只有不同的轴进入操纵请求，并更新上次读数；相同的轴不应用（原版只在轴值变化时投递，扰动时每条被接受的消息抽 3 次随机数，逐 tick 重复应用会改变随机数消耗与扰动后的速率）。锁定使请求在应用时被丢弃，但上次读数照常更新，与原版一致。这是变化检测，不是跨 tick 的按住缓存：每 tick 仍消费本次轴快照。
- **有效手动轴与上下文：** 视角模式属于地图（8）或基地（6）上下文时，有效偏转为 0：进入时按变化检测应用零偏转，停止旧的手动转向。这是有意差异（原版在地图与基地中不读设备，已应用的转向继续），计入 R-04c。其他上下文（飞行与 Warp）采用本 tick 的轴，与原版在这些视角模式中读设备一致。地图、基地与 Warp 的模式切换由 P3-09/P3-10 实现；同 tick 的上下文切换须影响后续命令和本 tick 的有效轴。
- **整数路径（玩家，`0x21dd0`）：** 在原版处理消息 0x20000 的位置应用，即 Core 的请求处理阶段，按投递次序；为此 Core 新增内部请求类型 `control`，不在对象更新中直接写移动块（形状见[检查点 A 定稿的状态与契约](#检查点-a-定稿的状态与契约)）。
  - 门禁依次为：移动块存在、机型记录存在、未锁定；否则无效果也不抽随机数。扰动非零时先抽 3 次随机数（每条被接受的消息，包括只带油门的消息），再读字段。
  - 油门非“不变”时：指令速度 = F(油门表项 × 实体 `maximumSpeed`)，清到达标志。油门表索引按原版由油门值得出；**索引超出表的范围时钳到表内**（项目规则：原版在上限降低后的 `−` 可越出表尾读取未定义内存，检查点 A 定为钳制，已知差异）。
  - 每轴：“不变”不写；0 清该轴启用标志（速率保留但不施加）；其他偏转按原版取负、可叠加扰动后钳位，经灵敏度表乘机型角速率（+0xAC、+0xB4、+0xB0 分别对应第 1、2、3 轴）写入速率并置启用标志。
  - 请求保存投递时的值，不引用之后被改写的控制状态；同 tick 多次增减、匹配与置零的结果可独立断言（见[速度与油门](#速度与油门)）。
- **浮点路径（`0x21fd8`）：** 作为规则函数交付（含扰动时的 5 次抽取与 `0x56b8c` 的随机方向），语义按 M-02。它不只服务于自动驾驶：P3-08 的 AI 飞行器、P3-07 的导弹回调（`0x2ac10`）与种类 `0x4000` 的回调都调用它，因此 G-09 不取消它。P3-06 不投递浮点操纵请求；请求类型由第一个调用者（P3-08 或 P3-07）按 P3-02 的扩展规则加入。
- **读取时刻：** 采用 P3-02 已批准的游戏动作边界：每个成功 tick 消费本次轴快照，不在 Core 新建 DOS 设备轮询计时器或跨 tick 的手动按住缓存。原版设备的到期间隔与项目 tick 采样的差异由 R-04c 量化，不能以键位一致代替操控一致。
- **清键：** 手动轴归零在当前 tick 停止旧的手动转向分量，不等待设备轮询到期；这不清除独立的受击冲量、定时旋转、速度辅助开关、指令速度或其他已接受规则。
- **Runtime 边界：** 暂停、页面隐藏与 G-02 占位不调用 step，结束不补计时间；失焦、退出 Pointer Lock 等由 P3-04/P3-05 清除外部输入，随后送入中立快照，中立快照按变化检测应用零偏转。Core 没有旧手动输入可在恢复后重新激活，也不暴露 DOM 或宿主时间。浏览器输入重复与物理键绑定仍归 P3-05，不要求适配器仿真 DOS 缓冲的丢键。

### 速度与油门

- **油门不是持久状态（检查点 A 定稿）：** 原版控制块 +0x1C 是每帧的待发送值，发送后复位；持久量是移动块的指令速度（M-04，[油门、最高速度与速度匹配](../../../original/formats/executable.md#throttle-maximum-speed-and-speed-matching-p3-0603)）。Core 不保存油门；每条写油门的命令得到一个整数油门值，由它投递的 `control` 请求携带。
  - 写油门的命令只在飞行上下文处理（原版只有 `0x264a0` 处理油门键；Warp、基地、地图上下文都不处理，命令得 `ignored`/`wrong-context`）：
    - `increase`：读回值加固定步长，不超过满油门；`decrease`：读回值减同一步长，不低于 0；
    - `zero`：0（原版 `\`）；`maximum`：满油门（原版 Backspace）；
    - `select-number` n（1–9）：原版 Shift+n 的第 n 个固定档位（Shift+1 等同归零；原版 Shift+0 等同 Backspace，项目由 `maximum` 表达）。原版未按 Shift 的数字在飞行中无作用；物理绑定由 P3-05 决定。
  - **读回：** 原版 `0x21ca8` 由“指令速度 ÷ 当前最高速度”反算油门（向零截断；没有移动块或最高速度不为正时为 0）。匹配之后指令速度任意，`increase`/`decrease` 从匹配后的比例出发。读回的基准是玩家更新开始时的指令速度，包括本 tick 速度辅助的直接写入，不包括尚未应用的辅助恢复请求（与原版一致：按键读回在消息循环之前）。
  - **同 tick 多条速度命令（项目规则）：** 原版每次键盘轮询至多处理一个键；Core 每 tick 按数组顺序处理全部命令。后一条命令的读回计入本 tick 前序速度命令的效果，按与请求应用相同的纯函数推算（`control` 请求：F(油门表项 × 最高速度)，锁定时它在应用时被丢弃，推算值不变；匹配请求：匹配值，不受锁定影响）。因此“增、增”等于原版相继两帧各按一次。原版 `+`/`−` 与待发送值的比较在实际中从不成立（高概率），Core 不实现。
  - **请求合并：** 原版每帧至多发送一条操纵消息（待发送油门与变化的轴）。Core 中，若本 tick 由命令投递的最后一个请求是 `control` 请求，轴的变化并入该请求；否则另投一个只带轴的 `control` 请求。由此每 tick 至多一条速度命令时，请求条数与原版消息条数相同。
  - 通讯菜单打开时，`select-number` 归菜单，由 P3-10 加入优先级。原版档位键在菜单打开时仍有效（除非菜单占用该码），这是已知差异。
  - `confirm-selection` 在普通飞行且无通讯/基地菜单占用时，与 `speed/match-target` 进入同一规则（原版 Enter）；保留原命令类型与索引，只发一个结果。`navigate-selection` 不猜成增减速度。`select-number` 与 `confirm-selection` 在 Warp 上下文得 `ignored`/`wrong-context`（原版 Warp 上下文不处理这些码）；在基地、地图与通讯上下文由其负责规则处理，尚未接入时明确 `not-implemented`。
- **油门表：** 启动时由代码计算的线性表（M-04），按[技术决定 11](#技术决定)作为代码规则在 Core 中独立实现，不需要导入。满油门的表项使指令速度恰等于最高速度。
- **最高速度（`0x30e0c`）：** 作为纯函数实现，在实例化扩展点的 `0x3060c` 位置写入（不抽取随机数）。
  - `maximumSpeed` 属于实体的飞行状态，不藏在可空移动块中；停放实体仍需它。非玩家取内容基准（机型 +0xB8）；玩家在能量量低于阈值时按能量量与机型 +0x88 的整数运算得出，否则取基准，再按子系统两位字段 2 乘系数。内容基准与规则计算的当前上限分开。
  - **重算时机（M-04）：** 只在实例化、救援、导弹与种类 `0x4000` 的构造（各经 `0x3060c`），以及能量菜单改变分配等级时。受损与基地修理不重算，新系数要到下一次重算才生效。P3-06 只在实例化时写入；能量量、阈值、分配等级与两位字段归 P3-07，P3-06 的纯函数在实例化时用代码固定的初始等级与清零的两位字段计算，不保存这些能量状态。
  - **上限降低后（`0x21d88`）：** 作为规则函数交付，由重算者调用：只在“当前速度 ÷ 新上限”严格大于 1 时把指令速度设为新上限并清到达标志；当前速度不被钳制。
  - 玩家分支读取的能量量与子系统状态属于 P3-07（R-09）。P3-07 接入前，`speedLimitStatus` 为 `'initial-only'`，不在缺少实时数据时声称动态最高速度已就绪。
  - P3-07 接入时使用同一纯函数和权威实时状态，按上述时序重算，并把 `speedLimitStatus` 改为 `'live'`；已经集成时不得回退到初值。初值、各损伤状态、资源不足与恢复、上限变化后的指令速度均需契约测试；完整 R-04 的动态分支须在集成后对照，本任务未取得时保留未完成项。
- **初始移动块（`0x2c3b0`）：** 模式 `craft`、满油门：当前速度与指令速度都恰等于实体当时的 `maximumSpeed`，到达标志置位，速度比 = F(最高速度 ÷ 机型 +0xB8)（基准不为正时为 0），其余字段为零或空。实例化为活动与恢复活动时都按此创建；玩家的姿态另取单位矩阵（P3-02 已实现）。
- **按住 `+`/`−` 的节奏：** P3-05 决定物理按住如何产生动作，P3-06 每 tick 处理收到的每个命令，不以 DOS 键盘轮询到期与否丢弃它。规则本身的冷却或状态门禁只按已确认依据执行。

### 匹配速度与速度辅助

- **玩家目标引用：** 玩家状态中的目标实体 ID 或 null，对应原版玩家对象 +0x8C（检查点 A 定稿）。
  - **初值为 null，有代码证据（M-09）：** 实例化不写 +0x8C（`0x68050` 写的是 AI 目标 +0x90），分配器把它清零。首次可操纵更新末尾的自动选择（最近的敌方模式对象，`0x2799c`/`0x63858`）属于 P3-07；首次可操纵更新之后的目标因此依赖 P3-07，不依赖 P3-08。
  - **生命周期（P3-06）：** 玩家更新开始时，不能解析的目标 ID 清为 null（原版丢弃失效句柄）；目标停放时由停放切换清除（只清玩家目标恰为该对象的情形）；玩家实体移除时随玩家引用一起清除。玩家 Warp 开始时清除归 P3-09。被移除的 ID 不能解析为新实体。待移除与被毁源的目标在移除前仍有效。
  - 选择与切换目标由 P3-07 写入。Core 测试经内部状态设置目标，不开放生产写入口。
- **手动匹配（`match-target` 与飞行中的 `confirm-selection`）：** 原版 Enter 只要求玩家目标非空，没有种类、距离、计时或开关条件，不显示消息。
  - 判定：目标为空，或目标没有移动块 → `ignored`/`no-target`（原版静默无作用）；否则 `accepted`，投递内部 `match-speed` 请求（原版消息 0x80000 的对应物，与 AI 匹配同一例程 `0x21adc`）。
  - 应用：目标的当前速度钳制到 [0, 玩家当前最高速度] 后写入玩家移动块：模式 `craft` 时为指令速度并清到达标志，其他模式时为当前速度。成功后发出 `speed-matched`（`origin: 'command'`）。锁定不阻止匹配（原版 `0x21adc` 不检查锁定）。
  - 原版 Enter 在按键处理中直接写移动块；Core 改经请求，使同 tick 的多条速度命令保持数组顺序。每 tick 至多一条速度命令时结果与原版相同，因为对象更新与请求处理之间没有 P3-06 的规则读取玩家的指令速度（P3-07、P3-08 在此区间加入读取它的规则时须复核）。
- **速度辅助（检查点 A 定稿）：** `toggle-auto-match`（原版 Ctrl+Enter）与难度辅助（[路径 8](../../../original/formats/scenario.md#difficulty-readers-p3-01)）是**同一个开关**；手动匹配是独立的、无状态的。
  - **状态：** 开关（初值 = 战役组是否为 0）、到期时刻（初值 0，立即到期）、“已匹配”标志（初值 false）。不保存 HUD 闪烁计数器（表现层，P3-13）；自动驾驶恒为关（G-09），辅助总走“自动驾驶关闭”的分支。
  - **切换：** 飞行上下文中 `toggle-auto-match` 翻转开关并发出 `speed-assist-toggled`；开启时到期时刻归 0、清除“已匹配”，关闭时两者不变。原版每次切换都显示开/关消息，开启时还启动 HUD 闪烁，二者由 P3-13 从事件呈现。
  - **位置：** 玩家可用时，在玩家更新中、失效目标清除之后、命令批次与轴的变化检测之前运行，不论视角模式。某 tick 的命令改变的开关或目标，辅助在下一 tick 才看到。
  - **无有效目标：** 若“已匹配”，投递满油门、三轴不变的 `control` 请求（在本 tick 命令的请求之前），清除“已匹配”，发出 `speed-assist-released`；否则无作用。
  - **有效目标：** 目标种类属于辅助种类掩码，且时钟不早于到期时刻（含等号）；三维距离平方（各分量差乘以其 f32 舍入值后求和）不大于阈值的平方（**等于时也匹配**）。满足时：先记录双方当前速度差是否超过常数（原版的闪烁条件，玩家没有移动块时速度按 0），再直接按手动匹配的规则写玩家移动块（不经请求，与原版一致），置“已匹配”，到期时刻 = 本次时钟 + 固定间隔（不追赶）。目标缺少移动块时写入失败，但“已匹配”与到期时刻照样更新。只有写入成功时才发出 `speed-matched`（`origin: 'assist'`，带速度差标志）。范围外、种类不符或未到期时无作用，计时不推进。
  - **目标各状态：** 更换目标不复位计时与标志；目标被移除、停放或玩家开始 Warp 后，下一次辅助走“无有效目标”分支；被毁但未移除的目标仍可被匹配。
  - 匹配不等于重新选择目标；目标选择缺失时明确保留尚未集成状态，不在生产入口注入测试目标。
  - 开关与“已匹配”走 projection，事件只通知一次性反馈；P3-13 不能靠累计事件重建持续事实。消息文字由既有 `data/flight-messages`/HUD 内容解析，不进入 Core 硬编码文字。原版没有“最新匹配时刻”这一状态，projection 不提供它。

### 活动区域、停放与世界边界

依据见 [世界边界、活动区域、停放与自动驾驶](../../../original/formats/executable.md#world-boundary-active-area-parking-and-autopilot-p3-0604)。

- **活动区域（`area-check`，第 17 阶段）：** 按 `0x3a468`/`0x3a4b0` 实现：
  - **筛选：** 种类 `0x1fffffe`（除玩家外全部），状态为活动及以上（7、8）。
  - **判定：** 与实例化共用 `0x3a540` 的测试：以玩家位置为中心，x/y 距离平方严格小于 56,250,000 时在区内；没有玩家实体时一律在区外。玩家 Warp 期间的中心（玩家状态中的点）归 P3-09。
  - **切换：** 区外且活动 → 写状态区域切换，种类位 `0x1f00000`（导弹、炮弹、爆炸等，P3-07 的种类）改写待移除，不停放、不发事件；区内、停放且不在 Warp 中 → 写状态区域切换；其余（区外的停放或停靠对象、区内的活动或停靠对象、Warp 过境中的停放对象）不变。区域检查直接写状态，不释放任何东西。
  - **停放切换（Q-08 的请求处理时机，`leave` 请求）：** 停放（活动或停靠 → 停放）：释放移动块，只在玩家目标恰为该对象时清除玩家目标（其他对象的 AI 目标、编队领队与速度辅助状态都不清除）。恢复（停放 → 活动）：按初始移动块规则新建移动块（满油门，当前位置与姿态）。两者都不改 `lastParkedUpdateClock`、`warpClock` 与 `inWarp`。
  - P3-02 的 `startsActive` 改为调用同一判定函数，结果不变。
- **停放更新（`parked-update`，第 13 阶段）：** 按 `0x2f1b0` 实现：
  - **筛选与节奏：** 遍历种类 `0xfffff`，选停放、状态为活动及以上、未被毁的实体。对每个选中的实体每 tick 抽一次世界随机数，得到本次的随机阈值；时钟不早于 `lastParkedUpdateClock` + 阈值（含等号）时到期。到期时先计算经过时间 = 时钟 − 旧值并把 `lastParkedUpdateClock` 写为本次时钟，再做后续各步。停放与恢复不重置它，因此长期活动后才停放的实体首次到期时经过时间很长（原版如此）。
  - **Warp 过境（`0x2f298`）：** `inWarp` 与 `warpClock` 都非零值时，过境持续机型 +0xA8 秒（有有效编队领队时取领队的机型）；未结束则跳过本实体的其余更新；结束时清 `inWarp`。原版通用回调在状态 0–3 也调用它，所以过境中的停放实体不推进生命周期状态：P3-06 在实体自身更新的通用部分加入同一检查。
  - **停放行进（`0x2f314`，P3-06）：** 输入为编队领队与 AI 状态（[检查点 A 定稿的状态与契约](#检查点-a-定稿的状态与契约)）：设置了但已失效的领队先清除，本次不运动；主体为有效领队，否则为实体自身；按主体的 AI 模式取目标（模式 2 时有效的对象目标优先，否则取 AI 目标），求目标点（有目标时为目标位置加主体的目标偏移，零偏移先换成随机方向乘随机长度并保存）。随后按原版依次处理：
    - **到达**（距离平方严格小于常数）：有目标时清偏移；无领队且模式为 4 时由来源记录的放置路线取新目标点（含该路线的抽取）；清 `inWarp`；做离开世界测试（下文）。不写位置。
    - **Warp 跳跃**（P3-06，检查点 A）：条件、跳跃长度、随机抖动（6 次抽取）与 `warpClock`/`inWarp` 的写入按原版；有领队时取领队的 `warpClock` 后做编队跟随。
    - **正常行进：** 姿态重建为朝向目标点，步长 = F(经过秒数 × 机型 +0xB8)（内容基准，不是当前上限），不超过距离，加小幅随机抖动（6 次抽取）。
    - **编队跟随：** 复制领队姿态，位置 = 领队位置 + 偏移在领队三行上的分量和。
    - 位置提交时原版做扇区资源测试；P3-02 的资源测试在 Core 中总是通过（已披露差异），因此总是写入。每次写位置使放置序号加 1。
    - 僚机到达基地的报告（`0x39820`）与靠近基地的报告（`0x3c3b0`）归 P3-10，接入前不做。
  - **停放战斗**（`0x2ffec`/`0x30150`）在停放行进之后，归 P3-07/P3-08，接入前不做；它们的抽取接入前不在随机序列中（集成缺口，由其负责任务补上）。
  - P3-08 交付前，停放机体按实例化时的 AI 状态行进（与活动机体“按实例化时的移动块运动”同属分阶段接入，不是 AI 的替代）。此后 AI 程序对 AI 状态的改变归 P3-08。
- **离开世界（`0x2f314` 的到达分支）：** 这是唯一的真正退场：停放实体（种类不是僚机）的主体到达目标点时，用主体本次更新前的位置（忽略 z）测试内缩 100 单位的世界矩形（严格比较，内缩边界本身算在内），在矩形外时直接写状态待移除并发出 `object-left-world`（带来源快照，供 P3-11 计数），不经请求。实体在下一 tick 由自身更新提出移除，在请求处理中移除。
  - 重新放置（Warp 跳跃、行进步与编队跟随）与其他情形都不是退场，不发事件；僚机永不离开。
  - 同一对象只退场一次：写入待移除后它不再被停放更新选中，待移除期间 ID 有效但不可重复计数。域外错误不是规则退场，不能发事件伪装为正常结果。
  - `warpClock` 与 `inWarp` 由 P3-06 加入（实例化抽取、停放路径的读写），P3-09 复用同一字段（玩家 Warp 与完成）。
- **活动对象的世界边界：** 没有处理（M-07 已确认）：`0x3a41c` 的调用者中没有一个夹取、移动或拒绝活动对象的位置，活动对象（含玩家）可以飞出世界矩形而没有任何夹取、移除或消息；活动的非玩家对象离开活动区域后停放，交给停放更新。Core 不自行夹取。只适用坐标域故障规则。

### 起飞初始状态

- **范围：** 指任务开始时首次实例化的玩家。离港放置归 P3-10，救援放置归 P3-11。依据见[初始飞行状态](../../../original/formats/executable.md#initial-flight-state-p3-0605)。
- **P3-02 已实现、不变：** 位置（放置）与单位矩阵姿态（右 +x、上 +y、前 +z，相对扇区平面机头垂直向外）。
- **P3-06 补上（检查点 A 定稿）：**
  - `maximumSpeed`：实例化时按代码固定的初始分配等级与清零的两位字段计算，确定、不抽取；
  - 移动块：初始移动块（模式 `craft`，速度 = 指令速度 = 最高速度，到达标志置位，速度比 = F(最高速度 ÷ 机型 +0xB8)，其余为零或空）；
  - 玩家目标：null（代码证据，见上）；

  - AI 初态（`0x68050`，见[实例化扩展](#实例化扩展)）：对玩家恒为 2 次抽取（世界随机点），AI 目标为空，AI 模式为目标点模式；这些字段对玩家只有自动驾驶会读（G-09），但抽取必须在随机序列中；

- **核对：** 分开记录“实例化完成且尚未运动”“首次运动”与“首次可操纵更新后”的暂停点。按对象身份、源声明和操作数核对，用实例化相对时间，不把原版构建/过场用时、随机绝对时钟或不同随机序列的结果与 Core 直接逐位比较。首次可操纵更新后的目标（自动选择）以 P3-07 接入为前提。

### 实例化扩展

检查点 A 定稿 P3-06 在 P3-02 实体初始化扩展点中的工作与位置。各步按[实例化](../../../original/formats/executable.md#instantiation-p3-0203)的原版次序，在请求处理中、P3-02 的分配与命名之后执行；其他任务的步骤在括号中，由它们在同一位置加入：

1. 最高速度（`0x3060c` 的位置，不抽取）。（P3-07：`0x3060c` 的能量字段与能量计时的 1 次抽取在此。）
2. （P3-07：清零两位字段。）
3. **AI 初态 `0x68050`（检查点 A 由 P3-08 移入 P3-06）：** 固定的若干种类只写 AI 模式；其他种类（含玩家）由来源记录取候选种类掩码，遍历取最近者（不分状态与活动，自身也计入），最近者属另一方且远于常数距离时抽 1 次随机选择候选；有结果时写 AI 目标与模式（同方或另一方），没有时取目标点并写目标点模式。P3-02 的内容契约已拒绝记录 +0x4C 路径，因此目标点总是世界随机点（2 次抽取，z = 0）。一次调用的抽取次数取决于来源记录与当时存在的对象：原版为 0–3 次，其中 3 次只出现在经记录 +0x4C 路径路线取目标点时（+0x50 为 2 的 1 次加 `0x688c4` 的 2 次），该路线在 Core 中不可达，所以 Core 为 0–2 次（随机候选的 1 次与目标点的 2 次互斥，见 core 分册的[已知差异](../../../engineering/modules/core.md#已知差异)）；目标偏移初值为零。分支与种类集合见[初始飞行状态](../../../original/formats/executable.md#initial-flight-state-p3-0605)。此后 AI 程序对这些字段的改变归 P3-08。
4. `lastParkedUpdateClock` = 本次时钟。
5. `warpClock`：玩家与僚机以外的种类 = 本次时钟 + 随机区间（1 次抽取）；玩家与僚机为 0，不抽取。`inWarp` = false。实例化发生在时钟阶段之后，时钟为正，所以抽取得到的值总不为 0，不与哨兵混淆。
6. （P3-08：`0x20990` 的 AI 程序。）
7. 活动判定（P3-02，改为调用共用的区域判定）。
8. 活动实体：初始移动块（`0x2c3b0`）；玩家的单位矩阵姿态（P3-02）。（P3-10：`0x38cd4` 的僚机报告。）
9. 玩家：P3-02 的玩家状态；P3-06 的玩家目标（null）与控制状态。

段 5 编组请求在每个成员实例化之后记录编队领队与编队偏移（P3-02 的派发，由 P3-06 的修订补入实体，见[对 P3-02 契约的增量](#对-p3-02-契约的增量)）。

P3-06 自己的抽取（`0x68050`、`warpClock`）位于原版的相对位置；P3-07、P3-08、P3-10 的抽取在它们接入前不在序列中。Core 不复现原版的随机序列（P3-02），这只是各任务的集成缺口，由其负责任务在同一位置补上并递增 rulesVersion。

#### 共同定义

- **单位：** 位置为世界单位，速度为单位/秒，角速率为 rad/s，角度为 rad，时钟为 1/64 秒的单位；生产 tick 为 2 单位，h = 1/32 秒。ulp(x) 为 x 处的 f32 末位单位。±0 视为相等。
- **独立求值器：** 01 的精确有理数求值器（`local/research/p3-06/motion/ref_step.py`）或 11 的参考（[flight-motion.test-support.ts](../../../../src/core/rules/flight-motion.test-support.ts)），两者在 120 个合成多步样例（2,422 步）上逐位一致。按 M-01、M-10 的运算次序与就近舍入（技术决定 12）计算，正弦与余弦取正确舍入值。期望只来自原版读数与求值器。
- **临界正余弦：** 一次旋转的 sin θ 或 cos θ 的精确值，与夹住它的两个相邻 f32 之间的舍入分界点之差不超过其绝对值的 2^-40 时，称为临界。x87 FSIN/FCOS、模拟器以宿主双精度求值的结果与 JavaScript 的 `Math.sin`/`Math.cos` 的相对误差都在 2^-51 以内，只有临界值可能存成相邻的两个不同 f32；2^-40 留出 2^11 倍余量。每个值成为临界的概率约 2^-15。合成检验：5 万个随机角的正余弦，宿主 libm（模拟器在本机以宿主双精度求值时所用）与 V8 的结果存为 f32 后，与正确舍入的 f32 只可能在临界值处不同，实测都没有分歧，临界值各 3 个。
- **固定步长求值 eval2：** 求值器从比较起点的原版读数出发，以 2 单位/tick 推进。读数是上一帧运动之后的状态，记其状态时刻 T = 样本 − 步长；原版在帧 k 的回调暂停施加的刺激于帧 k 的运动之前生效，因此映射到第 (T_k − T_0)/2 个 tick 的运动之前（步长都是 2 单位的整数倍，B-006），效果按 R-04b 精确核对过的规则写入。项目在同一 tick 的对象更新与请求处理中应用输入、之后运动（[P3-02 系统流水线](../02/spec.md#系统流水线)），与原版的帧内次序相同，所以映射本身不引入输入对齐误差。
- **步长超额 E 与上界 E_cap：** 跨 k 个生产 tick（步长 2k 单位）的原版帧记 e(k) = k(k − 1)/2，E 为比较区间内各帧之和；只有 0 与 2 单位的帧时 E = 0。区间的帧数 F 与单位数 U 由两端读数给出，帧内步长未知。步长不超过 6 单位时 E ≤ E_cap(F, U)：把 U/2 个 tick 尽量装入 3 个 tick 的帧（每帧 e = 3），至多 F 帧，余下的装入下一帧。F × 3 < U/2 的区间必含更长的帧，列为无效区间。理由：基准下除首次运动与视角切换的载入帧外，预实验与 B-006 观察到的步长都是 0、2、4 单位，B-006 在 20000 cycles 下见过 6；以 6 为界给单个较长帧留出余量，以 4 为界则没有。

#### R-04c 固定步长持续运动

比较区间分两种：**单窗**从一个干净窗口起点（该暂停未施加输入）注入，到窗口终点；**链**从一串窗口的干净起点注入，按映射施加其中的刺激，不再注入地经过其后每个读数边界。注入的前态包括移动块与玩家控制状态中各轴的上次读数，使原版已生效的偏转不被重新应用。每个有效区间的每个边界核对两个条件：

1. **与规则同序：** 候选与 eval2 逐位相等（位置、三行、速度、速度比、到达标志）。路径上有临界正余弦时，候选须等于把每个临界值取相邻两个 f32 之一所得的某条 eval2 路径；临界值多于 10 个的链在窗口边界重新注入、分段比较。理由：生产步长下候选与同一规则的独立求值同序，唯一可容许的实现差是正余弦；这一条使 R-04c 对规则、输入映射与流水线次序的任何偏差都敏感。
2. **步长预算：** eval2 与原版读数之差满足下表。这是 P3-02 固定步长时间模型相对原版可变步长的有界差；候选满足条件 1 时，它与原版之差同此。

在每个边界，取比较起点以来各量的最大值：施加的加速度 |a|（加速取机型 +0xBC，减速取 +0xC0，已到达为 0），速度 v（当前速度与指令速度的较大者），启用的稳定角速率 ω_p、ω_y、ω_r，速度比 r_s，参考最高速度 ref（机型 +0xB8）；t 为起点以来的秒数。

- W = |ω_p·ω_y| + |ω_p|·ω_r′ + |ω_y|·ω_r′，其中 ω_r′ = |ω_r| + |ω_y|·r_s（机型 +0xC4 置位且偏航启用时；否则 ω_r′ = |ω_r|）；耦合起作用且速度在变时 α = |ω_y|·|a|/ref（耦合横滚随速度比变化），否则 α = 0；ω⊥ = √(ω_p² + ω_y²)（横滚不转动第 3 行）。
- 每单位 E 的系数：b_θ = κ·h²·(W + α)（rad），b_p = κ·h²·(|a| + v·ω⊥) + b_θ·v·t（单位），κ = 1.25。
- 舍入项：n_r = F + U/2；r_θ = n_r × 2^-20 rad；r_v = n_r·ulp(v)/2；r_p = √3·n_r·(ulp(p_max) + ulp(6v/64))/2 + (r_θ·v + r_v)·t，p_max 为区间内位置分量的最大绝对值，最后一项是姿态与速度的舍入差经时间造成的位移。
- 差：dev_θ 为对应行之间的最大夹角（rad），dev_p 为位置差的长度（单位），dev_v 为速度差（单位/秒）。
- E_fit = max(0, (dev_θ − r_θ)/b_θ, (dev_p − r_p)/b_p)；系数为 0 的一项在差不超过舍入项时记 0，否则记为无穷大。

| 条件 | 判据 |
|---|---|
| 步长预算，每个边界（单窗与链） | E_fit ≤ min(E_cap(F, U), 0.25 × U/2 + 2) |
| 速度，每个边界 | dev_v ≤ r_v；到达标志相同，除非 eval2 的速度与指令速度之差不超过 r_v |

- **推导与核对：** 一个跨 k 个 tick 的原版帧与 k 个生产 tick 相比：速度按时间线性，只差舍入（两者在同一时刻跨越指令速度，读数边界都是帧边界，所以到达标志与到达用时在边界一致）；位置差为 e(k)·h²·(加速度 + v × 第 3 行的转速)，因为显式欧拉在整帧中用帧初的速度与方向；姿态差为三次旋转两两对易子之和，至多 e(k)·h²·W，耦合横滚随速度比变化另加 α 项；此后姿态差的大小不变，并经 v 使位置差随时间增长。合成检验中 k = 2、3 的单帧差都在二阶项的 0.999 以内，κ = 1.25 是三阶项的余量；随机的 0、2、4、6 单位分区下，世界坐标量级的 300 个窗口与 200 条含输入变化的链、坐标在 50 单位以内的 200 个窗口与 150 条链，全部在界内，且 E_fit ≤ 0.8 E，即 E_fit 不高估真实超额。
- **预算的两部分：** E_cap 是步长不超过 6 单位时的可行上界；0.25 × U/2 + 2 限制典型大小：每 tick 0.25 个超额 tick（只有 2、4 单位的帧时约合平均步长 2.67 单位），另加 2 以容纳短区间中的两个 4 单位帧。B-006 不中断窗口的平均步长 2.11 约合每 tick 0.05，预实验逐帧序列约 0.16（逐帧暂停可能使其偏高），0.25 至少是观察到的最高值的 1.5 倍。超额不超过这一典型值的随机分区在合成检验中都满足预算。预实验的 30 个单窗与 5 条链（最长 594 单位）的全部边界都满足，E_fit 至多 1.9（诊断，不是正式样本）。
- **灵敏度与窗口长度：** 系数为 0 的项（匀速直线的位置；只绕俯仰轴或只绕横滚轴的姿态，绕单轴的旋转与步长划分无关）要求只差舍入，一个 tick 的输入偏移造成的转角 ω·h 是 r_θ 的数百倍，所以单轴的链精确核对输入映射；R-04b 的逐帧对也核对刺激在同一帧生效。合成检验中，原版比映射晚一个 tick 施加输入的 66 单位区间，在俯仰、横滚、偏航、俯仰加横滚、加速与减速中每类 40 个全部超出预算，在俯仰加偏航中 40 个超出 29 个；组合操纵依靠单轴链已核对的同一映射，自身只受步长预算约束。窗口取自动选择的到期间隔（约 66 单位、1 秒）：典型的步长超额远低于一个 tick 的偏移，也不增加暂停。
- **输入对齐（同一外部时刻）：** 上述映射按原版的施加时刻输入，核对的是规则与帧内次序。对同一外部时刻的输入，原版只在设备读取或键盘轮询触发的帧应用（严格超过到期后的第一帧），项目在输入所在的 tick 应用（技术决定 9 批准的逐 tick 动作边界），两者生效时刻之差 δ 满足 −2 ≤ δ ≤ I 单位，I 为原版该路径实测的最大到期间隔（规则上设备读取为 6、键盘轮询为 16 单位加触发帧的步长，步长至多 6 时分别至多 12 与 22 单位）。一次输入变化的生效时刻平移 δ 后，差至多为：转向变化 Δω 的姿态差 |Δω|·|δ|/64 rad 与位置差 v·|Δω⊥|·|δ|/64·t；油门变化的速度差 |a|·|δ|/64（变速期间）与位置差 min(|Δv_c|, |a|·t)·|δ|/64，Δv_c 为指令速度的变化。链中各次变化的界相加，记为延迟界 A。判据：|δ| 不超过原版一个到期间隔，由“原版每次到期都在规则规定的帧触发”（17 精确核对并报告 I）与“Core 在输入所在的 tick 应用”（Node，AC-03）共同保证；由此引起的操控差以 A 为界，18 逐条链报告 A。
- **反复到期：** 比较区间内没有作用于玩家运动的 Core 到期规则（速度辅助关闭），反复到期的累计偏移在本项为 0，由 R-04d 判定。
- **输入域与有效区间：** 玩家；两端视角模式都是 0xC，速度辅助与自动驾驶关闭，两端都没有冲量、定时旋转、锁定或扰动，状态 7，没有救援；只有配方中的输入，摇杆为 Medium 满偏。不满足这些条件的区间与 F × 3 < U/2 的区间列为无效，不计入，也不抵扣数量下限。跨入地图或基地的窗口单独列出，不计为一致（采集方案中没有）。

#### R-04d 匹配与辅助

- **条件与结果，精确：** 以原版读数为操作数按 M-05 判定：距离平方（各轴的双精度差乘其 f32）与 f32 射程平方的比较（相等时匹配）、种类掩码、到期（样本不小于到期时刻）；匹配后指令速度逐位等于目标速度钳到 [0, 最高速度] 的结果，到达标志清除，已匹配置位；速度差标志（严格大于）；手动匹配结果相同且不留状态；开启时到期与已匹配清零，关闭时保留；匹配后失去目标时的满油门请求。
- **节奏：** 原版每次辅助匹配在到期（含等于）之后、距离在射程内的第一帧发生，到期重设为该帧样本 + 32（精确）。目标一直在射程内时，间隔 I 的超出量 o = I − 32 满足 0 ≤ o ≤ 匹配帧步长 − 2，项目在 2 单位的 tick 上的间隔恒为 32，两者每个间隔之差即 o；两者都不追赶，累计差 Σo 逐次报告。目标在到期时不在射程内的间隔只核对“第一帧”这一条。
- **输入域：** 难度组 0 的开局、敌方模式目标、自动驾驶关闭。阈值的等号与其余负分支只由 Node 覆盖。

#### R-05a 起飞初始状态

- **精确：** 实例化暂停的固定字段（状态、单位矩阵、速度 = 指令速度 = 最高速度、到达、速度比、移动块其余为零、AI 目标为空、AI 模式 4、Warp 计时 0、控制块未建立）；最高速度 0 ulp（确定的公式）；控制块的初值；首次可操纵更新后的目标为按记录的距离分数最近的敌方模式对象（P3-07 接入后判定）。
- **相对时刻：** τ = 样本 − S_B。τ(+0x18) = τ(+0x20) = 0；τ(+0x24) − 128 是 0–63 的整数（支持集）。实例化在帧 B，控制块建立与首次运动在 B + 1，首次可操纵更新在 B + 2，按帧精确比较；若原版的载入请求跨帧（[initial flight state](../../../original/formats/executable.md#initial-flight-state-p3-0605) 中高概率的一步），按整帧顺延并记录。
- **支持集：** 放置按 P3-02 的支持集；`0x68050` 的目标点须是某一对抽取值按记录的公式得到的值。
- **不比较：** 首次运动的步长与位移。原版的首步包含实例化之后的载入时间（预实验 190 与 230 单位，依赖 cycles 与载入负荷），项目首步为 2 单位，属于 P3-02 批准的时间模型；这次运动的公式由 R-04a 按实际步长核对，帧 B + 1、B + 2 的 τ 照实报告。

#### R-05b 区域、停放、离开世界与世界边界

- **精确：** 区域判定（按记录的公式，距离平方与 f32 半径平方严格比较）；状态 5 的写入与切换的帧次序（检查帧 N 写状态 5，N + 1 切换，停放对象于 N + 2 回到状态 7）；移动块的释放与重建，玩家目标的清除；停放更新时 +0x18 等于当时的样本；正常行进与 Warp 跳跃中抖动前的位置、行进长度与姿态三行，以及编队跟随的位置，在给定原版操作数时 0 ulp；Warp 跳跃的 +0xC8、+0xCC；到达与真正退场（离散，退场只计一次）。
- **随机部分：** 每轴抖动是代码确定范围内的整数 n，且 F(D(p + n)) 等于读数；两次停放更新之间的经过时间满足 64 ≤ 经过时间 ≤ 126 + 更新帧的步长（上一帧该对象已被选中而未到期时；项目为 64–128）。
- **越出世界矩形的活动对象：** 活动与状态不变（精确）；位置与从上一读数起的 eval2（直线匀速）之差 dev_p ≤ r_p，只含舍入项（n_r = F + U/2）。`skip` 跳过的停止不改变直线匀速的结果，所以长时段可用于这一核对，但不作计时窗口。
- **输入域：** 状态 7 及以上的停放对象，作弊标志清除；玩家在扇区平面内直线匀速飞行。

#### 样本、窗口与运行数

正式样本只计工具报告为 `complete` 的运行。数量是一个采集段（B-008 的 F1–F5）全部合格运行的合计；“来自 2 次运行”指至少两次独立运行中各有一个。表中每个下限都是必需的：最少运行数之后仍不足时，17 至多再追加两次同配方的运行（标 † 的项能否出现取决于游戏而非配方，最需要追加）；仍不足的项未完成，17 记录缺口、原因与恢复条件并记为 blocked（AC-10 不通过），不以 Node 测试代替运行样本。只有写明“出现时全部比较”的项没有下限：步长 0 按覆盖下限，未出现时由代码与 Node 覆盖并在结论中披露；到达帧由 R-04c 的边界覆盖；停放对象的 Warp 跳跃、到达与真正退场按 B-008 的方案，未出现时写明原因与恢复条件，由 Node 覆盖，R-05b 的结论写明哪些分支经运行核对。为满足日志预算，17 可以把一段的配方拆成几个，每个配方都满足最少运行数。

R-04c 的类别按速度状态（已到达、加速、减速）与启用轴（无、俯仰、偏航、横滚、俯仰加偏航、俯仰加横滚）区分。

| 玩家目标引用 | 实体 ID 或 null；实例化时为 null（代码证据），失效、停放、移除时清除 | 生命周期 P3-06；选择 P3-07；Warp 开始清除 P3-09 | 快照 |
| `warpClock`、`inWarp` | `warpClock` 为非负安全整数时钟单位，0 为哨兵（“未设”：不限制 Warp、不在过境）；`inWarp` 为原版 Warp 中标志。实例化对玩家与僚机以外的种类抽取一个未来时刻 | P3-06 接入初值与停放路径的读写，P3-09 复用其余用途 | 实体快照；同一字段，不在两处各保存一个计时器 |
| 命令原因码 | 新增 `player-unavailable`、`wrong-context`、`no-target` | Core | `command-result`；比较的字段表 |
| 领域事件 | 新增 `speed-assist-toggled`、`speed-matched`、`speed-assist-released`、`object-left-world`，形状见下节 | Core | 冻结的 step 输出；反馈顺序及字段进入 compare 校验 |
| `flight` 分区 | 改为 `{ motion, combat }`，两者分别为 `not-implemented` 或各自的 `ready` 联合，不让一个外层 `ready` 暗示完整玩法已接入 | Core | 不覆盖先完成的另一分区；整体就绪判定必须检查所需分区 |
| 运动 projection | `motion: { readiness: 'ready', player }`；player 为 null 或 `{ entityId, position, orientation, speed, commandedSpeed, maximumSpeed, speedLimitStatus, speedAssist: { enabled, engaged } }`。位姿复用 `Vec3`/`Matrix3`；速度单位为运行时单位/秒；`speedLimitStatus: 'initial-only' \| 'live'` 显式区分开发初值与动态规则 | Core | 无玩家实体时 player 为 null，不伪造零速度。玩家实体存在而缺少移动块或控制状态为 Core 故障；开发初值状态不计完整 R-04 验收 |

### 检查点 A 定稿的状态与契约

依据：01–05 的完成证据与 21 写入的 [P3-06 运动一节](../../../original/formats/executable.md#flight-motion-controls-speed-parking-and-take-off-p3-06)。以下以 TypeScript 记法写出形状；注释中的原版偏移只说明对应关系。所有 f32 字段都是 `Math.fround` 的不动点且有限；非有限或违反约束的值为 Core 故障。

**实体（P3-06 加入，`Entity` 与 `EntityInit` 一并覆盖）：**

```ts
maximumSpeed: number;          // 对象 +0x78。f32，运行时单位/秒。实例化写入（P3-06）；重算归 P3-07、P3-11
lastParkedUpdateClock: number; // +0x18。非负安全整数时钟单位。实例化 = 时钟；停放更新到期时与 Warp 离场请求（P3-08）改写
warpClock: number;             // +0xC8。非负安全整数时钟单位，0 = 未设
inWarp: boolean;               // +0xCC
movement: MovementBlock | null; // +8。停放或移除时为 null
ai: AiState;                   // `0x68050` 写入的初态
formation: Formation | null;   // P3-02 修订：段 5 派发写入（见对 P3-02 契约的增量）

interface MovementBlock {
  mode: 'craft' | 'warp';        // 原版模式 0、3；P3-07、P3-09 按扩展规则加入其他模式
  speed: number;                 // +8，f32 单位/秒；不受最高速度钳制，积分不限正负
  commandedSpeed: number;        // +0x6C，f32 单位/秒
  atCommandedSpeed: boolean;     // +0x78：置位时速度与速度比不更新
  speedRatio: number;            // +0x74，f32；参考最高速度（+0x70）恒等于机型 +0xB8，由 craft-info 取得，不另存
  steering: { pitch: SteeringAxis; yaw: SteeringAxis; roll: SteeringAxis }; // 绕第 1、2、3 行
  timedRotation: { pitch: TimedRotation | null; yaw: TimedRotation | null; roll: TimedRotation | null };
  impulse: { direction: Vec3; magnitude: number } | null; // +0x18–+0x28，f32；衰减后小于 0 时为 null
  locked: boolean;               // +0x5C
  disturbance: { level: 1 } | { level: 2; biases: readonly [number, number, number] } | null; // +0x88 与整数偏置；浮点偏置由整数偏置按原版换算得出，不另存
}
interface SteeringAxis { rate: number; enabled: boolean } // +0x60–+0x68 与 +0x7C–+0x84；f32 弧度/秒（单位高概率）；关闭时速率保留但不施加
interface TimedRotation { rate: number; decay: number; end: number } // f32 弧度/秒、弧度/秒²（符号随速率）、到期的 f32 任务秒
interface AiState {
  mode: 0 | 1 | 2 | 4 | 5;       // +0xC4，原版取值；P3-08 按扩展规则加入其余取值
  target: EntityId | null;       // +0x90；不能解析时视为无效
  goal: Vec3;                    // +0xAC–+0xB4，f32
  targetOffset: Vec3;            // +0xB8–+0xC0，f32；实例化为零
  objectTarget: EntityId | null; // 非玩家对象的 +0x8C：初值 null，由 P3-08 的 AI 写入；停放行进的模式 2 优先读取它。
                                 // 玩家的 +0x8C 是 PlayerState.target，玩家实体的 objectTarget 恒为 null
}
interface Formation { leader: EntityId; offset: Vec3 } // +0x7C 与 +0x80–+0x88，f32
```

- **移动块的生命周期：** 实例化为活动时与恢复活动时由初始移动块规则创建（模式 `craft`，速度 = 指令速度 = `maximumSpeed`，到达，速度比如前述，三轴稳定转向为 0 且关闭，定时旋转、冲量、扰动为空，未锁定）；停放与移除时为 null；被毁源与停靠的实体保留。原版块中不被模式 0、3 规则读取的位置副本与表现字段不进入 Core。
- **写入责任：** 速度、指令速度、到达、速度比由 P3-06 的积分、操纵应用与匹配写入（P3-07 的导弹发射、P3-09 的 Warp 另写）；稳定转向由两条操纵路径写入；冲量与定时旋转由 P3-07 的写入者设置、由积分衰减与清除；锁定与扰动由 P3-07 设置、由 P3-10/P3-11 清除。
- **AI 初态与编队：** 未经 `0x68050` 的运行时实体（P3-07 的弹丸等）使用分配器的缺省（模式 5、两个目标为空、零向量），由创建它的任务确认。停放行进中，设置了但已失效的编队领队被清为 null。

**玩家状态（P3-06 加入）：**

```ts
target: EntityId | null;         // 玩家对象 +0x8C
control: PlayerControl | null;   // 有玩家实体时非空，玩家实体移除时与 entityId 一起清空；救援保留
interface PlayerControl {
  lastAxes: { pitch: number; yaw: number; roll: number }; // 整数偏转，初值 0
  speedAssist: { enabled: boolean; dueClock: number; engaged: boolean }; // 控制块 +0x1B4、+0x1B8（非负安全整数时钟单位）、+0x1BC
}
```

**内部请求（封闭纯数据，P3-02 `Request` 联合的新增变体）：**

```ts
| { type: 'control'; entityId: EntityId; throttle: number | null;                 // 消息 0x20000；null = 不变
    axes: { pitch: number | null; yaw: number | null; roll: number | null } }   // null = 不变，0 = 关闭，其他为整数偏转
| { type: 'match-speed'; entityId: EntityId; targetEntityId: EntityId; commandIndex: number } // 消息 0x80000，玩家的手动匹配
```

- 油门是非负安全整数；应用时的表索引钳到油门表内（已知差异）。偏转是满偏刻度内的整数。`leave` 请求扩展为停放切换（见[活动区域、停放与世界边界](#活动区域停放与世界边界)）。
- 浮点操纵请求（消息 0x40000）与 Warp 离场请求（消息 0x800000）不由 P3-06 投递，由其第一个投递者按扩展规则加入。

**领域事件：**

```ts
{ type: 'speed-assist-toggled'; tick; commandIndex: number; enabled: boolean }
{ type: 'speed-matched'; tick; targetEntityId: EntityId; origin: 'command'; commandIndex: number }
{ type: 'speed-matched'; tick; targetEntityId: EntityId; origin: 'assist'; speedDifferenceExceeded: boolean } // 匹配前双方速度差超过原版闪烁常数
{ type: 'speed-assist-released'; tick }                    // 匹配后失去目标，恢复满油门
{ type: 'object-left-world'; tick; entityId: EntityId; kindBit: number; source: EntitySource | null } // 脱离世界的来源快照
```

- **一个 tick 内的次序：** 玩家更新中，辅助的事件（`speed-matched` assist 或 `speed-assist-released`，每 tick 至多一个）先于命令结果；每条命令的 `command-result` 按索引发出，`speed-assist-toggled` 紧随其结果；手动匹配的 `speed-matched`（command）在请求处理中、该请求应用成功时发出；`object-left-world` 在停放更新阶段发出。
- `speed-matched` 只在写入成功时发出；辅助写入失败（目标没有移动块）不发事件，原版此时仍可能启动 HUD 闪烁，这是只影响表现的已知差异。

**容量核算（D-08）：** 记号沿用 P3-07 子任务 07 为共享预算给出的记号（协调者 2026-10-10 转交）：K 为本 tick 的命令数，Ct 为全部机体数；另记 Lw 为本 tick 离开世界的停放机体数（≤ Ct）。

- **P3-06 自己的项：** 事件 ≤ K（每条命令至多一个附加事件：`speed-assist-toggled` 或手动匹配的 `speed-matched`）+ 1（辅助的 `speed-matched` 或 `speed-assist-released`）+ Lw（`object-left-world`，每个对象一生至多一次）。请求 ≤ K（每条速度命令至多一个 `control`/`match-speed`）+ 2（辅助恢复、单独的轴请求）。区域检查与离开世界直接写状态；实体随后在自身更新中提出的 `leave` 属于 P3-02 的“每实体每 tick 至多一个生命周期请求”，不另计。
- **与 P3-02 合计（实体上限下）：** 事件 = 命令结果（≤ `commandsPerTick`）+ 附加事件（≤ `commandsPerTick`）+ 辅助事件（≤ 1）+ `object-instantiated`（≤ `spawnExpansion`）+ `object-left-world`（≤ `entities`）= 64 + 64 + 1 + 1,024 + 2,048 = 3,201 ≤ `eventsPerTick`（4,096）。请求（单独计数，上限同为 `eventsPerTick`）= 生命周期请求（每实体至多一个；可用的玩家不投递）+ 生成请求（≤ `spawnExpansion`）+ 速度命令的请求（≤ `commandsPerTick`）+ 2 = 2,048 + 1,024 + 64 + 2 = 3,138 ≤ 4,096。P3-06 用掉 P3-02 预留的“每实体一个规则事件”。
- **与 P3-07 的上界：** P3-07 的估计（尚待其检查点定稿）含二次项（命中类事实中的 2·A·Ca 与 (Dm + Ea)·Ct），在实体上限下没有一个固定的 `eventsPerTick` 能容纳；这些事实是否计为领域事件、如何设界由 P3-07 决定。P3-06 的项是线性小项，本身不要求修订 `CORE_LIMITS`；P3-07 修订预算时，把上面 P3-06 的项计入合计。
- 单 tick 工作量：运动、停放更新与区域检查各为实体数的线性遍历；每次实例化的最近者搜索遍历候选种类，最坏为 `spawnExpansion × entities` 次距离计算，不另设上限。
- 快照文本：每个实体新增的状态在最坏情况下不超过约 1.5 KiB 规范文本，加上既有字段仍在 `canonicalTextLength` 依据的每实体 4 KiB 之内。
- 因此 P3-06 不改 `CORE_LIMITS`；09 更新其依据注释，15 测试上述上界。

### 对 P3-02 契约的增量

下列是对 P3-02 共享契约的变更。批准本 spec 确定各项的方向与已写明的规则；检查点 A 已于 2026-10-10 补全细节，P3-02 spec 的实际修订（[P3-06 的契约修订](../02/spec.md#p3-06-的契约修订检查点-a)）与本 spec 的修订同一次提交，此后才能实现任何 D 项。按用户的预先授权，该修订不需逐次审阅，但仍不授权未写明的字段。P3-02 的既有 goal 与 subtask 是历史记录，不改写。

- **D-01 世界创建输入（已定）：**
  - `CreateWorldInput`、录制入口与 `ReplayContent` 增加必需的 `craftInfo`；外层缺字段/多字段沿用 `readExactRecord` 的 `CoreInputError`，Asset ID 或内容错误保留内容读取器错误，语义不符为 `CoreInputError`。错误只带结构路径和稳定原因，不回显导入值。
  - 校验 Asset ID 的 kind；`original-import` 只接受唯一切片的 `data/craft-info`，synthetic 可用合法的 data Asset ID。族和 schema 绑定由同包的 `decodeRuleDataPayload`/`validatePackage` 保证，不增加 Core 原版来源认证。
  - 语义检查覆盖玩家、所选僚机、全部直接/延迟/编组实例的机型绑定，以及实际使用的分母、速率、数值域和可达模式；零速率或空参数须按相应字段证据处理，不能一律钳制、补值或拒绝所有未用记录的零字段。检查点 A 定稿的检查只拒绝会使规则出错的数据：
    - 可实例化的每个种类位都有机型记录（craft-info 只有种类位 0–19 的记录）；
    - 这些记录中 P3-06 读取的 f32 字段（+0x0C、+0xA0、+0xAC、+0xB0、+0xB4、+0xB8、+0xBC、+0xC0）有限；除下一条外，零值按原版处理（例如 +0xB8 不为正时速度比为 0，+0xBC 或 +0xC0 为 0 时速度不向该方向变化），不拒绝；
    - +0x0C 向零截断后为正：停放行进在模式 2 的零偏移替换中以它为随机长度的模数，任何可实例化的机体都可能成为目标，截断为 0 会使规则出错；
    - 玩家机型的能量分支：+0x88 不为 0（除数），且在 P3-07 可达的全部分配等级（0–3 的组合）下，能量量、阈值与上限的整数运算不溢出 i32，结果有限；
    - 停放 Warp 的计时运算（(+0xA8 + +0xA4) × 64 与 +0xA8 × 64）对可实例化的种类不溢出。
  - setupHash 覆盖严格读取后的完整 craft-info（含 ID）及 `MissionSetup`，固定字段顺序；`WorldState` 显式保存冻结的机型内容。已派生规则参数不能与原内容散落成两份可变事实。
  - 三份逻辑 Asset 与 craft-info 来自同一经 `validatePackage` 验证的资源包，由调用者保证，Core 不认证来源。
- **D-02 实体（检查点 A 已定稿）：** 增加 `maximumSpeed`、`lastParkedUpdateClock`、`warpClock`、`inWarp`、可空的 `movement` 与 `ai`；段 5 派发在实体上记录可空的 `formation`（原版已有、P3-02 尚未保存，由本修订补入）。形状、单位、初值与写入责任见[检查点 A 定稿的状态与契约](#检查点-a-定稿的状态与契约)；`EntityInit`、生命周期（停放切换释放与重建移动块，停靠的实体也可停放）、快照写入器和测试构造器一并覆盖。
- **D-03 玩家状态（检查点 A 已定稿）：**
  - `PlayerState` 增加 `target`（初值 null，有代码证据）与可空的 `control`（每轴上次读数与速度辅助；不保存油门）。
  - 目标在失效、停放与玩家移除时清除，停放清除的职责由 P3-07 的交接移到 P3-06；Warp 开始清除归 P3-09。
  - `warpClock`、`inWarp` 是实体字段（D-02），由 P3-06 接入实例化抽取与停放路径的读写，不顺带实现玩家 Warp；P3-09 复用同一字段。
- **D-04 命令（已定）：**
  - 接入 `speed` 的六种操作与普通飞行的 `select-number`/`confirm-selection`，已有命令形状不变；命令逐 tick 有序且恰好一个结果，不引入 DOS 轮询丢键。`select-number` n 在普通飞行中等于原版 Shift+n 的速度档位；速度命令只在飞行上下文处理，其他上下文为 `wrong-context`。
  - `COMMAND_RESULT_REASONS` 增加 `player-unavailable`、`wrong-context`、`no-target`，其他规则任务可沿用。
- **D-05 projection（结构已定）：**
  - `flight` 按数据表拆分；P3-02 已定义的目标、资源与武器语义保留在战斗组，其具体 ready 形状由 P3-07 定稿，不在本任务扩展。
  - 不把缺失资源/目标填为零或空列表；没有玩家的运动读数显式为 null，开发期动态上限未接入有明确标识。持续辅助指示可从任意一次 projection 恢复，不靠事件历史；运动组的辅助字段定稿为 `speedAssist: { enabled, engaged }`（原版没有“最新匹配时刻”，草案中的 `lastSpeedMatchClock` 删去）。
- **D-06 领域事件（检查点 A 已定稿）：** `object-left-world`、`speed-assist-toggled`、`speed-matched`（command/assist 两个变体），以及新增的 `speed-assist-released`；形状与次序见[检查点 A 定稿的状态与契约](#检查点-a-定稿的状态与契约)。比较校验的事件字段表随之扩展。
- **D-07 版本与快照（规则已定）：**
  - 快照覆盖全部新权威状态（实体的飞行状态、移动块、AI 初态与编队，玩家目标与控制状态）。格式版本相对合入时支持的版本递增，不能在并行任务之后仍硬编码“改成 2”；`RULES_VERSION` 同样相对当前递增。
  - replay 记录形状不变（craft-info 经 setupHash 绑定，`ReplayContent` 是 replay 的调用输入而非记录字段，检查点 A 没有增加运行配置），因此 replay 格式版本保持不变。新字段与静态内容均进入规范文本/身份绑定，不能仅靠 producer 或人为版本号辨认数据改变。
  - Render State 的形状不变。
- **D-08 内部接入（规则已定，容量在检查点 A 核算）：**
  - 既有 movement、parked-update、area-check 阶段接入规则，阶段次序不变；`object-sets` 阶段在 P3-06 中保持为空（P3-06 的规则不读取它），说明与建议负责阶段见 P3-02 的修订。对象更新中的玩家更新加入飞行控制（失效目标清除 → 速度辅助 → 命令判定 → 轴的变化检测）；请求处理加入 `control`、`match-speed` 请求与扩展的停放切换；实体自身更新的通用部分加入 Warp 过境检查。内部请求为封闭纯数据，不接受外部处理器。辅助先于命令批次，命令结果按原索引有序；需要改变已批准的时序须重新审批。
  - 初始化位置按原版记录的依赖和抽取顺序（[实例化扩展](#实例化扩展)）：最高速度、AI 初态、停放更新时间、Warp 计时与移动块各有一次写入，不提前/重复抽取。帧尾请求的丢弃规则不变；真正退场与区域检查直接写状态，不经请求，真正退场的领域事件不能误放进已关闭请求队列。
  - 容量已按定稿的事件与请求核算（[检查点 A 定稿的状态与契约](#检查点-a-定稿的状态与契约)）：事件界 3,201、请求界 3,138，都在 `eventsPerTick` 之内，快照长度在每实体预算之内，`CORE_LIMITS` 不变。合入时与并行规则的总量一起复核；容量失败锁存故障，不发布部分输出。

### 持久化与兼容

- **不涉及：** IndexedDB、localStorage、资源缓存、导入协议、内容 schema 与转换器版本。
- **快照与 replay：** 都是带版本的纯数据，不做迁移：
  - 快照格式版本递增；快照只用于诊断与检查点哈希，Core 不读取旧快照；
  - 旧 replay 记录因规则版本或 setupHash 不符而被拒绝，须用新版重新录制。
- **数据边界：** 快照、私有记录与诊断可能包含导入内容的派生状态，只在本地使用；公开测试只用合成内容。

## 技术决定

1. **按有证据的规则实现，不另建物理：** 不引入通用物理或刚体引擎，沿用 P3-02 的固定步长与数值策略。若连续驾驶不满足已批准的保真判据，必须修正规则或重新批准相关时间契约，不能标为“R-01 已知差异”后放行。
2. **条件化计算与持续运动分别验收：** 离散分支精确核对，连续量使用有来源的误差预算，不要求未经依据的逐指令/逐位一致，也不采用人为替换 sin/cos、只用最大单帧步长推断整段误差的判据；具体数值判据在[检查点 B](#执行检查点)定稿。
3. **机型数据作为世界创建输入（D-01）：** 运动直接依赖机型记录，因此作为初始数据进入 setupHash，使 replay 绑定实际读取的机型数据。P3-07 共用同一输入。
4. **拆分 `flight` 分区（D-05）：** 运动与战斗分区可独立表达可用性；这只消除读模型的人为耦合，不消除最高速度、目标、停放运动等真实规则依赖。开发期初值有明确标识，不能被完整玩法消费者误认为已验收的实时规则。
5. **目标引用归属（D-03）：** P3-06 提供一个共享引用及其生命周期，选择归 P3-07。检查点 A 按 M-09 定稿：实例化时玩家目标为空有代码证据（`0x68050` 写的是 AI 目标），首次可操纵更新后的目标来自 P3-07 的自动选择，不依赖 P3-08。该归属随检查点 A 的 P3-02 修订批准。
6. **跨任务的输入分阶段接入：** 允许先验证消费者纯函数，不允许将缺失状态替换成常量后声称生产闭环完整。对未接入的实时能量、AI/目标或 Warp 输入，保留明确缺项和集成验收；不得通过安排假系统解除依赖。若原任务拆分确实无法完成其既定责任，先修订并批准相关任务的边界，不暗增环形依赖。检查点 A 据此把实例化时的 `0x68050` 移入 P3-06，解除停放运动与 P3-08 之间的环形依赖。
7. **自动驾驶延至 P4（G-09，检查点 C 已定）：** 阶段索引允许 P3-06 决定其范围。先完成手动飞行、速度控制与已要求的辅助，避免把完整 AI 驾驶拉进本任务。M-06 证实其非必需：每个新的玩家对象自动驾驶为关；只有飞行中按 `a` 且有有效目标时才开启；碰撞、救援与程序自身只会关闭；所选任务的生成、流程、救援、停靠、Warp 与地图都不开启它，任务流程、结果与失败代码中也没有它的读者（[自动驾驶](../../../original/formats/executable.md#world-boundary-active-area-parking-and-autopilot-p3-0604)）。Core 不提供自动驾驶命令，规则总走“自动驾驶关闭”的分支。

   检查点 C 写入 P3-01 [缺省清单](../01/spec.md#缺省清单)的条目：

   | ID | 缺省或替代 | P3 中的呈现 | 依据 | 补齐阶段 |
   |---|---|---|---|---|
   | G-09 | 自动驾驶（`a`） | P3-05 拦截 `a` 并显示暂缺标注；Core 没有自动驾驶命令，不提供假成功 | M-06（P3-06/04）：闭环不依赖它，没有流程自动开启它 | P4 |

   不复用 G-08 的授权；编号已核对不冲突。
8. **灵敏度固定为 Medium（G-10，检查点 C 已定）：**
   - 原版的灵敏度只作用于非零的摇杆偏转，原版键盘不产生偏转，所以对原版的键盘配置没有影响（M-03）。但按[操纵](#操纵)定稿的推荐映射，项目轴作为整数路径上的数字摇杆经过灵敏度表：Low 档会降低满偏转向率。因此切片固定为 Medium（原版默认、基准配置与 README 的缺省），由代码计算的表实现并绑定规则版本，不读取可变的本机配置作为权威初值。
   - 原版飞行中按 F11 在 Low、Medium、High 之间循环并显示消息；P3 不提供这一切换：

     | ID | 缺省或替代 | P3 中的呈现 | 依据 | 补齐阶段 |
     |---|---|---|---|---|
     | G-10 | 飞行中切换操纵灵敏度（F11） | 固定为 Medium；P3-05 拦截 F11 并显示暂缺标注 | M-03（P3-06/02）：原版飞行中可用 F11 切换；项目轴经原版整数路径与灵敏度表，切换会改变项目操纵 | P4 |

   - 被排除的方案：绕过灵敏度表的映射（不需要 G-10，但偏离原版摇杆路径，须记为差异）；按 High 线性表（与 Medium 在满偏时相同，但非满偏的轴值不同，且不是原版默认）。
   - 不增加未要求的通用设置系统、Gamepad 或键位重映射。
9. **保持逐 tick 动作边界：** 轴快照每 tick 消费；所有合法离散命令按数组顺序判定，不等 DOS 轮询、不模仿丢弃队列。真实冷却与辅助到期仍属于 Core 规则。原版输入采样与项目动作边界的操控差异必须对照，必要调整回到共享契约审批。
10. **中立输入与地图门禁优先：** 不保留会在清键、恢复或关闭地图后复活的旧手动轴。冻结的是 Runtime 暂停期间的游戏状态；地图不暂停，零手动轴不等于速度归零，也不清除独立的自动规则。原版在地图与基地中保持旧转向；本项的防御性归零是有意差异，计入 R-04c。
11. **常量与表的分类：**
    - 运动代码中的标量常量，以及由代码在启动时计算的表，是代码规则，在 Core 中独立实现（同 [P3-01/10 决定表](../01/subtasks/10-data-closure.md#完成证据)第 32 行）。
    - 对存储表不能仅凭“位于 EXE 数据段”定类：已有闭包也把掩码、周期等列为代码规则。先沿用已批准分类；未分类的表按内容用途与证据补齐闭包决定。确需新导入时，修订并批准 P3-03 后交付，不抄原版表或文字作为源码常量。
12. **舍入方向沿用 P3-02 的决定：** f32 写回就近舍入。R-04a 的逐帧读数会揭示飞行中运动写回的实际舍入。若有帧只与向零舍入一致，相应验收暂停，执行者按证据给出推荐方案，按[执行检查点](#执行检查点)的授权修订 P3-02 的数值策略与本 spec 并记录理由（与 P3-02/14 的处理相同），不在代码中悄悄改变全局数值策略。
13. **按检查点定稿：** 方向、规则与验收在开始前定；只有研究才能回答的事实（完整状态形状、数值容差、缺省项是否成立）在[执行检查点](#执行检查点)以 spec 修订定稿。理由：现在定稿只能靠猜，违反“不按猜测实现”；不在固定检查点记录、边做边改共享契约，会让 P3-07 等并行任务返工。用户 2026-10-09 进一步授权：检查点 A、B、C 的修订，以及改变已定方向的修订，按推荐答案直接定稿，不需逐次审阅；授权的边界见执行检查点一节。

技术决定 1 至 12 按用户 2026-10-09 生成与审阅时“直接用你最推荐的答案”的授权写入；技术决定 13 是用户同日选定的处理方式（“根据你的建议，我们再改改spec”），其中的预先授权来自用户同日对 goal 的修改与批准（“i made some change. approve and commit”）。这些授权不涵盖总计划与 ADR 中的冻结决定。
