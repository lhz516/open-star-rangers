## 完成证据

2026-10-09，worker `exec-p3-02-01`（基于认领提交 `44472e4`）。只读静态分析，不涉及浏览器或基准运行。

- **方法：** Ghidra 12.0.1 以 `-noanalysis -readOnly` 打开项目的私有副本（`local/research/p3-02/pipeline/ghidra/`），内存中建立的函数与 `__watcall` 均丢弃，没有 `-overwrite`。顺序、比较、状态值与寄存器参数按原生指令核对；调用方用相对调用与 32 位值的原始扫描核对；“循环之后不投递消息”与“更新回调中会分配对象”用直接调用的可达性搜索核对（经指针的回调不在搜索内，文中已写明）。脚本与输出在被忽略的 `local/research/p3-02/pipeline/`（`ghidra_scripts/PipeProbe.java`、`probe.sh`、`out/p1.txt`–`out/p41.txt`、`check-links.ts`）。
- **Q-08（已确认，代码）：** 事实见 [对象表](../../../../original/formats/executable.md#runtime-object-table-p3-0201)。结论：新对象追加在种类表表尾；遍历按种类位升序、同种类按分配次序，且下一个节点在推进时才读取；移除只经消息 0x20、在派发器消息循环中进行，节点失效后由持有者检查；移除不改动来源记录的计数与名称记录。分配器没有规则上限，内存耗尽时程序退出；实例化中唯一的分配后拒绝（扇区资源检查）何时发生未确定（未确认），不属于规则结果。因此 `CoreLimits` 是项目的故障预算，在原版中没有对应的规则结果。
- **Q-09（已确认，代码）：** 事实见 [帧流水线](../../../../original/formats/executable.md#frame-pipeline-p3-0201)。结论：消息不跨帧；处理过程中新投递的消息在同一遍、排在更早的消息之后处理，循环之后投递的消息被丢弃；玩家回调在 `0x20938` 中最先；本 tick 生成的对象不倒回阶段 4，在生成的这一 tick 也不运动、不参与碰撞。与 [spec 阶段表](../spec.md#系统流水线)的逐条对照：

  | spec 阶段 | 原版 | 结论 |
  |---|---|---|
  | 1 输入登记 | 没有独立阶段，输入在阶段 4 由玩家对象的更新回调读取 | 一致（项目边界） |
  | 2 任务流程 `0x3266c` | 每帧第一步，开头先清空派发器消息表 | 一致 |
  | 3 时钟 `0x25894` | 同上 | 一致 |
  | 4 对象更新 `0x20938` | 按种类位、再按分配次序，玩家最先；遍历中分配到更高种类位的对象在同一遍更新（可达路径：AI 的 `0x62aa0` → `0x38780`，种类 `0x4000`） | **冲突**：spec 写“遍历 tick 开始时的实体” |
  | 5 派发器 | 队列检查只投递生成请求，实例化在消息循环中、排在本帧更早投递的消息之后；循环之后的次序已确认，其中 Warp 完成与爆炸到期都在运动之后 | **部分冲突**：spec 写“先生成，后处理消息” |
  | 6 帧尾规则推进 | `0x50508` 在渲染中推进 Warp，下一帧派发器中的 `0x2bf08` 检查 | 一致 |
  | 7 移除与提交 | 没有帧尾移除：对象在被标记后的下一次更新回调之后、该帧的阶段 5 经消息 0x20 移除；在阶段 5 及之后被标记（毁伤、离开世界、区域检查）则晚一帧，其间仍在种类表中 | **冲突**：移除的时机与阶段 |

- **Q-10（已确认，代码）：** 事实见 [输入轮询](../../../../original/formats/executable.md#input-polling-p3-0201)。结论：游戏输入只在玩家对象的更新回调中、玩家未被毁时读取；按键上下文在每次轮询时按视角模式选择；轮询在取样严格超过到期时刻时进行，不追赶，每次最多一个键，其余丢弃；主炮是两次设备读取之间保持的电平，导弹是单次请求，二者都在每帧的回调中处理；切换地图、Warp 与视角都不清空缓冲，只有过场会清空；主炮电平与摇杆轴在地图、Warp 与基地中不更新。被毁序列中不轮询游戏按键，F1 等视角键不能离开被毁视角，这更正了 P3-01/09 的已确认结论（executable 中两处已改）。动作形状没有发现不足。
