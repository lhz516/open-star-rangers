# P3-11：任务事件、结果、救援与重试 — Spec

## 问题与目标

P3-02 至 P3-10 已经交付正式 Core、Runtime、原版键位、飞行、战斗、AI、地图与 Warp、通讯与停靠。但闭环的 L-09“任务结果”与 L-10“重试或返回”（[P3-01 闭环步骤](../01/spec.md#闭环步骤)）还不能走通：

- **任务流程没有终态。** [world-state.ts](../../../../src/core/world/world-state.ts) 中，`MissionStatus` 只有 `built`，`flow.mainState` 只有 3，`MissionSubState` 只有 P3-10 的 0、3、4、5。[pipeline.ts](../../../../src/core/systems/pipeline.ts) 的 `mission-flow` 阶段只运行停靠检查，`mission-teardown` 阶段为空。
- **CR-13 调用点只是注释。** [P3-02 的 CR-13](../02/spec.md#cr-13-其他任务在-p3-07-规则中的调用点d-03-之外的接口)为本任务保留了 `0x6977c`、`0x32d74`、`0x32dec`、`0x33464`、`0x32e14(1)`、`0x339cc` 与救援 `0x67b98`，目前只在 [damage.ts](../../../../src/core/systems/damage.ts)、[destruction.ts](../../../../src/core/systems/destruction.ts)、[energy.ts](../../../../src/core/systems/energy.ts)、[launch.ts](../../../../src/core/systems/launch.ts) 与 [spawn.ts](../../../../src/core/systems/spawn.ts) 中以注释标出。
- **玩家被毁后流程停住。** 玩家被毁后，爆炸、逃生舱与跟随都会照常发生；逃生舱到期后，玩家停在被毁状态，既不救援也不失败（[Core 交接](../../../engineering/modules/core.md#交接)）。
- **段 2 事件触发没有进入规则。** `MissionSetup.eventTriggers` 由 [load-mission.ts](../../../../src/core/mission/load-mission.ts) 原样透传，没有计数，也没有被读取。
- **`result` 分区未实现。** 该分区恒为 `not-implemented`，`ResultReason` 与 `ResultMessageReference` 仍是 `never` 占位（[projection.ts](../../../../src/core/projections/projection.ts)）。
- **应用流程没有结果位置。** [mission-flow.ts](../../../../src/app/mission/mission-flow.ts) 没有结果位置，`MissionEndReason` 只有故障、停止与清理失败。[P3-04 流程表](../04/spec.md#应用流程)中“结果（P3-11 接入）”一行为空。运行中衔接只覆盖 G-02/3、G-02/4（[P3-04 运行中衔接](../04/spec.md#运行中衔接p3-10-的修订)）。
- **没有结果页。** G-06 的文案写明“尚无结果页”（[slice-gaps-copy.ts](../../../../src/ui/mission/slice-gaps-copy.ts)）。
- **原版证据尚未覆盖完整结果链。** 已有成功页面的用户观察、规则的代码证据，以及 P3-07 的被毁至逃生舱到期读数；它们不能合称为成功、救援和失败均已运行对照。所选任务中正常玩法的失败路径仍为高概率（[U-031](../../../original/unknowns.md)），缺口按证据适用范围核实。

完成后可观察到：

- 在 Node 中，用合成内容或本地真实内容创建的世界会按原版规则推进任务流程：
  - 段 2 事件触发计数对象事件。
  - 无存活或待生成的敌方类对象时，合格的对象事件触发全清；经过流程门禁、结算等待（Warp 中推迟）、完成消息与结果延时，锁存成功，再退场。
  - 主流程仍在任务进行中时，玩家被毁进入被毁视角，逃生舱到期后进入损失处理。同一次尝试中前两次处理为救援，第三次为失败；能量耗尽经信标等待进入同一入口。全清标志、主流程阶段与损失处理的先后不能简化成“最后敌机死亡后再无失败”。
  - 僚机损失设置 30 个名义秒的计时；只在允许的流程状态下排入无线电消息。
  - 全程以带 tick 的领域事件与 `result` 分区呈现。
- 在浏览器中，救援显示可跳过的 G-02/5、G-02/6 占位，之后同一关继续。任务结束时依次显示 G-02/7 至 G-02/9 中适用的占位，再进入明确标注的项目结果页（G-06）。结果页显示结果、规则原因与成功时的任务总结，可经 [P3-04 的重开路径](../04/spec.md#应用流程)重试，也可返回菜单。
- 同一内容、配置、种子与输入在同一运行时 replay 一致，与占位显示多久、是否跳过无关。
- 原版事实写入 `docs/original/`。R-20 至 R-22（[规则对照目录](../01/spec.md#规则对照目录)）优先复用已有代码、数据与合格运行；新运行优先合并取证，仅补无法闭合的必需缺口。失败链以一次集中运行作为首选方案，不承诺一次必然足够，也不因减少 DOSBox 而自动豁免验收（[对照方法与判据](#对照方法与判据)）。

阶段范围依据[总计划 §12](../../master-plan.md#12-开发阶段与验收条件)，任务导航见[阶段索引](../tasks.md#p3-11-任务事件结果救援与重试)。生成、审阅或批准本 spec 都不会自动启动实现。本任务沿用 [P3-01 的切片配置](../01/spec.md#切片配置)：战役 group 0 / slot 1（SCEN 3019）、原始难度 19、僚机可选。

### 任务流程状态

每次运行只构建一个任务。依用户本轮选择，Core **保留主状态 0/1 与既有退场阶段**，结果锁存之后完成清理，再停止 step；不循环进入下一关。主状态 2 的页面与新世界创建仍由 app 拥有，重试是新的世界（L-10）。这是单任务的项目边界，不声称原版退场状态不可达。

| 状态 | 原版 | Core 中的取值与职责 |
|---|---|---|
| 主状态 3 | 任务进行中 | 子状态 0：轮询任务状态，然后检查僚机损失计时。子状态 1：信标等待。子状态 2：被毁序列，不轮询。子状态 3–5：P3-10 的停靠 |
| 主状态 4 | 全清后的结算等待 | 每 0x140 单位检查一次；玩家在 Warp 中时再推迟 |
| 主状态 5 | 结果延时 | 到期时按预结算锁存成功或结算失败，转入退场；不实现调试结果入口 |
| 主状态 0/1 | 结果处理后退场；等待对象全部移除 | 在原定 `mission-teardown` 位置标记对象退场，通过既有生命周期移除；状态 1 的生成/发射门禁生效。清理包括玩家、僚机、弹体、爆炸、逃生舱、地图标记、AI 控制器与共享缓存引用 |
| 完成 | 原版随后进入下一任务的出发流程 | Core 不进入状态 2；清理完成后的提交边界发布最终结果，Runtime 截断后续 tick，app 显示终局占位和结果页 |
| 子状态 6 | 结束战役的请求 | 不加入。P3 没有结束战役的入口，不可达 |

- **谓词：** `inMission`、`0x3336c` 与 `0x33390` 按 CB-02 的原条件读取新的取值。`0x339cc` 在主状态 1 拒绝对应生成与发射请求；不能因平时总在状态 3 就实现成常真。
- **次序：** `mission-flow` 读上一 tick 的取样（C3）。在子状态 0 中，先检查任务状态，再检查僚机损失计时；与 P3-10 停靠分派的次序按 `0x3266c` 的跳转表实现（Q-01）。
- **到期比较：** 每条比较的 u32 视图、严格与否按 Q-11 逐条确认，不统一套用一种（已确认：主状态 4、5 为严格的 >，僚机计时、信标与停靠为 ≥，见 [ME-03](../02/spec.md#p3-11-的契约修订d-01)）。
- **三个时点分开：** 全清标志（停止生成）、预结算（状态 3→4 时确定总结）、结果锁存（成功处理或第三次损失），均不等于退场完成。锁存后的结果摘要不再受同 tick 的剩余更新或退场事件影响；退场完成前仍按已批准阶段表推进。D-01 必须明确每种入口当 tick 的剩余阶段、命令与请求结算、清理路径和最后提交，不允许临时加一个中途 return 跳过流水线。
- **命令与错误：** 锁存后不再接受改变玩法的新意图；已进入当前 tick 的合法命令仍各有一个结果，退场时不执行的命令使用定稿的封闭原因。尚未进入 step 的 Runtime 队列项才是取消通知，不能对同一命令同时报告执行与取消。故障优先于完成，清理失败不能用结果页掩盖。
- **清理范围：** 活实体归零，AI 控制器及共享缓存的活引用释放，玩家/地图等读模型正确转为无实体；历史事件、来源记录和冻结摘要可按既有契约保留不可再解析的旧 ID，不要求反向遍历所有字段清零，也不删除用于结果或 replay 的静态内容。

### 段 2 事件触发与任务总结

- **对象事件 `0x6977c`：** 在 CR-13 的位置接入，事件类型为：3 = 实例化，0 = 被玩家消灭，1 = 被其他原因消灭，2 = 离开世界（P3-06 的 `object-left-world`）。
  - 按对象的来源记录 +0x54 找到触发，增加该触发的实例化、被毁或离开计数。
  - 按 Q-02 核对按种类的记录（`0x1b45b4`）以及基地/民用类标志（`0x176744`、`0x176748`）的全部事件写入者；只为本任务所需的读者建状态，不能把被毁后的变化遗漏成“只在实例化时标记”。Q-02/Q-08 的结论：它们只有 `0x69e1c`（勋章）或没有读者，不建模（ME-01）。
  - Q-02 区分玩家、声明对象与无来源的动态对象；不得预设“玩家事件全不计”。P3-08 已交接的动态 Xpon 析构不报告 `0x6977c`，不因它也发 `object-destroyed` 就重复送入任务计数。
  - 被毁计数在 CR-13 的 `0x3c0f4` 之后立即完成；实例化与世界出口在各自原定调用点处理。内部对象通知不等于扫描一遍外发事件：不得重复增加击杀、把退场移除当被毁，或用已移除对象回查来源。
- **计数与生成配对：** 原版的 `0x695c0` 在计数后检查生成配对；当前原始解析边界已拒绝这条路径，规范模型不表达配对。Core 实现支持范围内的计数，不新增配对字段或重复读取原始数据。
- **任务总结（`0x69c54`，成功时）：** 先找到按段顺序第一个实例化或被毁计数非零的触发；按 Q-03 核实的比例公式取截断后的比例，选出第一个包含它的区间；若没有区间包含它，就转到下一个触发。
  - 选中区间的消息按次序拼接，就是任务总结。总结选择字节决定 G-02/9（所选任务只有比例 99–100 的区间带它，对应 `BASELOSS`）。
  - Core 只记录触发号与区间号的引用，不复制文字；文字由 UI 从导入内容中解析（总计划 §5 的状态与事件边界）。
  - 状态 3→4 时固定这份选择，结果延时期间基地继续受损不重新选择总结。没有匹配区间时为显式的无总结；空消息列表不等于缺失内容，仍保留选择字节。拼接按数组顺序、无自动分隔符。通过校验的消息是字节字符串，显示沿用项目内容解码约定，不当作 HTML。
  - `0x69e1c` 读取出现标志与重伤记录。Q-03 已核实它只影响勋章，不改变总结、选择字节或过场，记为 P4 的范围；`heavyDamage` 只供 P4（ME-17 决定 9）。
  - **创建时检查：** 总结选择值只接受 ≤ 0 与 13–19，其余值在 Core 创建时拒绝（ME-02、ME-17 决定 5）。
- **显示的时机与位置：** 区间消息不是飞行中的消息。原版只在成功后、下一关出发前页面 0xF 的第一章显示它们（已确认，代码；页面的绘制未追踪）。P3 没有下一关，因此在 G-06 的项目结果页上显示，并标注为“原版在下一关出发前显示的任务总结”（[结果页、重试与返回](#结果页重试与返回)）。

### 全清与成功

- **全清判定（`0x69a70`）：** 只要还有任一以下对象，就没有全清：
  - 种类在 `0x91780` 中的存活对象，且未被毁、对象状态不为 6，不含正被报告的对象（入口与全清的种类集合都由 `craftType` 即 `kindBit` 推导，`side` 过粗，不能代替）；
  - 生成队列中来源为这类种类的待生成项。

  原版入口要求敌方掩码 `0x93780` 的对象报告事件 0–2、头部 0x0C 为零且任务未结束；当前规范模型只表达已排除特殊模式/配对的支持集。Core 按该支持集实现入口，不另读原始头字段。没有剩余时同一阶段内置结束标志并调用 `disableSpawning`。
- **结算：** 主状态 3、子状态 0 看到任务状态为结束时，重新运行全清判定，保存预结算结果与任务总结引用，并进入主状态 4（0x140 单位后到期）。此时对外仍是进行中，不提前展示最终结果。
  - 主状态 4 到期时，若玩家视角为 1（Warp）就再推迟 0x140；否则发出完成消息事件（消息为 `data/flight-messages` 的完成消息），进入主状态 5（0x3C0 单位后到期）。
  - 主状态 5 到期时锁存成功结果，再退场。
  - 主状态 4、5 中模拟照常：玩家仍可飞行、开火、开地图与 Warp，也仍可能被毁，但不救援也不失败。
- **完成消息：** Core 发出带消息身份的一次性事件，不保存显示中的文字与剩余时间。消息行的位置、颜色、显示时长与绘制归 P3-13；Q-09 把 `0x4e9e8` 调用点的常量交给 P3-13。
- **成功的 G-02 变体：** 终态记录两项：
  - **返航变体：** 锁存时僚机列表首项存在且**对象状态** +3 ≥ 7 时为 `wingman`，否则为 `solo`（[成功列表](../../../original/formats/executable.md#cut-scenes-and-loop-transitions-p3-0108)，已确认，代码）。不是活动字段 +2，也不改成额外的船体、被毁或距离判断；依据结束时的对象，不依据出发选择。
  - **任务过场：** 总结选择字节为正时为该行（所选任务为 `BASELOSS`，G-02/9），否则为无。

  勋章行不判定（[勋章、统计与战役进度](#勋章统计与战役进度)）。

### 玩家损失：被毁与能量耗尽

- **被毁（`0x32d74`）：** 按 CR-13 在对象事件之后、爆炸构造之前调用；条件是主状态 3 且子状态不为 2。必要效果如下，精确写入次序由 Q-04 核实：
  - 子状态 2；
  - 调用者写视角 0x11、子模式 8，上一视角也写为 0x11（原版两次写入，Q-04），并按原版入口清除玩家目标，再用 `switchView` 处理左显示页副作用；它取代地图与 Warp（视角已是 0x11/8 时的无变化分支照原条件）；
  - 清空无线电队列，左显示屏回到页 0（`0x2cd20`），`radio-flushed` 加入新的原因；
  - 停靠对象置为 null。

  确切的次序与停靠中被毁时活动字段是否保留，按 Q-04 核实（DK4 交来的 U-031 问题）。
- **被毁序列：** P3-07 已交付爆炸延时 0xC0 与逃生舱（玩家模型第 1 列表的部件 0，高概率）。逃生舱在第一次更新后 0x140 单位到期，然后清除 `followedEntity`。本任务在这之后、逃生舱进入待移除之前调用 `0x32e14(1)`，同一 tick 的其余阶段看到救援后的玩家（CR-13、C3）。
  - F1 不能绕过玩家不可用门禁；其他命令保留 P3-05/P3-09 已批准的优先级与项目差异。`p` 暂停及任务菜单/退出仍走 Runtime 控制，不进入 Core 命令队列。
  - Warp 被放弃时不到达、不扣费，`inWarp` 保持不变（MW-09）。
- **能量耗尽（`0x33464`）：** 位于能量更新的耗尽分支，在钳到 0 之后。只在主状态 3、子状态 0 时生效：
  - 发出信标消息事件（`data/flight-messages` 的信标消息；原版经 `0x4e9e8` 排入消息行，其 0x3C0 是未画出时的过期时间，不是显示时长，显示由滚动决定，归 P3-13）；
  - 进入子状态 1，到期时刻为当前取样加 0x3C0。

  子状态未变时，之后的耗尽更新不再重设。到期以上一 tick 的取样比较，先进入子状态 2 并 `flushRadio`，再调用 `0x32e14(0)`（C3，已确认，代码）。若等待中被毁，则被毁入口覆盖子状态，旧信标期限失效，只沿逃生舱路径处理一次损失。
  - 信标等待中保持当时的视角，飞行命令照常判定。无能量时各命令的实际效果，以及停靠请求 `0x333b4` 能否覆盖子状态 1，按 Q-06 核实。
  - 地图在信标等待中仍可打开（B-001）。
  - 入口接在**每次**耗尽更新的钳零之后，不订阅只发一次的 `energy-depleted`。否则停靠覆盖子状态、救援后仍有耗尽锁存等情况下会漏报；按 Q-06 明确重新进入正常子状态后的重触发，测试混合损失链。

### 救援

- **入口（`0x32e14(p)`）：** 主状态不为 3 时什么都不做。救援计数为 0 或 1 时救援；为 2 时判为失败（[失败](#失败)）。`p` = 1 表示被毁，0 表示能量耗尽。
- **恢复玩家（已确认部分按 D7、C3、Q4；Q-05 补齐整条调用链）：**
  - 清除被毁标志并取得机型记录，依次 `fullRepair` → `rebuildWeaponBlock` → `initialiseResources`；不能先重建挂点再修理，也不能最后完全修理覆盖来源记录的资源百分比。区分 `0x67b98` 本身与外层 `0x32e14` 的写入。
  - 战役中且救援计数 < 2 时清除两个玩家限频（`clearCommunicationLimits`）。
  - 视角与上一视角都设为 0xC。
  - 外层恢复对象状态、重同步移动块与最高速度；油门按旧速度比例重算（Q-05），不直接替换为新任务初值。能量救援在 `mission-flow`，被毁救援在请求处理中；Q-05 核实两处的挂点选择消息都在消息循环结束前被处理，发出相同的 `weapon-selected`（ME-18 改写 `fullRepair` 标志的含义）。
  - 原版会改写玩家的运行时来源记录位置及放置引用（Q4）。在 [spawn-state.ts](../../../../src/core/world/spawn-state.ts) 的私有 `RuntimeRecord` 或经 D-01 定稿的等价状态中表达并进入快照；不能回写冻结的 `MissionSetup`、导入 payload 或 setupHash。每次非连续放置增加 `placementSerial`。
- **放置：** 统计种类在 `0x68000` 中、仍在实体表中的全部对象（不看状态、活动、被毁标志与待移除，Q-05 的更正），用世界 RNG 按 `rand() % count` 选出一个，再按 Q-05 核实的偏移与朝向放在它附近；没有这类对象时使用世界范围的缺省放置。
  - 不按距离选择，所以“最近的基地”只是巧合。
  - RNG 的取值域、取模原像数、支持集、条件抽取与先后按原版映射核对；取模不能写成严格均匀，尤其要覆盖 0、1 与多个候选。
- **保留边界：** 救援入口本身不重置其他对象、生成队列、任务状态、段 2 计数、击杀与射击计数、重伤记录和 AI 控制器（Q4）；玩家实体 ID 复用。这不表示整个 tick 其他系统停止更新，也不否认入口前已清空通讯、外层清限频及视角切换的效果。来源记录、对象活动与 `inWarp` 等逐字段按 Q-05/已批准契约处理，不笼统宣称“停靠以外的通讯状态全不变”。
- **之后：** 子状态 0，救援计数加 1，同一关继续。发出 `transition`（`gap` 为 G-02/5 或 G-02/6），由 Runtime 保持（[运行中与终局衔接](#运行中与终局衔接)）。
  - 原版在恢复玩家前播放列表。位于请求处理中的被毁救援用时进入下一轮取样；位于 `mission-flow` 中的能量救援用时进入本轮随后的取样（C3）。文件头给出的名义媒体时长不是运行测量。
  - Core 接纳 [P3-02 技术决定 2](../02/spec.md#技术决定)，省略媒体用时；只能说明媒体时长采用零值，不能据此宣称固定步长与关闭过场的原版整个世界状态等价。
- **救援船：** 不生成任何对象。

### 失败

- **第三次损失：** 主流程仍为 3 时的第三次损失处理（被毁或能量耗尽）。计数已为 2 时置结束标志并锁存失败，再退场；原因带损失类型，决定 G-02/7 的变体。主状态 4/5 中不进入这条入口。
- **主状态 5 的失败分支（研究推翻原前提）：** 01 证明它在正常玩法中可达：导弹击毁最后一个存活敌机恰与某编组到期同帧时，生成请求已移出队列而尚未处理，全清成立后该编组仍被实例化，下一次预结算判为失败（[State-5 failure in normal play](../../../original/formats/executable.md#state-5-failure-in-normal-play-p3-1101)）。D-01 定为照原版复现：原因为 `settlement-failed`，G-02/7 取被毁变体（原版以 p = 1 调用失败处理），不附“第三次损失”原因（[D-01 定稿](#d-01-定稿已批准)第 1 条）。调试结果入口不实现。
- **不是失败：** 以下情形都不判为失败：
  - 基地全部失去（只影响总结与 G-02/9）、僚机损失、任务时长；
  - 主状态 4、5 中的损失；
  - 任务菜单的重开与返回主菜单；
  - Runtime 故障或录制容量停止。

  不复用练习模式“被毁即失败”的分支。
- **失败之后：** P3 先锁存摘要、再退场，之后以 G-06 结果页代替原版页面。重试采用 P3-04 的独立切片实例路径，只在“重玩同一任务”这一点对应原版提示；不宣称战役统计保留与随机状态等价。

### 僚机损失计时

- 僚机（种类 2）被毁时，在停放判定与爆炸构造之前调用 `0x32dec`：只在标志为 0 时设置标志，到期时刻为当前取样加 0x780 单位（30 秒）。
- 只在主状态 3、子状态 0 中，在检查任务状态之后检查是否到期（上一 tick 的取样，非严格比较）。到期后清除标志，经 P3-10 的 `queueRadio` 排入表 20983 第 6 项的消息。
- 全清先到时，这条消息被丢弃。子状态 1–5 期间推迟。它不是任务结束条件。

### 结果读模型、事件与门禁

- **`mission` 分区：** 任务状态与流程阶段（正常、被毁序列、信标等待、停靠、结算等待、结果延时、退场、完成）。飞行中不额外显示救援计数、触发计数、未见敌机或到期时刻；诊断快照与玩家可见信息分开。
- **`result` 分区：**
  - 规则运行与退场期间为 `in-progress`，由 `mission` 阶段区分；内部预结算/锁存状态不能被 app 误当成可显示的最终结果。
  - 锁存时保存结果 success 或 failure、规则原因（全清、第三次损失及其损失类型，或结算失败）、任务总结引用（无匹配或失败为 null）、已用救援次数、终局 G-02 序列与玩家击杀合计；**退场完成后**才公开终态。
  - 原版成功/失败处理会清零救援计数；结果页的 `rescuesUsed` 是清零前冻结的项目摘要，不是继续参与规则的计数。同样，玩家删除后不能再从实体反算击杀。Q-08/D-01 明确锁存与复位的顺序。
  - 总结引用绑定本次任务 Asset ID 与触发/区间索引，不是裸的原版地址、文字或任意 URL。有效的空总结与解析失败分开；后者显示结构化错误，不默默隐藏。

  `ResultReason` 与 `ResultMessageReference` 由 D-01 定为封闭联合，不用开放载荷。
- **领域事件（D-01 定稿名称与字段）：** 每个事件都继承 `{ type, tick }`，加入比较器的逐字段读取：
  - 段 2 计数是权威快照状态；仅有真实消费者时才增加专门通知，不把内部计数全部暴露到生产画面；
  - 全清、进入结算等待、完成消息、结果锁存与退场完成；事件名与消费者在 D-01 中固定，避免两个“结束”事实混用；
  - 被毁序列开始、信标开始、救援（带选中的基地 ID、放置后的位置快照与救援次数）；
  - 僚机损失计时的设置与到期；
  - `transition` 的 G-02/5、G-02/6。

  一次性反馈（完成消息、信标消息）用事件；需要持续显示或判定的事实用状态。UI 不靠累积事件重建状态。P3-13 拥有消息行的有界显示队列及其时间语义，Core 的消息事件只带封闭消息键、tick/逻辑时刻等必要元数据；P3-13 在运行绑定时装配已导入的 `FlightMessages`，不为文字显示把原版字节加入 Core 快照或录制。
- **门禁：** `0x339cc` 见[任务流程状态](#任务流程状态)。P3-10 的 `0x3336c`、`0x33390` 读到子状态 1、2 时照原条件生效（例如被毁序列中无线电不取出，近处菜单不可用）。

### 运行中与终局衔接

本节是对 [P3-04 运行中衔接](../04/spec.md#运行中衔接p3-10-的修订)的修订方向，在 D-01 中同步定稿 P3-04 spec，不是已经批准的 API。

- **救援（G-02/5、G-02/6）：** 复用 P3-10 的设施，`gap` 联合加入两项。
  - 含 `transition` 的 tick 是本帧的最后一个 tick；会话立起屏障、取消未执行的命令、折叠两帧 Render State，再逐项保持。
  - 每项有独立的 `transitionId` 与凭证，结束后重锚时钟，不补跑。
  - 同一 tick 中救援与停靠或离港的衔接共存时，按事件次序组成有限序列；D-01 依据 Q-04、Q-05 复核后，救援衔接每 tick 至多 1 个且不与停靠或离港同 tick，上限仍为 2（ME-13）。
  - 占位显示的变体只用于标注，规则在 Core 中已经完成。
- **终局：** 结果锁存后先完成 Core 退场，**退场完成的提交 tick** 是本运行最后一个 tick。
  - Runtime 直接依据该次成功 step 的有类型完成输出/读模型截断，不通过 Event Bus 监听器调用控制。帧后派发之前先立起完成屏障，监听器不能再提交输入或重入生命周期；`FrameReport` 明确实际 tick 数、完成截断原因与结果，不冒充录制容量停止或故障。
  - 当前 tick 已执行的命令正常结算，Runtime 尚未交给 step 的命令取消一次；清输入、停止游戏 rAF、折叠两帧 Render State 后，在安全通知边界进入结果阶段。不得先销毁世界再试图读取最终结果/检查点。
  - 完成与运行中衔接同 tick 出现时，完成决定“不恢复模拟”；保留该 tick 已发生衔接的顺序，再接终局序列，不能重复同一终局占位。D-01 核实：锁存与完成的 tick 都没有运行中衔接，终局序列至多 2 项（ME-13、[P3-04 的终局](../04/spec.md#终局与救援衔接p3-11-的修订)）；违反为故障，不静默截断。
  - 会话按冻结数据逐项显示终局占位（失败为 G-02/7；成功为 G-02/8，以及适用时的 G-02/9），每项有绑定 ownerId/runId/transitionId 的一次性完成凭证，然后进入结果页。
  - 终局占位不恢复模拟，也不写 Core。
  - 故障、退出/释放、完成、普通保持的优先关系在 D-01 中完整列出；消费者、计时器、内容解析或清理失败不能被健康结果覆盖。终局没有需要恢复的模拟，不提供“继续飞行”；隐藏仍暂停占位的可见时间，不自动抢焦点。重试后的新运行仍受原有隐藏恢复保护。
- **录制与 replay：** 录制包含结果锁存与全部退场 tick，并在完成提交处结束；最终检查点不因恰好落在检查点间隔上而丢失或重复。健康完成的开发录制在重试/退出前可导出，故障录制保持禁止。replay 拒绝完成之后仍带 tick 的记录，不悄悄丢掉后缀；普通未完成前缀仍可作调试录制，不能冒称完整闭环。
- **生命周期：** 结果页保留只读运行数据及必要的资源包引用，停止游戏输入、Pointer/Keyboard Lock 等临时能力和播放消费者的活动；最终释放仍由既有 owner/run 所有者执行。重试复用 owner，但产生新 runId，旧 run 的输入、订阅、占位计时器与录制不会混入新运行。不得为结果页另建游戏循环。

### 结果页、重试与返回

- **结果页（G-06）：** 是任务壳中的 React 页面，经 projection → Zustand 桥接读取冻结的 `result`，终态立即发布。页面显示：
  - 成功或失败；
  - 规则原因的项目文字（全清；或第三次损失，区分被毁与能量耗尽）；
  - 已用救援次数与玩家击杀合计，标注为本次尝试的项目摘要，不冒充原版统计公式；
  - 成功时的任务总结：从导入内容解析区间消息，标注为原版在下一关出发前显示的总结。

  页面明确标注它代替原版的统计页、二选一提示、高分榜、晋升与勋章（P4）。项目文字集中在 `SLICE_GAPS` 所在的文件，不硬编码原版文字。内容按文本节点渲染，不执行 HTML；无总结时明确该分支没有总结，损坏/身份不匹配时显示失败原因。
- **操作：**
  - 重试走 P3-04 的重开路径：介绍占位 G-02/1 → 开始配置（预选上次的僚机）→ 出发；使用同一内容身份、固定难度与重新抽取的种子，不继承任何运行状态。原版在第一关重试时会重播 `C-INTALL`，对应 G-02/1。
  - 返回主菜单走 P3-04 的路径。

  两者都先失效并释放当前运行；清理失败沿用既有锁存。当前内容包被替换、缺失或新种子取得失败时不得偷偷切包/复用旧世界，按现有开始资格与创建错误反馈处理。
- **可访问性：** 页面保持 Classic 的 4:3 区域。进入时焦点移到结果标题，按钮可用键盘操作，状态不只靠颜色区分。隐藏时不抢焦点。
- **开始配置页的说明：** 按 [P3-04 决定 16](../04/spec.md#技术决定)复核 `MISSION_OBJECTIVES`：以项目文字概述成功条件（全部敌机被消灭或离开，之后经结算等待）以及救援与失败的规则（同一次尝试两次救援，结算等待中的损失不计），并标注置信度。不得写成“最后一架敌机死亡立即胜利”或“任何时候第三次损失都失败”；并说明结算时若有同帧新到达的敌机，任务判为失败（罕见）。

### 勋章、统计与战役进度

- **决定：** 所选任务在 P3 不判定勋章，G-06 明确披露“当前切片不判定勋章与晋升”；不是永久删除 P4 的功能。G-02/10 在本阶段不出现，依据 [P3-01/08 的处置选项](../01/subtasks/08-transition-media.md)。
- **理由：**
  - 勋章写在战役统计行（`0x3b8dc`，只由成功处理调用），属于 P3 不复刻的战役进度（G-06、U-014）。
  - 勋章的完整条件仍未追踪，不由不判定这一项目选择推导原版也没有勋章。
  - 原版只在没有任务过场时才考虑勋章。
- **有界核实（Q-08）：** 确认得分、统计行、勋章与晋升不回写任何影响本任务规则的状态，也不改变 G-02/8、G-02/9 与任务总结的选择。若核实不成立，先修订本 spec 再实现。
- **P4 交接：** `0x69e1c`、`0x3b8dc` 的勋章条件，以及得分与统计页的行对应，与 U-014 一起交给 P4。

### 数值、随机数与时序

- **时间：** 遵循 [P3-02 时间模型](../02/spec.md#时间模型)：时钟单位为 1/64 秒，生产中每 tick 2 单位。流程延时为 0xC0（3 秒）、0x140（5 秒）、0x3C0（15 秒）与 0x780（30 秒）。到期比较读哪一个取样、是否严格，按 Q-11 逐条确认。

#### 失败链运行

- **目的与身份：** 正常玩法、同一次尝试内取得损失→救援→损失→救援→第三次损失→失败的连续因果链。使用所选任务、难度 19、无僚机；读取任务身份、救援计数、结果/主流程状态，不以跨 run 拼接三次死亡证明可达性。观察与代码一致后，只升级实际覆盖的 U-031 结论。
- **配置与保护：** 优先复用 fixed 40000、HI 的基准设置及 `gameSettings` 的战役入口。记录 EXE/内容身份、媒体设置、配方指纹、cycles、游戏时钟、PIC 参考钟、调试暂停与文件保护。U-021 冻结后复核适用性；不把游戏时钟本身当作真实秒的速率证据。
- **刺激与预算：** agent 优先用已声明、回读合格的 BIOS 键盘/设备输入进入任务、跳过媒体和接敌；不开火、不停靠是初选策略，不要求被动等待必然成功。不改写生命、位置、RNG、主/子状态或救援计数，P3-10 的受损注入授权不适用于本任务。D-02 在采样前确定每族启动次数、游戏/宿主时间和停止预算；原失败运行时长只作规划依据，不是可达性证明。
- **集中读数：** 按事件锚取损失入口、计数、被毁视角、逃生舱到期/损失处理、恢复前后以及失败处理。恢复前读取旧移动块/油门、武器、资源、来源记录、通讯限频、候选基地及顺序，恢复后读取它们的实际变化；只比较完整操作数的规则，不用一个位置快照推断全部重置。
- **读数边界：** 明确停在 `0x67b98` 内部返回还是外层 `0x32e14` 完成后，不能将外层才写入的对象状态、移动块或计数要求提前。第三次损失记录清零前计数、失败分支与页面/过场结果；原版提示的两个选项归 G-06，不额外运行复刻它们。
- **整合与复用：** 原则上一次运行覆盖三次损失、两次恢复与一个失败；已有完整合格运行能满足时不重跑。B-009 的被毁片段只补相应计时证据，不能替代同次尝试的计数链。计时尽量使用原程序写入的时间戳和稀疏停止点，不为已有结论再密集单步。
- **不足或不一致：** 样本不合格与行为不一致分别报告；不一致不能以重跑直到通过掩盖。预算用完先记录缺口、尝试与恢复条件；只有经批准的新预算才继续。优先修配方或利用其他计划运行，不默认请用户游玩。确有 agent 无法完成的操作才请求最小帮助；未取得的必需证据仍为 blocked。

### 持久化与兼容

本任务不引入存档、IndexedDB/localStorage 写入或高分榜。默认只增加既有内容的消费者，不因此递增转换器；若发现必需 payload 缺口，则先修订 P3-03，变更转换器/内容版本、拒绝不兼容缓存并明确提示重新导入，不用猜测值兼容。replay 另供内容，校验 rulesVersion、实际格式版本、完整身份与 setupHash；不迁移旧录制，不嵌入原版文本。结果只在本次运行内存中；重试使旧 run/transition 凭证失效，返回菜单才释放对应 owner。不清理玩家资源缓存。

## 技术决定

1. **单任务也保留退场：** 用户本轮选择保留主状态 0/1 和既有 `mission-teardown`。先锁存结果，清理完成再停止；不增加下一关、状态 2 的 Core 页面流程或子状态 6 的结束战役玩法。
2. **锁存结果与停止模拟分离：** 保留原定阶段顺序，D-01 定稿锁存 tick 的剩余工作及清理边界。只有退场完成的 tick 才是最后 tick；其后的调用拒绝不锁存健康世界，结果页读取冻结摘要，不从已移除的玩家反算。
3. **救援接纳 G-02 零媒体时间：** 沿用 P3-02 技术决定 2，不宣称因此与原版整帧等价。按 C3 分别披露能量/被毁两条救援的媒体计入位置；引擎内倒计时、运动与生成不能随媒体一起省略。
4. **复用保持、单独处理完成：** 救援复用 P3-10 的有界序列与逐次凭证；正常完成有独立屏障和状态。故障/退出优先，完成后占位永不重启模拟。
5. **区间消息在结果页显示：** 区间消息是总结文字，不是飞行中的消息；结果页从导入内容解析并标注来源，Core 只保存引用。被排除的方案是在飞行中显示：原版不这样做，会改变信息呈现。
6. **P3 不判定勋章（G-06）：** 保留生成时的推荐选择，但 Q-08 必须核实实际副作用；不提前声称未追踪代码没有规则影响。发现必需读者则先调整契约。
7. **重试使用 P3-04 的重开路径：** 预选上次已确认的僚机、同一内容身份/固定难度、重新抽取种子并从 tick 0 创建新世界；不是复用旧种子或声称原版战役保存等价。同一 replay 仍要求相同初态、种子和有效 tick 输入。
8. **成功证据优先复用，不以决定升级事实：** B-003 的成功页面观察与具体触发路径分别保持原置信度。必须核实复用证据是否覆盖完整门槛，并取得 AC-13 的新版真实内容运行；缺少必需关联或时序时补采，不预先判为已确认/已完成。
9. **失败链集中取证：** 以一次运行覆盖两次救援和第三次失败为首选，不把一次视为充分性保证或硬性豁免。D-02 先规定合并窗口、合格条件和有界预算，再由 agent 优先执行。
10. **保留验收门槛，按缺口最小补采：** 用户本轮已明确选择。代码足以回答的离散规则不强迫开机；必需运行量没有证据时仍为 blocked。撤销初稿八项自动豁免，不沿用其他任务的特定豁免来代替本任务验收。
11. **跨 tick 状态由本任务拥有：** 救援计数、段 2 计数、流程到期时刻与僚机损失计时都是具名的快照状态，以静态调用接入 P3-07 的规则位置，不用 Runtime 订阅者回写。
12. **先定方向，后定细节：** 本 spec 批准方向、研究范围与验收要求；研究之后才能确定的字段，按[实施关卡](#实施关卡)在依赖它的工作开始之前定稿。

生成时已按用户的推荐选择授权起草；本轮两项新的明确选择见[审批](#审批)。这些选择不等于完整 spec、实施关卡或其他任务契约已批准，也不能代替原版证据。总计划与 ADR 中的冻结决定没有改变。

**1. 精确判据的依据**

- **时间链：** 本任务每个时间链节的锚都是游戏写入的时刻：主状态 4、5 共用的期限 `0x18681c`、信标期限 `0x186854`、僚机损失期限 `0x186818`、逃生舱到期与玩家的延迟爆炸计时。各自写入的是本帧还是上一帧的取样、比较严格与否，都已从原生指令确认（[Numbers on the flow and rescue paths](../../../original/formats/executable.md#numbers-on-the-flow-and-rescue-paths-p3-110102)、[C3](../../../original/formats/executable.md#c3-cross-frame-consumption-by-the-main-flow--confirmed-code)）。
  - **已有运行先例：** 同一套链节代数已在原版运行中逐单位成立。非严格与严格截止见 p-b-01 的逃生舱 0x140 与延迟爆炸 0xC0（[B-009](../../../original/behavior/B-009-combat-rules.md#原版一侧的逐类判定)，P3-07 的 D-02 判定）；上一取样截止见 P3-10 的停靠期限（[P3-10 D-02](../10/spec.md#d-02-连续行为判据已批准)第 1 条）。
  - **没有运行先例的链节：** 只有主状态 4、5 的“上一取样严格截止”。它的规则同样来自原生指令，由 S 族的读数按第 2 条的第 2 式检验，不预设容差。

  所以全部时间链都按链节归一化后精确比较。
- **离散量：** 主状态、子状态、计数、视角字段、选择值、候选数与序号、抽取次数都是整数；结果字、总结引用与结局变体是离散值。读数本身没有误差，按独立的代码期望精确比较。
- **恢复字段：** 救援的成对暂停都在同一次调用之内：`0x32e14` 的入口与返回，`0x67b98` 的入口与返回。两者之间只有阻塞播放的过场，没有规则更新。因此规定改变的字段须等于 Φ，规定保留的字段须逐位不变，没有运动、能量或碰撞的合法变化需要扣除。
- **不纳入精确比较的部分**（第 2 条的已批准差异逐项处理）：过场用时、退场帧数、锁存后的命令、扇区预算、Warp 中能量救援的油门越界，以及键盘轮询的取样节奏。

**2. 通用规则**

- **单位与分辨率：** 时间用游戏时钟单位（1/64 秒）。原版同一次运行中样本的奇偶不变、步长为偶数（[B-009 的误差来源](../../../original/behavior/B-009-combat-rules.md#误差来源)），新版每 tick 2 单位，所以两边的相对时刻都是 2 的倍数，时间分辨率为 2 单位。计数、状态与整数字段按 1；f32 按位读取。判据不使用真实秒、模拟器时间或宿主时间。
- **时间的来源：** 锚 = 游戏写入的时刻减去规则常数 C：

  | 锚 | 取法 |
  |---|---|
  | 结算等待的起点 | 主状态 4 的期限 − 0x140，即轮询帧的上一帧取样 |
  | Warp 推迟后的起点 | 新期限 − 0x140 |
  | 结果延时的起点 | 主状态 5 的期限 − 0x3C0 |
  | 信标的起点 | 信标期限 − 0x3C0 |
  | 僚机计时的起点 | 僚机损失期限 − 0x780 |
  | 逃生舱的起点 | 到期 − 0x140，即逃生舱首次更新的取样 |
  | 延迟爆炸的起点 | 计时 − 0xC0，即被毁的取样 |

  生效帧取自事件暂停的帧样本与步长 s（本帧与上一帧的样本差）；帧数 n 取帧计数之差。
- **链节：** P₂ 为新版在 2 单位/tick 下从锚到生效帧取样的值，C 为规则常数，d 为原版记录的偏差：

  | 链节 | 规则 | P₂ | 原版的 d 与有效范围 | 本任务的使用 |
  |---|---|---|---|---|
  | 非严格截止 | 第一个满足“取样 − 锚 ≥ C”的帧 | 2⌈C/2⌉ | 0 ≤ d ≤ s − 2，s 为生效帧的步长 | 逃生舱到期（C = 0x140） |
  | 严格截止 | 第一个满足“取样 − 锚 > C”的帧 | 2⌊C/2⌋ + 2 | 同上 | 玩家的延迟爆炸（C = 0xC0） |
  | 上一取样非严格截止 | 第一个满足“上一帧取样 − 锚 ≥ C”的帧（`0x3266c` 读上一帧取样，C3） | 2⌈C/2⌉ + 2 | 拆成到“第一个取样 ≥ 锚 + C 的帧”的非严格截止，加 n = 1 的帧链节，分别核对（下条） | 信标（0x3C0）、僚机损失（0x780） |
  | 上一取样严格截止 | 第一个满足“上一帧取样 − 锚 > C”的帧 | 2⌊C/2⌋ + 4 | 拆成严格截止加 n = 1 的帧链节，分别核对（下条） | 结算等待与每次 Warp 推迟（0x140）、结果延时（0x3C0） |
  | 帧 | 事件在 n 帧之后 | 2n | d = Σ(sⱼ − 2)，sⱼ ≥ 0 为这 n 帧各自的步长 | 全清写入任务状态 → 下一次子状态 0 的轮询（n = 1）；救援 → 下一次流程分派（n = 1） |
  | 同帧 | 同一次调用或同一条消息之内 | 0 | 0 | 逃生舱到期 → `0x32e14(1)`；信标到期 → 子状态 2 → 清空 → `0x32e14(0)`；第三次损失 → 任务状态 4 → `0x3351c` |

- **P₂ 的起点：** P₂ 都从锚算到生效帧的取样。主状态 4、5 的锚是轮询帧（或完成帧）的上一帧取样，所以在生产步长下，生效帧的取样比该帧本身的取样晚 C + 2 单位（0x142、0x3C2）。上一取样截止的两个分量分别核对：截止分量 d₁ = 第一个满足条件的帧的取样 − 锚 − P₁，0 ≤ d₁ ≤ s₁ − 2（s₁ 为该帧步长，P₁ 为对应的本帧截止的 P₂）；帧分量 d₂ = s₂ − 2（s₂ 为生效帧的步长）；总偏差为二者之和。
- **判据（归一化后精确）：** Φ(S, d) 按已确认的规则把窗口内各链节与离散写入合成期望值。
  - **S 的内容：** 只含原始输入：窗口起点的状态；操作数（位置、速度、能量、计数、候选链表）；外部输入；随机抽取的结果（`rand % 64`、`rand % count`、世界缺省的两次抽取）。
  - **确定性的分支：** Warp 推迟还是发出完成消息、救援还是失败、有无候选、是否因子状态推迟，都由 Φ 从 S 推出，不取自被测运行；原版一侧推出的分支还须与读到的相同，否则为单次转移的不一致。
  - **实现：** Φ 由私有脚本按 `docs/original/` 的事实独立实现，不调用被测的 Core。

  对每个窗口：
  1. 新版：Q新 = Φ(S新, 0)，S新 读自新版本次连续运行；
  2. 原版：Q原 = Φ(S原, d原)，每个 d 都在有效范围内。

  两式都精确成立：时间按 2 单位，计数与整数按 1，没有残余容差。第 1 式不成立，判为新版不一致；第 2 式不成立，说明原版与已确认的规则不符，回到研究（[达不到门槛时](#原版研究)），不放宽判据。
- **两层：**
  - **单次转移层：** 取原版在锚点读到的完整前态操作数，交给 Core 的内部规则函数（私有脚本可以调用它们），比较其后态与原版读到的后态；同一转移另须满足第 2 式。离散类别与第 4 条的数值都在这一层，它们的跨版本结论只来自这一层。
  - **连续层：** 来自 19 的新版连续运行（正式 World、2 单位/tick、真实内容、自己的种子与输入），每个窗口须满足第 1 式。时间类别的跨版本结论来自下一条的配对。离散类别在这一层只要求新版窗口满足第 1 式、原版窗口满足第 2 式，不要求两次运行走到同一取值（例如被毁的基地数相同）。
- **配对（时间类别）：** 同一链节与常数，窗口末端的分支相同（Warp 推迟或发出完成消息；因子状态推迟或在子状态 0 中消费），工作条件相同（到期时的子状态）。抽取结果不作配对条件。
  - 每个原版窗口至少须有一个配对的新版窗口，否则该类没有跨版本结论；只做单边核对的窗口不算对照样本。
  - 19 的运行须为原版取得的每种时间窗口提供同型窗口。缺少时由 19 追加新版运行，并纳入该类的全部新窗口；这不需要原版启动。
- **已批准的差异**（原版一侧按记录计入 Φ，新版按约定取值；单列，不判为不一致）：
  1. **救援过场用时**（[技术决定](#技术决定) 3，P3-02 技术决定 2）：原版的救援列表阻塞播放，它的用时由下一次取样吸收：能量救援由本帧的 `0x25894` 吸收，被毁救援由下一帧吸收（C3）；新版为零。这一步长不进入任何时间窗口，跨过它的窗口在救援之后的事件处重新起锚。单次转移层只核对用时进入哪一次取样：救援调用两端暂停的样本相同而参考钟前进，下一次样本更新吸收这段时间。
  2. **退场**（ME-17 决定 2、11）：原版的退场在结果页面之后，帧数为高概率；新版在锁存的下一 tick 完成。不比较退场帧数；退场的离散次序只按代码（第 6 条）。
  3. **锁存后的命令**（ME-17 决定 3）：窗口在锁存处结束。
  4. **扇区预算与 Warp 中能量救援的油门**（ME-17 决定 7、8；研究缺口 G-1、G-2）：原版若出现，记为该研究缺口的运行观察，不判为新版不一致。
  5. **任务原点**：原版的原点含出发过场（B-003），窗口不按任务原点的绝对时刻对齐。
- **窗口的选取：** 逐类表的锚机械地用于原版的全部读数与新版的全部事件。判定前列出每个候选窗口及其纳入或排除的原因，不能按比较结果挑选。
- **输入边界：** 原版只在键盘轮询读取按键，这一取样节奏归 P3-05 的 R-23。输入只用来建立工作条件（目标、自动驾驶、地图、Warp 的开始），从按键到首个效果不进入本任务的时间链。
- **排除：** 以下窗口不计入样本：
  - 读数不合格，或缺少某个链节的生效样本；
  - 不满足配对条件；
  - 窗口内有游戏暂停、选项页，或跨过第 1 项已批准差异的步长；
  - 第 4 条所列的边界样本。

  排除的窗口逐个写明原因；排除后数量不足时，按第 7 条处理。
- **独立性：** 启动时的时钟状态与刺激时机都相同的两次运行逐值相同，只算一次。本节的判据是逐窗口成立的精确式，不做统计推断，所以各类的最少样本按分支覆盖给出（第 3 条）。同一运行内的多个同型窗口用于覆盖，不算独立重复。
- **区分情形：** 各类的全部窗口合计应包含下列情形；没有出现时按 D2-6 处理：
  - 每种截止至少一次在步长 2 的帧上取样恰等于“锚 + C”，以区分 ≥ 与 >；
  - 每种帧链节至少一帧 s ≠ 2，以区分按帧计与按时间计；
  - 救援候选中至少一个对象状态 ≥ 4 或被毁标志为 1，以区分“不过滤”与“只计存活”；
  - 能量救援时玩家有目标，以区分“保留目标”与“清除目标”。

  Warp 推迟时“新期限 − 旧期限 − 0x140”等于推迟帧的上一帧取样减旧期限，必然 ≥ 2，所以每次推迟都区分“从当前取样重排”与“从旧期限重排”，无须另设条件。
- **媒体设置与配置：** 只适用于基准设置：过场开启（`CINEMATIC HIGHRES`）、GAMEHIRES 为真、音效与音乐 100，`fixed 40000` cycles。复用的 E-1 至 E-4 也是这一设置；其他设置的样本不混合。U-021：判据只依赖记录的步长，与 cycles 无关；结论只适用于 fixed 40000，冻结值不是 40000 时，须在冻结配置下重新满足各类的最少样本。

**4. 单次转移层的连续数值**

- **舍入的前提：** f32 写回的舍入方向在一般情形下没有静态结论（U-009），新版按已批准的就近舍入。原版读数先按就近重算：就近与截断结果相同的样本须逐位相等；两者不同时，与就近一致的样本照常计入，只与截断一致的样本单列为 U-009 的新矛盾，既不计入样本数，也不判为一致。
- **救援位置：** z := F(z + 2000.0f)，加法在双精度中精确，只有一次 f32 舍入；世界检查的一次移动按 [placement mappings](../../../original/formats/executable.md#placement-mappings-p3-0202) 逐步计算；象限姿态的常数逐位相等。
- **救援后的油门：** 比例 F(速度 ÷ 机型 +0xB8) 是双精度除法后的一次 f32 舍入（按上面的前提），乘 128.0 精确，向零截断为整数。就近与截断的比例给出不同油门时为边界样本，单列。
- **总结比例：** SCEN 3019 的可达比例为被毁数 ÷ 4 × 100，在二进制中精确，与 x87 精度无关。
- 其余比较量都是整数或位拷贝。

  - **理由：** 缺口表中的必需运行量只来自失败链与成功链两条终态链，二者在同一次尝试中互斥，必须分开；其余缺口都能并入这两条链的窗口，或按第 6 条处置。F 的三种刺激都有完整运行的先例（E-1、E-2、E-3），只留一次重做；S 的全清从未有运行到达，是主要的不确定性，多留一次。
  - **被排除：**
    - 为每个缺口或分支单独开机：重复进入任务，违背“最小补采”。
    - 不跑 S，成功链只用 E-5：E-5 没有任务身份与时间链，spec 的 R-21 要求一条连续成功链，AC-15 将阻塞。
    - 不设上限，或设更大的上限：与尽量少用 DOSBox-X 的要求相反；上限用完仍可经修订申请。
    - 关闭过场运行 F，以避开过场用时：与复用的 E-1 至 E-4 的媒体设置不同，样本不能合用；过场用时已按已批准差异 1 处理。
- **D2-2 F 的损失次序与刺激。**
  - **推荐：** 第一次被毁、第二次能量耗尽、第三次在地图中被动等待（第 7 条），阶段到上限时改用 Warp 耗尽能量。
  - **理由：** 一次运行同时覆盖两种救援入口（C-9 需要 p = 1 与 p = 0）与一次失败。接近敌机缩短被动等待。耗尽之前选中目标，使能量救援“保留目标”可以区分。第三次损失若是被毁，同时取得 #7 的地图情形；此后不再有救援，地图标志的遗留不影响之后的读数。
  - **被排除：**
    - 全程被动：损失的种类与次序都不可控，E-1 只有一个 15.7 分钟的样本。
    - 三次都用能量：没有被毁救援，C-5、C-7 与 C-9 的 p = 1 都缺失。
    - 在第一次或第二次损失时打开地图：救援后地图标志保持 1，可能干扰之后经地图选点的 Warp。
- **D2-3 复用资格，包括预实验运行 t2-01。**
  - **推荐：** 按第 5 条接纳；t2-01 与 E-2、E-3 同等对待，只作 C-14 的观察，不计入任何时间链、字段集或计数链，也不作被毁救援的样本。
  - **理由：** 资格取决于运行本身是否合格（`complete`、同一基准与配置、每个读数暂停的身份检查、没有注入），不取决于它在 P3-09 中的角色。P3-08 于 2026-10-15 也曾按资格复用预实验运行。
  - **被排除：**
    - 排除全部预实验运行：少一个独立开局，却不节省任何启动。
    - 把 E-2 至 E-4 当作救援字段或时间链的样本：它们的读数在救援之后数千单位的轮询，期间还有其他写入者。
- **D2-4 不可控分支的处置。**
  - **推荐：** #6 (a)、(b)、(c)，#7 的停靠、基地视角与 Warp 情形，以及 #8，都按必需运行量对待。在 F、S 的已计划启动中设条件暂停，机会出现即按 C-5、C-9、C-10 与 C-16 至 C-18 判定。F、S 的启动用完仍未取得的项记为 blocked；届时由协调者把未取得的项、已尝试的途径与可选的处置（追加启动、改作代码与 Node 的限定结论、保持 blocked）逐项交用户决定。现在不预先批准任何限定结论。
  - **理由：**
    - 用户选择保留验收门槛、不自动豁免；06 把这些项列为未观察的分支，其中 #6 (b)、(c) 是跨状态的因果与时序，#7 需要各情形中完整的被毁与救援状态链，#8 是位置分支。
    - 它们都需要合规刺激无法安排的巧合：全清恰好发生在被毁序列或停靠等待中、停靠中被导弹击毁、四座基地全部移除后再救援。没有可控的合规途径，所以只在已计划的启动中机会采样，不为它们增加启动。
    - 是否接受限定结论，等知道哪些项真的缺失之后再逐项决定，不需要为此提前开机，也不会在机会样本出现之前关闭门槛。
  - **被排除：**
    - 现在就批准为代码与 Node 的离散结论：会在不知道机会样本是否出现之前关闭门槛项；#6 (b)、(c) 含跨状态时序，#8 含位置链，不是纯离散。
    - 为这些分支各设专门的配方族：依赖巧合，预算无法有界。
  - **2026-10-31 修订 1：** 经用户批准，本条各项在有界的原版尝试之后改按代码与 Node 的限定结论判定；新判据、尝试与逐项结论见[审批节的修订记录](#2026-10-31-d-02-修订-1r-22-八项p3-1621)。上面的原文保留不改。
- **D2-5 僚机损失计时（#5）。**
  - **推荐：** 在 S 中机会采样：开局后命令僚机进攻，设条件暂停。只有“设置 → 到期判定通过并入队”的窗口能关闭 #5，按 C-13 判定；被全清丢弃与被子状态推迟只作补充覆盖。S 的启动全部结束仍没有这种窗口时，#5 记为 blocked。恢复条件：之后任一合格的原版运行取得它；或用户届时决定增加一次专门启动，或改作限定结论。
  - **理由：** 0x780 是时间链，属必需运行量，丢弃分支根本不到期，推迟分支单独也不显示到期的取样。僚机是否被毁取决于 AI，没有可控刺激，专门启动也不能保证取得；先并入 S 不增加启动。
  - **被排除：**
    - 现在就预留专门的配方族（1 至 2 次）：同样不可控，并增加启动。
    - 因为与信标同属“上一取样非严格截止”就改作代码结论：spec 与 06 都明确不以相似性豁免。
  - **2026-10-31 修订 1：** 同 D2-4 的修订（[修订记录](#2026-10-31-d-02-修订-1r-22-八项p3-1621)）：两次专门尝试未取得窗口，#5 改按代码与 Node 的限定结论判定；限定结论依据的是代码链与 Node 情形，不是与信标的相似性。
- **D2-6 区分情形没有出现时。**
  - **推荐：** 不为区分情形追加启动。该类照常按第 2 条判定，报告注明哪种区分情形没有出现，以及这一点只由原生指令与新版第 1 式支持。
  - **理由：** 新版以 2 单位步长逐 tick 推进，每个期限都恰有一个取样等于“锚 + C”，第 1 式本身已区分 ≥ 与 >、按帧与按时间；原版一侧的规则来自原生指令。基准步长以 2 为主，计划的窗口中这些情形大概率自然出现。
  - **被排除：** 像 P3-10 那样，达到最少样本仍未出现就补采：要为概率事件追加启动，与尽量少用 DOSBox-X 的要求相反。

- **工程检查：** 实现时运行 `pnpm check` 和 `pnpm check:compliance`；修改 baseline/Ghidra 工具分别运行 `python3 -B -m unittest discover -s tools/baseline -p 'test_*.py'` / `python3 -B -m unittest discover -s tools/ghidra -p 'test_*.py'`。仅生成/审阅文档时做链接、元数据和路由检查，不运行会构建应用的合规聚合命令。
