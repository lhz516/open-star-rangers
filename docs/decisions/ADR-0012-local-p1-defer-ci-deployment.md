# ADR-0012：P1 只做本地验证，CI 与部署移至 P5

## 背景

规划 P1 任务拆分时，用户明确要求当前只管本地验证，并确认将 CI 与 SWA 部署正式移出 P1 退出条件，统一归入 P5 发布阶段。本地原版数据隔离、哈希扫描与许可自检仍保留在 P1。

这改变总计划 §12 的阶段分配，不改变产品架构、最终发布门槛或依赖许可证政策。

## 决定

- P1 交付本地可运行的 Core、Runtime、UI projection/React、Three.js、菜单/导入占位与最小输入适配，并通过 Node、工程检查和合成浏览器验证。
- 同一输入 replay、一致性、生命周期清理及原版资源隔离仍为 P1 要求。仓库与本地构建产物哈希扫描、依赖许可判定及第三方声明可以在本地运行，不依赖 GitHub Actions。
- GitHub Actions、CI 中的合规自动门禁、仓库检查保护和 SWA 预览/正式部署的建设与实测统一归入 P5，不是 P1 的交付或阻塞条件。
- P1 的阶段评审只依据调整后的本地退出条件；通过时明确说明未完成的 CI/部署已归 P5，不用“本地预览”冒充云部署结果。
- P5 仍须取得真实 CI、部署与发布证据；此决定不豁免总计划 §9–11 的最终要求，也不放宽首次公开前的许可、名称、原版内容隔离与秘密保护要求。
- spec/goal/execute 工作流和本地 commit 授权不变，不因这次阶段调整而授权 push、部署或云资源修改。

## 考虑过的其他方案

- 保留 CI/部署为 P1 暂缓项：仍会阻止完整 P1 通过，与用户希望先完成本地骨架的安排不符。
- CI/部署改为 P2 并行项：会扩大以玩法资源为中心的 P2；用户选择统一归入 P5。
- 同时移除本地合规检查：会推迟发现误带原版文件和许可问题，因此保留本地检查。

## 后果

- P1 不需要 GitHub/Azure 凭据、远端 workflow 结果或云预览 URL 即可验收。
- 自动化和云发布工作由 [P5 阶段索引](../plan/p5/tasks.md)承接；P2/P3 的资源与玩法边界不变。
- [P1 任务计划](../plan/p1/tasks.md)只覆盖本地交付，各任务仍分别生成 spec、goal 与 subtasks。
